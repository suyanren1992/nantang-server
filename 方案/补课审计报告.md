### 4.3 关键发现

**教程的最大效用不在「提前预防」——在「事后诊断」。** 南塘的真实节奏是「先修 bug 后补课」（BUG_TRACKER:1163）。教程 18/19 安全篇在 D 系列施工时被直接引用（六段提示词），效果立竿见影。但测试篇（26）和安全审计篇（27）是 bug 出了之后才回头读的——A-7 校核不到账如果事前对照过 26 篇的「三种走法」，不会被「✅+N NT」的假成功骗过去。

**打回是教程有效率的反向指标。** D-9 打回两次（漏 14 处原生 prompt/confirm + 漏 mobile-bundle.js）——如果施工方在动手前对照过 0.2 总篇下的「实施真元文档」要求，应该先逐文件 grep 列出清单。卡面没写清楚文件列表，施工方也没要求补——两边都没按教程来。

## 八、谏臣二次对抗（二营 Codex · 2026-07-26 02:30 · 修正版）

### 🔴🔴 硬伤 8（重大）：所有"行锁"测试在 SQLite 下静默失效，D-5/D-17/D-26 锁路径从未被真实验证

**事实链**：

1. 生产数据库 = Neon PostgreSQL，驱动 `asyncpg`（requirements.txt + database.py:14-17）
2. 测试数据库 = 临时 SQLite，写死在 `server/tests/conftest.py:17` `sqlite+aiosqlite:///...`
3. **SQLite 方言不支持 `SELECT ... FOR UPDATE`**——SQLAlchemy 文档明确：SQLite 方言对 with_for_update() 静默接受但 SQLite 引擎本身只支持事务级表锁，不支持行锁
4. 我们代码里 29 处 `with_for_update()` 实锤：
   - `server/routes/nt.py`: 25 处
   - `server/routes/tasks.py`: 3 处
   - `server/routes/accommodation.py`: 1 处
5. **结果**：
   - D-5 行锁修复、D-17 populate_existing 补漏、D-26 住宿费日结行锁——这三处"对齐 D-5/D-17 判据"的资金路径，**测试全绿 = SQLite 下根本没加锁，锁逻辑从未被验证**
   - 测试 D-5 "顺序模拟并发"之所以通过，是因为 SQLite 串行化隔离+await 顺序执行天然无并发，锁不锁都一样
   - 如果 PostgreSQL 下 `with_for_update()` 写漏表、锁序错、populate_existing 漏放，测试抓不到

**为什么这不是危言耸听**：
- 这不是报告作者的错——作者按"南塘实证"列 A 级，D-5 commit 存在、线上没炸就是实证
- 但"线上没炸"和"锁真的生效"是两回事——并发提现要在高负载下才会触发
- 补课盲区 #7（异步并发/行锁/TOCTOU）的存在本身证明了我们在这方面没有外部参照，全靠自己摸

**补救建议**：
1. conftest.py 加方言告警：`if engine.dialect.name == "sqlite"` 时在测试日志加 WARNING"锁相关测试在 SQLite 下不验证 FOR UPDATE 语义"

|---|---|---|---|
| 1 | Render 支持 push-to-deploy、免费层、环境变量、PostgreSQL | ✅ 准确。但免费 PostgreSQL **30 天到期永久删除**。南塘用的是 Neon 而非 Render PG——无此风险 | [Render Pricing](https://render.com/pricing)、中堂备忘录:11「Render Web Service + Neon Postgres」 |
| 2 | Neon 是 serverless PostgreSQL，有分支、autoscaling、scale-to-zero | ✅ 准确。存储计算分离架构。免费层 100 CU-小时/月、0.5 GB 存储。2025 年 5 月被 Databricks 收购 | [Neon GitHub](https://github.com/neondatabase/neon)、[Neon 架构文档](https://neon.tech/docs/introduction/architecture-overview) |
| 3 | FastAPI SQLAlchemy async `with_for_update()` 实现行锁 | ✅ 准确。`SELECT ... FOR UPDATE` 在 PostgreSQL 下行锁有效。**SQLite 不支持 FOR UPDATE**——Codex 硬伤 8 属实 | [SQLAlchemy 文档](https://docs.sqlalchemy.org/en/20/orm/queryguide/#sqlalchemy.orm.Query.with_for_update)、Stack Overflow 并发实测 |
| 4 | SQLite 有单写入者瓶颈，生产环境并发写入需 PostgreSQL | ✅ 准确。SQLite 1 个写入者/次，>5 并发写入即瓶颈。PostgreSQL MVCC 支持 100+ 并发写入。南塘 C-4 迁 Neon 是正确的 | [SQLite 官方文档](https://sqlite.org/wal.html)、多源生产迁移案例 |
| 5 | `?v=` 查询字符串版本号是 PWA 缓存破坏的常见做法 | ✅ 准确。查询字符串版本控制是标准缓存破坏技术。推荐层级：内容哈希文件名 > 查询字符串 > 手动缓存名版本控制 | PWA Workbox 文档、MDN Web Docs |
| 6 | Docker 不推荐纯小白优先用（「把简单放启动、复杂留维护」） | ✅ 准确但偏主观。Docker 官方文档承认数据持久化/网络/资源限制是常见新手陷阱。Render 对此场景更友好 | Docker 官方文档持久化章节、Render 对比文章 |
| 7 | 补课教程没有并发控制/幂等设计/跨端命名规范 | ✅ 准确。标准 Vibe Coding 教程聚焦 CRUD 和部署，不讲 `with_for_update()`、幂等键、camelCase/snake_case 对齐 | 付政 42 篇全文无 `with_for_update`/`idempotency`/`camelCase` 匹配 |
| 8 | Cursor 是 AI IDE、Codex 是超级 Agent App——两者定位不同 | ✅ 准确。Cursor 基于 VS Code 的 AI IDE；Codex（现为 Claude Code 一部分）是 Agent 型工具。但 2026 年两者功能趋同 | Cursor 官网、Claude Code 文档 |

### 新发现的事实风险

| 风险 | 详情 | 对南塘的影响 |
|---|---|---|
| Render 免费层 Web Service 15 分钟无活动休眠 | 免费层 750 小时/月，闲置 15 分钟后 spin down，唤醒需 30-60 秒 | 南塘若在免费层且深夜无访问，第一个用户早上打开会等 30-60 秒冷启动 |
| Neon 免费层 100 CU-小时/月 | 超出后数据库暂停。0.25 CU 起算，持续运行约 16 天/月 | 南塘 20 人社区轻量使用应不超，但需监控 |
| `?v=` 版本号不是最优方案 | 行业金标准是内容哈希文件名（`app.3f2c1a9.js`），查询字符串可能被某些 CDN 忽略 | 南塘用 Render（非自配 CDN），`?v=` 有效。若换 CDN 需评估 |

### 验证结论

报告中 8 条外部事实陈述**全部准确**。额外发现 3 个事实风险——**Render 免费层冷启动**是最可能被用户感知的问题。

> **太傅注**：审计自己的审计——上网验证不是走过场。Codex 发现的硬伤 8（SQLite 锁静默失效）被 SQLAlchemy 官方文档证实。报告的 A 级判断基于「线上未炸=代码正确」，但 `with_for_update()` 在 SQLite 下根本没跑——这是「实证主义」的边界：你只能证明你测了的东西。
