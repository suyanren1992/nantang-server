**关键发现**：整个数据库只有 **3 条真正的外键约束**：
- `tenancies.user_id → users.id`
- `deposit_intents.user_id → users.id`
- `camp_builders.camp_id → camps.id`

其余所有表间引用都是裸字符串匹配，数据库层面不保证引用完整性。这是 SQLite 起步的典型遗留——没开 `PRAGMA foreign_keys = ON`。

## §三 NT 资金流向图（双池制）

> 经济系统已确认**双池制**：社区场地方池（`community_pool.balance`）+ 营地活动方池（`community_pool.camp_balance`）。
> 两个池都在 `community_pool` 表的同一行里，是同一张表的两个列。另有两个辅助池：储备池（`reserve`，用于提现）+ 冻结池（`frozen`，提现锁定中）。
> 多签钱包管理链上资金，地址配置在环境变量 `PLATFORM_WALLET_ADDRESS`。

### 3.1 钱的唯一真源

**答案：`nt_ledger` 是唯一真源（账本）。**

解释（人话版）：

- `nt_ledger` = 你的银行流水单。每一笔 NT 从哪来、到哪去、多少钱、什么原因，全记在上面。只增不删，不可篡改。
- `users.nt_balance` = 你钱包里显示的余额。它是从流水单算出来的——把你所有的收入减去所有的支出，就是这个数。
- `community_pool.balance`（及各子池）= 社区金库显示的余额。同理，从流水单算出来的。

当前代码在**同一个数据库事务里**同时更新流水单和余额，所以正常情况下它们一定对得上。验证端点 `/api/nt/verify`（`server/routes/nt.py:381-412`）做的事就是：把所有用户余额 + 所有池子余额加起来，和 `total_issued`（总发行量）对比，差超过 1 NT 就亮红灯。

**如果有一天对不上了**，以 `nt_ledger` 重算为准——因为流水单是 append-only，不可逆；余额是可变衍生值，可被 bug 直接改坏。流水单可以重放出正确的余额，但余额推不出流水单。

**现状一句话**：`nt_ledger` 是账本，`users.nt_balance` + `community_pool.*` 是钱包。账和钱包在同一个事务里同步写，正常不会对不上。但如果出了 bug，账本是最终裁决者。

### 3.3 钱的循环全路径（人话版）

```
钱从哪来的？
  → 系统启动时创建社区池，里面有 500 NT（nt_helpers.py:45-52）
  → 池子钱不够时每天自动补 20 NT（nt.py:1056-1057）
  → 有人从链上充值 NT 到多签钱包，链扫描器检测到后加到用户余额 + 储备池（chain_scanner.py:164,170）
  → 管理员可以手动给某个人或社区池加 NT（nt.py:288,300）

钱怎么花的？
  → 用户之间转账，从一个人钱包到另一个人钱包（nt.py:220-221）
  → 花 NT 消费，钱从用户钱包回到社区场地池或营地活动池（nt.py:262-270）
  → 发布任务要托管 NT——钱从用户钱包（或社区池）锁进 task_escrow（tasks.py:99-126, cron.py:92-93）

钱怎么挣的？
  → 完成任务，托管金释放到执行者钱包（nt.py:574,581,569-571）
  → Peer 校核通过，从社区池发 NT 给做事的人和校核的人（nt.py:869,879,891）
  → 离线 earn 同步，从社区池发 NT（nt.py:971-972）
  → 任务取消/删除，托管金退回（nt.py:649-666, tasks.py:172-184）

钱怎么烧的？
  → 管理员 cashout 提现，NT 从用户余额销毁，total_issued 减少（nt.py:320-323）⚠️ 此端点已废弃但代码还在

住宿费怎么走的？
  → 每天 00:05 cron 自动扣：有钱的从余额扣到社区池，没钱的记欠费（nt.py:1039-1050）
  → 退房时结清欠费，从余额扣到社区池（accommodation.py:92-95）
  → 换房时旧房间欠费同样结算（accommodation.py:42-47）

提现怎么走的？
  → 用户申请提现 → NT 从余额转入冻结池，储备池同步扣减（nt.py:369-371）
  → 管理员在 admin.py:50-87 confirm/reject（批① D-18 已上线）。⚠️ confirm 对 NTLedger entry 查询未加行锁——两个管理员同时确认同一条可能双花

池子内部怎么调的？
  → 盈余划拨：运营池太多钱（>1000），超出 500 的转入储备池（nt.py:1064-1067）
  → 自动调水：运营池钱不够（<150），从储备池补到 300（nt.py:1074-1078）
  → 储备池主要用途：承接链上充值 + 给提现提供 NT
```

### 3.4 住宿欠费（独立于 NT 流通）

`tenancies.debt` 是一条**不在 NT 流通圈内**的债务记录：
- 日扣时用户余额不够 → `t.debt += rate`（nt.py:1047）
- 退房/换房时有余额则扣款还债，没余额则记录欠费未结（accommodation.py:92-102）
- debt 是 INTEGER，不会自动扣利息，没有上限，不会强制追缴

## §五 风险清单

> 只列事实，不给方案。方案另发卡。

### R1 · 外键真空

**事实**：18 张表中，数据库级外键约束只有 3 条（`tenancies.user_id`、`deposit_intents.user_id`、`camp_builders.camp_id`）。`nt_ledger.from_user`、`nt_ledger.to_user`、`nt_tasks.poster`、`nt_tasks.assignee`、`verifications.doer`、`journal.user` 等全部是裸字符串。删除一个用户后，所有关联的流水/任务/校核记录变成悬空引用，数据库不会报错。

**实证**：`models.py` — 除上述 3 处外，无其他 `ForeignKey`。

### R2 · NT 余额可被两条路径同时改

**事实**：`users.nt_balance` 在同一时刻可能被以下路径并发修改：
- 用户自己发起转账（`nt.py:220-221`）
- 用户自己消费（`nt.py:262`）
- cron 每日住宿扣款（`nt.py:1039-1040`）
- 管理员 topup/cashout（`nt.py:300,320`）
- 任务结算（`nt.py:581`）
- 校核 earn（`nt.py:879`）
- 链上充值到账（`chain_scanner.py:164`）
- 离线 earn 同步（`nt.py:972`）

代码对这 8 条路径中的大多数加了 `.with_for_update()` 行锁——但 SQLite 的 `SELECT FOR UPDATE` 行为与 PostgreSQL 不同：**SQLite 在 WAL 模式下只对写事务排队，不真正阻塞读**。如果两条写路径在同一毫秒内读取了同一个 `nt_balance`，后提交的会覆盖先提交的，导致余额丢失。

**实证**：K-1 审计报告第八节已证实——`conftest.py` 写死 sqlite+aiosqlite，29 处 `.with_for_update()` 在测试中从未真正生效。

### R3 · 提现 confirm/reject 端点存在但 NTLedger entry 查询未加行锁

**事实**：提现两阶段完整实现——阶段一（`nt.py:369-371`，用户余额→冻结池）+ 阶段二（`admin.py:50-87`，管理员 confirm/reject）。批① D-18 已上线。但 confirm/reject 对 `NTLedger` entry 的查询（`admin.py:54-56` / `admin.py:73-75`）未加 `.with_for_update()` 行锁——两个管理员同时确认同一条提现申请，可能双重扣减 `frozen` 池。

**实证**：`admin.py:50` `@router.post("/withdraw/confirm")`、`admin.py:69` `@router.post("/withdraw/reject")` 两个端点存在且逻辑完整。`admin.py:54-56` 查询 entry 无 `with_for_update()`，锁仅加在 pool 行（`admin.py:60` `_get_pool(db, lock=True)`）。

### R4 · community_pool 是单行表但并发创建可能出两行

**事实**：`_get_pool()`（`nt_helpers.py:37-60`）的逻辑是「查不到就创建」。理论上两个并发请求同时查不到 → 都创建 → 第二行插入触发 `singleton` 列的 UNIQUE 约束报错。虽然概率极低，但一旦发生会导致整个 NT 系统崩溃。

**实证**：`models.py:94` — `singleton = Column(Boolean, default=True, unique=True)`

### R5 · tenancies.debt 无上限，无追缴

**事实**：住宿欠费（`nt.py:1047`）只记不追。用户余额不够就一直累加 debt，没有上限、没有利息、没有自动追缴。退房时余额不够就记一笔「欠费未结」流水然后清零 debt（`accommodation.py:99-102`），NT 实际蒸发。

**实证**：`nt.py:1046-1050`（只加 debt 不阻止入住）、`accommodation.py:99-102`（余额不够时 debt 清零但 NT 没收回来）

### R6 · nt_ledger 无审计字段

**事实**：`nt_ledger` 是财务核心表，但没有 `updated_at`、没有操作者 IP、没有请求 ID。出问题后只能看 `created_at` + `reason` 字符串推断，无法精确回溯是哪个请求、哪个 IP、在什么上下文下写的。

**实证**：`models.py:40-54` — `nt_ledger` 列清单。

### R7 · 公告表有 nt_amount 但不参与资金核验

**事实**：`announcements.nt_amount`（`models.py:249`）存储「某某完成某某获得 X NT」的金额展示，但这个数字不参与 `/api/nt/verify` 的总量校验。如果有人改了 announcements 里的数字，不会触发任何告警。

### R8 · Float import 死代码

**事实**：`models.py:2` import 了 `Float` 但全文件没有任何列使用它。虽然无害，但如果未来有人误用 Float 定义金额字段，会导致精度问题。

### R9 · 多签钱包私钥管理不在代码中

**事实**：代码通过 `PLATFORM_WALLET_ADDRESS` 环境变量引用多签钱包地址（`nt.py:17`），读取链上余额（`nt.py:487-504`），但私钥管理、多签流程、Gas 费支付等完全不在代码中。这是设计选择（安全隔离）而非缺陷，但意味着链上资金的实际控制权不在本系统内。
