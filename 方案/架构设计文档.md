## 一、分层道理

### 1.1 四层切法

南塘云村切成四层，每层只许干一件事，不许越界：

```
┌─────────────────────────────────────────────┐
│  L1  客户端静态站                              │
│      nantang-mobile/  纯 HTML/CSS/JS          │
│      负责：渲染 UI、本地状态、离线缓存             │
│      不许：直接写数据库、直接调链上合约             │
└──────────────────┬──────────────────────────┘
                   │  HTTP (JSON)
                   │  JWT 令牌鉴权
┌──────────────────▼──────────────────────────┐
│  L2  FastAPI 服务端                           │
│      server/  Python 3.14 + uvicorn          │
│      负责：鉴权、业务逻辑、NT 记账、数据同步        │
│      不许：存前端状态、管 CSS、做动画               │
└──────┬───────────────────────┬──────────────┘
       │  SQL (asyncpg/aiosqlite)│  RPC (web3.py)
       │                         │
┌──────▼──────────────┐  ┌──────▼──────────────┐
│  L3  Neon Postgres   │  │  L4  OP 链           │
│      数据库           │  │      Optimism L2     │
│      负责：持久化      │  │      负责：NT 代币    │
│      不许：跑业务逻辑  │  │      不许：高频写入    │
└─────────────────────┘  └─────────────────────┘
```

### 1.2 为什么这样切

**为什么不是 SPA + BFF（Backend for Frontend）三层**：南塘云村的"前端"就是静态 HTML 页面，没有 SPA 的路由/状态管理复杂度。加一个 BFF 层 = 多一层要维护的代码 = 多一层会挂的地方。FastAPI 直接面对客户端请求，因为业务逻辑够简单——大部分端点是 CRUD + NT 记账，不需要聚合多个微服务。

**为什么不是微服务**：Render 免费层只有 512MB 内存。拆成 5 个微服务 → 每个只有 100MB → OOM 风险。单体 FastAPI 在这个规模是最优解——等日活破 100 人了、内存不够了、某个路由模块变成瓶颈了，再拆。现在拆 = 过度工程。[技术栈文档 §1.1](./技术栈文档.md) 写了 FastAPI 选型理由。

**为什么数据库不跑在 Render 上**：Render 免费层 15 分钟无请求自动休眠——如果数据库也跑在上面，休眠 = 数据全丢。Neon 是独立服务，不跟 Render 一起休眠。而且 Neon 的 100 CU-小时/月免费层，比 Render 自带的 PostgreSQL 附加组件便宜（Render PG 最低 $6.5/月）。[技术栈文档 §2.1](./技术栈文档.md) 有完整选型理由。

**为什么 OP 链是独立层**：链上操作是异步的、有 Gas 费的、有延迟的。如果混进 L2 的业务逻辑里 → 一个链上 RPC 超时卡住整个 API 请求。所以 chain_scanner 是独立的后台协程（[server/main.py:23-31](../server/main.py#L23-L31)），跑在 FastAPI 的 lifespan 里但不阻塞 HTTP 请求。没配 RPC URL → 静默跳过，不炸。

### 1.3 每层的宪法级约束（跨层不改不报）

| 层 | 可以做的事 | 不可以做的事 | 违反例子 |
|----|-----------|-------------|---------|
| L1 客户端 | 渲染 UI、本地 localStorage、离线缓存、发 HTTP 请求 | 直连数据库、直连 OP 链 RPC、自己签发 JWT | `core.js` 如果 contains `new Web3(...)` → 红灯 |
| L2 服务端 | 鉴权、业务逻辑、数据库读写、发链上交易 | 生成 HTML、管 CSS class、存客户端 UI 状态 | `nt.py` 如果 contains `<div class=` → 红灯 |
| L3 数据库 | 持久化数据、索引、事务 | 跑 Python 代码、发 HTTP 请求、发邮件 | 用 PG 的 `pl/python` 扩展 → 红灯 |
| L4 OP 链 | 存 NT 代币余额、Transfer 事件 | 跑业务逻辑（业务逻辑在 L2，链上只管转账） | 在合约里写 `if user.role == "admin"` → 红灯 |

## 二、模块边界

### 2.1 服务端模块（server/routes/）

模块划分与职责边界见架构现状图 §2.2（[架构现状图.md:91-107](./架构现状图.md#L91-L107)）。以下写「为什么这样分」：

**nt.py（1092 行）为什么最大**：NT 经济核心——转账/消费/赚取/提现/校核/住宿日扣/离线 earn 同步/池子调水/总账核验，9 个关注点全在一个文件。不是因为设计——是因为 NT 经济一开始只有"转账+消费"，后来一块一块往上加（住宿扣款是 D-26 加的、离线 earn 同步是批①加的、池子调水是批①加的），每次都往同一个文件塞。当 NT 经济逻辑再长到 ~1500 行左右 → 拆 `nt.py` 为 `nt_transfer.py` + `nt_earn.py` + `nt_settlement.py` 的触发条件。

**data.py（513 行）的边界模糊**：名字叫"data"但实际管了 9 件事——journal/activity_log/card_discoveries/verifications/newbie_quests/canteen_menu/meal_orders/map_locations/announcements/inventory + sync_shared + sync_all。这些的共同点是"共享数据"，但这不构成架构意义上的模块边界。如果一个新加入的开发者不知道一个功能该放哪个文件 → 大概率会放 data.py → data.py 继续膨胀。P1 级的整理项（见 §五拆分差距）。

**admin.py（87 行）为什么这么小**：管理员功能只有两件事——提现审批（[server/routes/admin.py:50-87](../server/routes/admin.py#L50-L87)）+ 极少量的用户管理。这是好的——管理员不是超级用户，只是审批员。如果有一天管理员要管公告/管菜单/管地图 → 应该拆出 `admin_canteen.py` + `admin_config.py`，而不是往 admin.py 塞。

**cron.py（128 行）为什么独立于 routes/**：[server/cron.py](../server/cron.py) 不在 routes/ 目录——因为它不是 HTTP 端点，是后台循环。这是有意设计：HTTP 请求处理器和定时任务处理器是不同的生命周期，分开防混淆。cron 的直接调用 `_run_daily_settlement()`（[server/cron.py:123](../server/cron.py#L123)）走的是内部函数调用，不走 HTTP → 不需要 token、不需要鉴权 → 天然避免了"cron 鉴权过期停止工作"的坑。

**chain_scanner.py（192 行）为什么是独立文件**：和 cron 同理——不是 HTTP 端点，是后台协程。而且 chain_scanner 的依赖（web3.py + OP_RPC_URL）是可选的——如果放进 routes/ 里，import 时 web3 没装 → 整个服务起不来。独立文件 + try/except 包在 lifespan 里（[server/main.py:23-31](../server/main.py#L23-L31)）→ 没装 web3 不影响其他功能。

### 2.2 前端模块（nantang-mobile/js/）

模块清单与加载顺序见架构现状图 §2.1（[架构现状图.md:51-87](./架构现状图.md#L51-L87)）。以下写「为什么这样分层」：

**四层加载顺序不是偶然的**：
1. **基础设施层**（utils / mobile-bundle / nt / auth / seed-test-data）先加载 → 后续模块依赖它们的函数和全局变量。没有模块系统（不用 ES module import），加载顺序 = 依赖关系。
2. **数据与引擎层**（nt-core / app-data / api / data）→ 数据结构和 API 适配层要在 UI 之前就位。`AppData` 是全局共享状态，所有 UI 模块都读它。
3. **核心 UI 层**（core.js，1797 行）→ 最大模块，包含所有页面切换、overlay 管理、全局函数定义。它必须在功能模块之前加载，因为功能模块调用它的函数。
4. **功能模块层**（ui-village / ui-camp / ui-wizard / ui-phase4 / ui-social / ui-archive / ui-cardroom）→ 各管一个 overlay 或页面，相互独立。
5. **应用入口**（app.js，2715 行）→ 最后加载，初始化全局状态、挂接路由、启动轮询。

**为什么不用 ES module**：因为不需要打包工具。18 个 JS 文件通过 `<script>` 标签按顺序加载，全局函数直接调用。代价是加载顺序敏感、全局命名空间污染（`CURRENT_USER` / `TASKS` / `_inboxReadIds` 全在 index.html 的 `<script>` 块里定义）、改一个函数名要 grep 全仓库确认没有其他文件调用。收益是零 build 步骤、改了 JS 刷新浏览器立即看到效果。在日活 < 50 的规模下，这个代价是可接受的。触发重构条件：模块数超过 25 个，或出现「两个模块定义了同名函数互相踩」的 bug。

**app.js（2715 行）的膨胀问题**：2715 行包含了页面路由 + 所有 overlay 的初始化 + 业务逻辑黏合代码。它是架构现状图 §三 P0 级拆分差距（[架构现状图.md:141](./架构现状图.md#L141)）。不是"应该拆"——是"现在拆比再塞 500 行进去再拆便宜"。但拆分本身的回归风险很高（app.js 被所有页面引用，拆坏一个引用 = 白屏），所以触发条件是「有 2 天以上的连续开发窗口 + 拆前先写 app 级冒烟测试」。

### 2.3 跨端契约（API 面）

**API 面定义在哪**：
- 服务端：每个路由文件的 `@router.post/get` 装饰器 + pydantic model（如 [server/routes/nt.py:20-29](../server/routes/nt.py#L20-L29) 的 `TransferRequest`）
- 前端：`api.js` 是对 API 的封装（[nantang-mobile/js/api.js](../nantang-mobile/js/api.js)），但不是契约定义——契约在服务端，前端适配服务端

**谁有权改契约**：
- 普通字段增删（加一个可选字段、删一个前端已不用的字段）→ 施工卡正常流程
- 「改触发源/调用方/幂等键」= 宪法级改动（[宪法汇编 §二.2](../方案/宪法汇编.md)），必须走铁律 9（丞相拟票→两营对抗→砚仁批）

**跨端命名纪律**（宪法汇编 §二.3）：前端和服务端对同一个东西的名字必须一致。`presence` 不能在前端叫 `presence` 在服务端叫 `user_status`。改一端必 grep 全仓库查另一端——DB-1 打回教训：以为只改了一个文件，实际另一个文件还在用旧名字。

**前→后调用对应表**：见架构现状图 §2.3（[架构现状图.md:111-119](./架构现状图.md#L111-L119)）。注意 `app.js` 是万能调用者——任务大厅调 `tasks.py`、我的页调 `admin.py`、地图调 `data.py`。这不是设计缺陷，是"入口文件"的职责：黏合各模块。但当一个功能从 app.js 迁移到独立 ui-*.js 时，API 调用也要跟着迁移——这部分目前没有强制执行，是 P1 整理项。

## 三、数据流主干

### 3.1 NT 资金闭环

**全流程**：见数据模型 §三（[数据模型.md:121-296](./数据模型.md#L121-L296)），已完整绘制了 NT 从发行到消费到回收的每条路径及代码行号。本文不重复画。

**这里写「为什么这样设计」**：

**为什么 nt_ledger 是唯一真源**：[数据模型.md §3.1](./数据模型.md) 讲清楚了——`nt_ledger` 是 append-only 银行流水单，`users.nt_balance` 是钱包余额（从流水单算出来的衍生值）。如果对不上，以流水单重算为准——因为流水单不可逆，余额可被 bug 直接改坏。验证端点 `/api/nt/verify`（[server/routes/nt.py:381-412](../server/routes/nt.py#L381-L412)）做的就是：把所有用户余额 + 所有池子余额加起来，和 `total_issued`（总发行量）对比。这是经济系统的安全带——差超过 1 NT 就亮红灯。

**为什么两个池子（community_pool.balance + camp_balance）在一行里**：[数据模型.md §3.2](./数据模型.md) 解释——`community_pool` 表只有一行，两个池子是同一行的两列。这是 ponytail 决策：与其建两张表（community_pool + camp_pool）加外键约束，不如单行多列——因为查询永远只读这一行，锁住一行等于锁住所有池子，避免跨行死锁。代价：加一个新池子要 ALTER TABLE 加列（而不是 INSERT 一行），已发生过 3 次（reserve、frozen、camp_balance 都是后来加的）→ [server/database.py:60-76](../server/database.py#L60-L76) 可见每次加列的迁移代码。

**为什么住宿欠费不在 NT 流通圈内**：[数据模型.md §3.4](./数据模型.md) —— `tenancies.debt` 是一条独立的债务记录，不参与 NT 总账核验。设计理由是：住宿欠费是"用户欠社区的钱"，不是"社区欠用户 NT"。如果用 NT 记账 → 欠费要在账本里记一笔负的 → 总账核验要多处理一种边界情况。当前方案：欠费只是 tenancies 表的一个数字，退房时有余额就扣，没余额就清 debt + 记日志 → NT 蒸发。这在下个版本该改——但不是本卡的活（见 §四·历史包袱）。

### 3.2 presence / 共享数据同步链路

**数据走向**：

```
客户端 A 翻牌
  → AppData.flipPresence()   [app-data.js:509-525]
  → POST /api/data/sync_shared { presence: { "砚仁": { status:"onsite", ... } } }
  → 服务端 MapLocation 按 key="presence:砚仁" 存 JSON  [data.py:404-415]
  → updatedAt 防回写: 只有更新的数据才覆盖

客户端 B 登录/轮询
  → GET /api/data/sync_all   [data.py:433-]
  → 服务端返回全量数据（含 presence MapLocation）
  → _mergeSyncData() 合并到本地 AppData  [core.js:916-]
  → UI 刷新: 「砚仁 🟢 在地」
```

**为什么用 MapLocation 存 presence 而不是单独建表**：[server/routes/data.py:404-415](../server/routes/data.py#L404-L415) —— presence 数据和地图数据、公约配置一样，都是"key → JSON blob"。MapLocation 表（[server/models.py](../server/models.py)，key + data TEXT 两列）是一个通用 KV 存储，省了为 presence 单建一张表。代价：① presence 的 JSON 结构没有 schema 约束——如果前端写了一个 typo 字段，服务端照样存；② 查"所有在线用户"要扫全表找出所有 `key LIKE 'presence:%'` 的行然后 `json.loads` → O(n) 性能，人多了会慢。**触发重议条件**：同时在线 > 50 人。

### 3.3 离线 earn 队列 → 服务端合并

**链路**：

```
客户端离线期间
  → NT.earn() 写入本地 localStorage 队列  [nt.js]
  → 网络恢复后
  → POST /api/nt/earn-sync { items: [...] }  [nt.py:939-978]
  → 服务端日上限检查 (EARN_SYNC_DAILY_LIMIT, 默认 5)
  → 逐条: pool.balance -= amount, user.nt_balance += amount
  → 写 ledger (type="earn", reason="离线同步: ...")
```

**为什么有日上限（5 条/天）**：[server/routes/nt.py:944](../server/routes/nt.py#L944) —— 客户端 localStorage 可以被用户手动改。如果不上限，用户可以伪造 100 条 earn 记录一次性同步进来 → 凭空刷 NT。日上限 5 条 + 单条金额上限（`EARN_SYNC_MAX_BATCH`，默认 50）→ 攻击面控制在 5×50 = 250 NT/天。这不是完美的防刷方案（完美方案是 earn 必须走 peer 校核），但它是"够用 + 不挡正常使用"的平衡。

**为什么不在离线队列里记录"谁校核的"**：因为离线期间没有网络，peer 校核不可能完成。当前离线 earn 信任客户端声称的 earn 金额——这是有意留下的信任口子，对应功能清单 F11「离线 earn 同步」的设计意图（[功能清单.md](./功能清单.md)）：先让在地劳动不因网络断而丢失，再逐步收紧校验。

## 四、有意设计 vs 历史包袱

> 如实标注——不美化历史，不提前重构。每条标：设计 / 包袱 / 期权。
> 实证锚点 = 可在代码中 grep 出的具体行。

### 4.1 有意设计（v11 设计落地）

| # | 设计决定 | 为什么这样 | 实证 |
|---|---------|----------|------|
| D1 | 前端不用框架，原生 JS 18 模块 | 零 build 步骤，砚仁能直接改文案。见 [技术栈文档 §3.1](./技术栈文档.md) | index.html 加载 18 个 `<script>` [index.html:513-530](../nantang-mobile/index.html#L513-L530) |
| D2 | SQLite 本地 + Neon PG 线上，同一套代码 | 开发不装 PG，上线不换代码。见 [技术栈文档 §2.2](./技术栈文档.md) | [database.py:8-19](../server/database.py#L8-L19) URL 自动转换 |
| D3 | cron 用 asyncio.sleep 不用 APScheduler | 少一个依赖。Render 容器没 cron daemon，asyncio 是最简方案。见 [技术栈文档 §4.5](./技术栈文档.md) | [cron.py:45-48](../server/cron.py#L45-L48) `while True: await _wait_until(0,5)` |

### 4.3 为什么"现在不修"

**H1（presence 混维）**：修它 = 改前端 presence 数据结构 + 改后端 sync_shared 存储格式 + 迁移已有 presence 数据 + 更新所有读 presence 的 UI 组件。影响面跨 5 个文件，回归风险高。已有 D-27 卡挂在批③。

**H2（FK 补齐）**：加 FK 约束 ≠ 只改 models.py。加了 FK → 删除用户时的行为要定义（CASCADE? SET NULL? 拒绝删除?）→ 所有涉及用户删除/软删除的端点要改 → NT 总账核验要能处理 FK 级联导致的余额漂移。这是一张中卡，不能当小修小补做。

**H3（cashout 残留）**：代码没坏——因为前端已经没入口调它了。但如果留着，安全扫描会发现"有个不需要审批就能销毁 NT 的端点" → 必须解释 → 浪费注意力。D-21 墓碑清理统一收割。

### 5.3 不做的事（YAGNI）

- **微服务拆分**：日活 < 50，单体 FastAPI 在 512MB Render 上绰绰有余。拆微服务 = 过度工程。
- **CSS-in-JS / Tailwind**：单文件 552 行 CSS 够用。引入 Tailwind → 要装 PostCSS → 要 build 步骤 → 违背"改完刷新即看"的原则。
- **TypeScript 迁移**：18 个 JS 模块全改成 TS → 要 tsconfig + build + 类型定义。当前 JS 的类型错误靠运行时发现，成本可接受。触发条件是"出现一个因为类型错误导致的生产事故且 bug 存活超过 1 天"。

## 六、已知限制

> 每条 = 限制是什么 + 为什么无法避免 + 应对口径 + 升级触发条件。

### 6.1 Render 冷启动

- **限制**：Render 免费层 15 分钟无请求 → 自动休眠。下一个请求要等 3-10 秒容器冷启动。
- **为什么无法避免**：免费层的代价。$7/月升级 Always-On 可解。
- **应对**：① 前端显示"正在连接…"（[index.html:1269](../nantang-mobile/index.html#L1269) `loadingEl.textContent = '正在恢复会话…'`），不等 5 秒超时不弹错误；② JWT 无状态认证 → 休眠后登录态不丢（Session 会丢）。
- **升级触发**：日活超过 20 人时，每 15 分钟一次的冷启动 = 每小时有 4 个人看到"正在连接…"超过 3 秒 → 升 Always-On。

### 6.2 Neon 免费层 100 CU-小时/月

- **限制**：Neon 免费层每月 100 计算单元-小时。超过 → 数据库限速或暂停。
- **为什么无法避免**：免费层的代价。付费层 $19/月起。
- **应对**：① SQLAlchemy 连接池复用（[database.py:21-22](../server/database.py#L21-L22) `async_sessionmaker`）；② 不跑复杂聚合查询（所有查询都是单表 + 简单 join）；③ 定时任务只有 cron 一个，每天只跑一次。
- **升级触发**：Neon Dashboard 显示月 CU 用量超过 80 → 评估升付费层或加 Redis 缓存减少 DB 查询。

### 6.3 SQLite 行锁静默失效

- **限制**：SQLite 不支持 `SELECT ... FOR UPDATE`。但 SQLAlchemy 在 SQLite 下调用 `.with_for_update()` 不会报错——只是锁没生效。本地测试全绿 ≠ 线上 PG 真的锁住了。
- **为什么无法避免**：SQLite 的设计限制——它是文件级锁，不是行级锁。用 SQLite 做本地开发必然有这个差异。
- **应对**：① 编码规范 §2.1（[宪法汇编 §二.1](../方案/宪法汇编.md)）：资金/权限写路径必加 `.with_for_update()` + `populate_existing`；② 锁有效性不以 SQLite 测试为凭——PG 集成测试卡 K-2（在途）；③ 本地上线前跑 `grep 'with_for_update' server/routes/*.py` 确认所有资金路径都有锁。
- **升级触发**：K-2 PG 集成测试卡完成后 → 所有资金路径的锁有效性得到 PG 实证 → 此风险降级为"受控"。

### 6.4 PWA 离线未实现

- **限制**：无 Service Worker，无 manifest.json，无离线缓存。断网 = 白屏。
- **为什么尚未实现**：PWA 在 P2 远期规划。当前阶段优先在线功能完整。
- **应对**：① `_offline` 标志处理（[api.js](../nantang-mobile/js/api.js) 网络错误返回 `{ok:false, _offline:true}`，调用方不弹 toast）；② 离线 earn 队列（[nt.py:939-978](../server/routes/nt.py#L939-L978)）——断网期间 earn 存在 localStorage，恢复后同步；③ `index.html` 已加 `<meta name="viewport" viewport-fit=cover>` 和 `<meta name="theme-color">`（[index.html:5,7](../nantang-mobile/index.html#L5)），是 PWA 的前置准备。
- **升级触发**：第一个真实用户反馈"村里信号不好用不了"时。

### 6.5 OP 链 RPC 依赖外部节点

- **限制**：chain_scanner 依赖 `OP_RPC_URL` 环境变量指向的 RPC 节点（[chain_scanner.py:13](../server/chain_scanner.py#L13)）。如果 RPC 节点挂了 → 链上充值监控停止。
- **为什么无法避免**：读链上数据必须经过 RPC 节点。自己跑 OP 全节点在这个规模不现实。
- **应对**：① 没配 RPC URL → 扫描器静默跳过（[main.py:23-31](../server/main.py#L23-L31)），不影响其他功能；② 扫描断点续扫（[chain_scanner.py:33-46](../server/chain_scanner.py#L33-L46) `last_scanned_block.txt`）→ RPC 恢复后从断点继续，不漏块。
- **升级触发**：链上充值成为主要 NT 来源 → 加备用 RPC URL + 自动切换。

### 6.6 前端全局命名空间污染

- **限制**：18 个 JS 文件 + index.html 内联脚本共享同一个全局 scope。`CURRENT_USER`、`TASKS`、`_inboxReadIds`、`_campCurrentId` 等全是 `var` 声明挂在 window 上。
- **为什么无法避免**：不用 ES module 的代价。这是有意设计 D1 的 trade-off。
- **应对**：① 变量命名前缀约定：`_` 开头 = 模块内部（如 `_inboxReadIds`），大写 = 全局常量（如 `CURRENT_USER`），小写 = 局部变量；② 新增变量用 `window.xxx` 显式声明，不用裸 `var`；③ 命名冲突时 → 打开浏览器 console → `Object.keys(window).filter(k => k.includes('xxx'))` 查是谁先定义的。
- **升级触发**：出现两个模块定义了同名全局变量且导致 bug。

### 6.7 无自动化 CI/CD

- **限制**：部署靠 Render 的 auto-deploy（push main → 自动拉代码 → pip install → 重启）。没有 CI（持续集成）——没有自动跑测试、没有 lint、没有 deploy_check 自动门禁。
- **为什么尚未实施**：三脚本（deploy_check/security_scan/arch_check）已经覆盖了关键的部署前检查，但都是手动跑。CI 的全自动门槛 = GitHub Actions 配置 + 测试能在 CI 容器里跑（需要 PG 镜像）。
- **应对**：① 丞相 push 前手动跑三脚本（宪法汇编 §四·4.1 安全复核）；② vault_gate 每日自跑 arch_check（[arch_check.py](../nantang-mobile/scripts/arch_check.py)）。
- **升级触发**：团队超过 2 人同时提交代码时。CI 的最简方案：GitHub Actions → 跑 deploy_check（纯 stdlib，不需要装依赖）→ PASS 才允许 merge。
