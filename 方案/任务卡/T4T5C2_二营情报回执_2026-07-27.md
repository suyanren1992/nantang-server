## 疑团①：T4 取消领取 + 撤回管理员不可见

### 1. 涉及文件（路径:行号）
- `nantang-mobile/js/data.js:361-383`（`claimTask` 领取全链路）
- `nantang-mobile/js/data.js:384-389`（`unclaimTask` 打开申请弹层）
- `nantang-mobile/js/data.js:390-396`（`confirmUnclaim` 提交取消申请）
- `nantang-mobile/js/data.js:480-494`（`requestWithdraw` / `confirmWithdraw`）
- `nantang-mobile/js/core.js:503`（「📩 取消认领」按钮入口）
- `server/routes/nt.py:521`（`POST /tasks/{id}/accept` 领取端点）
- `server/routes/nt.py:637`（`POST /tasks/{id}/cancel` 发布者撤单端点）
- `nantang-mobile/js/ui-camp.js:980-985`（`_getPendingReview` 管理待办数据源）

### 2. 归因分类
🔴 现有功能坏——「取消认领 / 申请撤回」是**写空气的死链**：申请字段只写不读，无渲染、无审批、无服务端同步，甚至不落盘。

### 3. 证据链（锚点 → 推论）
**事实 A（领取有正向链路）**：`claimTask`（data.js:361）把 `{name,status:'in_progress'}` 推入 `t.claimants`（:369），`AppData.updateTask` 落盘（:371），HTTP 模式调 `POST /api/nt/tasks/{id}/accept`（data.js:379 → nt.py:521）。领取本身前后端都通。

**事实 B（取消认领是死链）**：点「📩 取消认领」(core.js:503) → `unclaimTask`（data.js:384）只弹确认层 → `confirmUnclaim`（data.js:390-396）**仅执行**：
```
t.unclaimRequest=CURRENT_USER; t.unclaimRequestedAt=today();   // data.js:393
filterQuests(); renderMyTasks(); refreshUserUI();               // data.js:395
```
**它不从 claimants 移除自己、不调 AppData.updateTask、不调任何 API、不调 _saveShared**。

**事实 C（申请字段全库无消费者）**：全量检索 `unclaimRequest` / `withdrawRequest`（含 …RequestedAt/…RequestedBy）——
仅 data.js:393 与 data.js:491 两处**写入**，**再无任何读取/渲染/判断处**（grep 全 js 目录，命中数=写入 2、读取 0）。

**推论 1（领取无法真正取消）**：`confirmUnclaim` 只在内存对象挂了个 `unclaimRequest` 标记就结束，claimant 仍在列表里、任务仍占名额。刷新（重新从服务端 sync）后该内存标记丢失。→ **实测「领取后无法取消领取」＝功能根本没实现，只有一个假 UI**。

**事实 D（管理员待办数据源对不上）**：管理面板「营队任务待审批」块的数据源 `_getPendingReview`（ui-camp.js:982-983）过滤条件是 `t.status==='pending_review'`；而其它撤回/取消申请（`unclaimRequest`/`withdrawRequest`）根本不是任务状态、也无任何列表把它们捞出来。

**推论 2（撤回管理员看不到）**：取消/撤回申请既不改 `status`、又无专门的待办列表渲染它们，管理员端任何区块都不会显示。→ **实测「撤回后管理员『待处理』看不到」＝申请信息进了内存黑洞，无渲染出口**。

### 4. 影响面初判
- 认领后成员被永久绑定，无法自助释放名额；名额被占死。
- 发布者/管理员端完全看不到取消/撤回诉求，流程断环。
- HTTP 模式下服务端 `/accept` 已记录 assignee，前端即便本地删 claimant 也需配套的「取消领取」服务端端点——**目前服务端无 assignee 主动退领端点**（仅 `/accept` 领、`/cancel` 由发布者整单撤，nt.py:521/637）。

### 5. 未明项
- 是否曾有历史版本实现过 `unclaimRequest` 的渲染后被删（git log 未在本次只读范围内追溯）——列为待核。
- 服务端 `/cancel`（nt.py:637）能否被复用为「发布者同意取消领取」的近似路径，需设计阶段定夺，不硬猜。

## 疑团②：T5 村口悬浮待处理 → 待审核点不开 + 撤回/重新提交

### 1. 涉及文件（路径:行号）
- `nantang-mobile/js/data.js:331-360`（`doSubmit` 提交，置 `status='待审核'`）
- `nantang-mobile/js/ui-camp.js:980-985`（`_getPendingReview` 过滤 `pending_review`）
- `nantang-mobile/js/ui-camp.js:843-867`（管理面板区块1「待审批」渲染）
- `nantang-mobile/js/ui-social.js:205-243`（营地信箱「待处理」聚合，含 `_getPendingReview`）
- `nantang-mobile/js/core.js:494`（`isReviewer` 定义）
- `nantang-mobile/js/core.js:508-510`（待审核卡片仅 reviewer 出审核按钮）
- `nantang-mobile/js/core.js:424`（my 上下文 showReviewBtn 同样限 reviewer）
- `nantang-mobile/js/data.js:511-515`（退回修改→重新提交路径）

### 2. 归因分类
🔴+🟡 混合——(a) 营地待办**状态词对不上**导致列表恒空/审核不了；(b) 移动端待审核**审核权限锁死在 reviewer 单人**；(c) 撤回提交无机制、重新提交仅退回态才有。

### 3. 证据链（锚点 → 推论）
**事实 A（提交产出的状态是中文『待审核』）**：`doSubmit`（data.js:345）置 `t.status='待审核'`，claimant `c.status='submitted'`（data.js:343）。

**事实 B（营地待办查的是英文 pending_review）**：`_getPendingReview`（ui-camp.js:982-983）：
```
return tasks.filter(t => t.status==='pending_review' && t.reviewer===CURRENT_USER)
```
查 `'pending_review'` —— 与实际写入的 `'待审核'` **永不相等**。

**推论 1（待审批块恒空／点开无内容）**：区块1「营队任务待审批」（ui-camp.js:844-847）数据来自 `_getPendingReview`，恒返回空 → 显示「暂无待审批任务」（ui-camp.js:865）。→ **实测「待审核点不开／审核不了」的一个断点：状态词 `pending_review` vs `待审核` 不一致**（营地任务侧）。营地信箱「待处理」计数（ui-social.js:208-215）也依赖同一函数，此源同样恒 0，混入的 `2` 更可能来自 `_getPendingSubmissions`（claimants 里 `status==='submitted'`，ui-camp.js:987-1000）。

**事实 C（移动端审核权限锁死 reviewer）**：待审核卡片按钮（core.js:508-510）：
```
if(isReviewer) btns='…✓通过…✕打回…';
else if(isMyClaim) btns='🔍 等待审核';   // 无 else 分支
```
`isReviewer=t.reviewer===CURRENT_USER || (!t.reviewer && t.publisher===CURRENT_USER)`（core.js:494）。

**推论 2（指定他人为审核人后谁都点不动）**：当任务**指定了 reviewer 且非当前用户**时，发布者本人、普通管理员打开该「待审核」卡都落到无 `else` 的空分支 → 卡片展开但**无任何审核按钮**。→ **实测「待审核点不开」的第二个断点：审核动作只认 reviewer 一人，无管理员兜底**。

**事实 D（撤回提交无机制；重新提交仅退回态）**：检索提交后「撤回提交」——无任何函数/入口（claimant 提交后卡片只显示 `🔍 等待审核`，core.js:510，无撤回按钮）。「重新提交」仅在 `status==='退回修改'` 且 `isMyClaim` 时出现（core.js:511-515 / data.js:427 置退回态）。

**推论 3**：成员提交后无法自行撤回重来；只有被审核人打回（confirmReject，data.js:415-428）后才能「重新提交」。→ **实测「缺撤回提交/重新提交」＝撤回提交确实无机制，重新提交依赖被动打回**。

### 4. 影响面初判
- 营地任务提交后进「待审批/待审核」区块因状态词错配而不显示，管理员无法处理营队任务审核。
- 个人/社区任务指定审核人后，除该审核人外无人（含发布者、admin）能审，卡死。
- 成员误提交无法自撤，只能等打回，体验与后台流双双受阻。

### 5. 未明项
- 「村口悬浮待处理『2』」的确切宿主组件（营地信箱 badge / my-page urgent chip data.js:300-303 / 社区全貌某处）需真机截图定位，本次只读定位到两个候选计数源，未能唯一化。
- `pending_review` 是否为服务端某处曾用状态（与 TASK_STATUSES 的 `submitted='待审核'` 分叉），需与后端词表并案核，列为待核。

## 疑团③：C2 校核队列——确认第一条后第二条点不开

### 1. 涉及文件（路径:行号）
- `nantang-mobile/js/ui-cardroom.js:502`（校核卡整卡 onclick=`_openVerifyDetail`）
- `nantang-mobile/js/ui-cardroom.js:517-522`（列表卡内 ✅/🙅 按钮）
- `nantang-mobile/js/ui-cardroom.js:464-475`（`_confirmWitness` 作证弹层）
- `nantang-mobile/js/ui-cardroom.js:533-568`（`_openVerifyDetail` 详情弹层）
- `nantang-mobile/js/ui-cardroom.js:1010-1032`（`_showModal` / `closeDiscoveryForm`）
- `nantang-mobile/js/app-data.js:405-434`（`verifyAction` HTTP 异步分支，`return {async:true}`）
- `server/routes/nt.py:837-848`（同对 1 小时冷却，429）
- `server/routes/nt.py:850-860`（日上限 10 次，429）

### 2. 归因分类
❓+🔴 两条独立成因：(a) 遮罩层本身会自清，DOM 残留证据不足（倾向非遮罩残留）；(b) **服务端「同一验证人 1 小时内不能重复校核同一 doer」冷却**是「只能校核一次」的最强嫌疑；(c) 异步重绘时序会造成「点了没反应」的观感。

### 3. 证据链（锚点 → 推论）
**事实 A（遮罩自清，不残留）**：`_showModal`（ui-cardroom.js:1010-1011）开头即
`document.querySelectorAll('.disc-modal-overlay').forEach(s=>s.remove())`——每次开弹层先清同类；作证确认按钮（ui-cardroom.js:471）点击时也先 `modals[i].remove()` 再调 `verifyAction`；`closeDiscoveryForm`（ui-cardroom.js:1029-1032）清 overlay + toast。`showConfirm`（data.js:525-527）同样先清 `.confirm-card`。
**推论 1**：从静态代码看，**没有发现会持续拦截点击的全屏残留遮罩**（各遮罩创建前都自清同类，且 trumpet toast 是 `pointer-events:none`，ui-cardroom.js:12）。→ 「遮罩残留」一说**证据不足，倾向排除**（除非同帧内多路径叠加，属运行时未明）。

**事实 B（verifyAction 是异步且提前返回）**：HTTP 模式（app-data.js:405-434）先 `return {async:true}`，成功回调里才 `renderCardRoom()`/`renderVerifyRoom()`（app-data.js:418-419）重绘网格、`refreshUserUI()` 重拉余额（:420）。确认按钮已在点击瞬间同步移除弹层（ui-cardroom.js:471），但列表要等服务端回包才刷新。
**推论 2（重绘时序造成"点了没反应"）**：网络往返期间，第一条卡仍是 pending 视觉；用户去点第二条时，`_openVerifyDetail` 能开，但紧接着服务端回包触发 `el.innerHTML=_renderVerifyTab()`（ui-cardroom.js:371-374）**整体重建网格 DOM**，正在交互的节点被换掉，表现为「点了一下又被刷没/点不动」。→ 这是**时序观感型**断点，锚点：app-data.js:418-419 的重绘 + ui-cardroom.js:374 的 innerHTML 全量替换。

**事实 C（服务端 1h 同对冷却）**：`approve_verification`（nt.py:837-848）：同一 `verifier` 对同一 `doer` 在 1 小时内已有 `verified_at` 记录 → **429「你在 1 小时内已经验证过 TA 的记录」**。前端 catch（app-data.js:423-432）把 429 转 toast 并**把状态回滚为 pending**（:430），卡片留在原地。
**推论 3（"只能校核一次"的最强解释）**：seed/实测里若队列多条属于**同一 doer**，确认第一条后，第二条 approve 命中 1h 同对冷却被 429 拒，前端回滚 pending → 表现为「第二条点了确认没用、像点不动」。→ 这与议单 C2 原话「只能校核一次」高度吻合，**比纯 DOM 更能解释**。

### 4. 影响面初判
- 若队列同 doer 多条：确认一条后其余同 doer 条目在 1h 内全部无法确认（设计限流的副作用被当成 bug）。
- 异步重绘期间的交互被整表 innerHTML 替换打断，放大「点不动」观感。
- 纯 DOM 遮罩残留：静态证据不足，需运行时 DOM 快照确认。

### 5. 未明项
- 实测「第二条」与「第一条」是否**同一 doer**——决定究竟是 429 冷却（事实C）还是重绘时序（事实B）。需真机复现时看 Network 是否有 429 / Console 是否弹「1 小时内已验证」。
- 是否存在同帧多遮罩叠加的极端 DOM 残留，需运行时 DOM 树验证，只读代码无法证实证伪。

## 太傅注（DeepSeek 教学 · 三行）
- 补课章节：《UI 假动作（写状态不落盘/无消费者）与死链识别》《前后端状态词一致性（enum 对齐）》《乐观更新 vs 异步重绘时序 + 限流 429 的用户可感知性》。
- 人话原理①（T4/T5 死链与错配）：按钮点了像办了事，其实只在内存写了张没人看的便利贴（unclaimRequest），或后台在按错门牌找单子（pending_review≠待审核）——功能没接通，不是坏了是没连上。
- 人话原理②（C2）：多半不是遮罩挡住，而是"同一个人一小时只准给同一个人作证一次"的服务端规矩把第二次挡了（429），前端又把卡片退回原样，看着就像"点不动"；叠加"点完等服务器、列表被整段重画"，手感更糊。
