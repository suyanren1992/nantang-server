## 二、归因分类

**BE-2 遗留半成品**（后端已治一半、前端未跟进）：
- 事实：后端 list_tasks 早已有 limit=50, offset=0（BE-2③，tasks.py:48），过滤后内存切片 	asks[offset:offset+min(limit,200)]（:76），默认只吐 50 条。
- 事实：前端 fetchTasks 旧实现只发一次 GET /api/tasks?mode=hall（api.js:158 原），**不带任何分页参数**，吃后端默认 limit=50。
- 推论：任务累计超 50 条后，第 51+ 条"进行中"任务永久不进大厅列表——即砚仁所述"任务多了旧的看不到"。根因在前端未翻页，非后端无分页能力。

## 三、证据链（锚点→推论）

1. 后端契约=返回 list（test_auth.py:131 isinstance(r.json(), list) 硬依赖）→ 不能改返回体形状，故用**响应头** X-Total-Count 暴露总数，返回体仍为 list（契约零破坏，54 passed 佐证）。
2. 前端 request 底层只回 resp.json() 不给头（api.js:49）→ 前端不硬解析头，改用"**页满即续拉**"策略（tasks.length>=PAGE 则拉下一页），不依赖头解析，离线/失败 .catch 兜底回已累积部分或 null。
3. 造 60 条实测：默认页返回体 len==50、X-Total-Count==60（test_hall_total_count_header_not_capped 通过）→ 头如实反映、不被截断。
4. 造 65 条 offset 翻页拼接：无重复、全覆盖（test_hall_offset_pagination_covers_all 通过）→ 前端循环分页逻辑正确性由测试复刻验证。

太傅注（补课·三行内）：
1. 补课章节：HTTP 分页三式（limit/offset · cursor · X-Total-Count 头）+ CORS expose_headers 机制（自定义响应头默认不暴露给跨域 JS，须显式列白名单）。
2. 人话原理：后端早能"按页发货"，但前端只喊了一嗓子拿走头 50 件就走——本卡让前端"装满一箱就再喊一次"直到货架搬空；总数写在包裹面单（响应头）上，前端不靠它也能靠"这箱没装满=到底了"判断收工。
3. 契约保命：列表返回体形状是老测试的命根子（isinstance list），加总数只能塞进响应头、不能改包装，故 54 条测试零回归。
