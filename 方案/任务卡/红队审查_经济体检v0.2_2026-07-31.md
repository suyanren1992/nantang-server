# 红队审查 · NT 经济闭环体检报告 v0.2

> 红队角色：手册§六·补二对抗审查。只挑漏洞+给证据，不施工。

## 红队判定：**有条件 PASS**

v0.2 比 v0.1 质量跃升一个量级——修复了 P0-2（校核 approve 不写 XP）、P0-3（CV 固定 +5 反向激励），且主动勘察了代码现状（§一表格）。但仍有 **2 个 P0 + 3 个 P1**，不修不能上卡。

## P0 级漏洞（阻塞施工）

### P0-1：checkCvGate 已存在——阈值 500 而非 100

v0.2 §2.3 设计 `proposal_threshold: 100`（L75）。**但前端 `checkCvGate` 函数已在代码中运行，且提案权阈值写死 500。**

**实证**：`nt-core.js:541-550`

```javascript
function checkCvGate(userId, action) {
  var gates = { post_task: 0, buy_work: 0, propose: 500, jury: 500 };
  // jury 走 XP 检查（line 548），其余走 CV
  if (action === 'jury') return { pass: xp >= required, ... };
  return { pass: cv >= required, ... };
}
```

**冲突**：
- v0.2 说 CV ≥ 100 = 提案权
- 代码说 CV ≥ **500** = 提案权
- 5 倍差异，不统一就上卡=赌

**额外发现**：jury（陪审）已用 XP ≥ 500 做门槛——v0.2 完全不知道这个机制已存在。

**影响**：v0.2 §一 体检表（L31）写"提案权：平台无 CV 阈值检查 🔴"——**这是错的**。`checkCvGate` 函数已导出（`nt-core.js:717`），只是**未被 D-15 提案流程调用**（见 P1-1）。

### P0-2：XP 按类别分桶——单一 `experience_value` 整数字段不支持

v0.2 §2.2 设计 XP 按劳动类别分桶 + 同类当周递减 `[10,5,3,1,1,1,1]`（L52）。

**实证**：
- `models.py:29`：`experience_value = Column(Integer, default=0)` — **单一整数**
- `nt-core.js:115`：`experienceValue: 0` — **前端也是单一整数**
- 前端 `earnFromPool`（`nt-core.js:478`）：`u.experienceValue = (u.experienceValue||0) + amount` — **不按类别**

v0.2 §五 实施清单（L160）说"database.py 迁移：新增 xp_by_category JSON 字段"——承认了需要改，但**没给迁移方案**。

**阻塞原因**：
1. 现有测试数据（若有用户）的 `experience_value` 是单一累积值，无法拆分为按类别
2. 递减需要记录"本周该类做了几次"——需要新表或新 JSON 字段存 per-category per-week 计数
3. v0.2 没设计 `xp_by_category` 的数据结构（JSON schema？新表？），实施清单只说"加字段"

**建议数据结构**：
```json
// User.xp_by_category (JSON text field)
{
  "kitchen":  { "total": 120, "week_count": 2 },
  "farming":  { "total": 85,  "week_count": 0 },
  "cleaning": { "total": 40,  "week_count": 1 }
}
```
`week_count` = 本周已做次数（每周一重置），用于查 `decay_schedule[week_count]` 得本次 XP。

## P1 级漏洞（不修会留隐患）

### P1-1：D-15 提案流程不调 checkCvGate——admin 独占提案权

v0.2 §五 说"提案权检查函数 `check_proposal_right(user)`"（L159），但没发现**现有 D-15 提案流程只允许 admin**。

**实证**：
- `app.js:520-521`：`if (_me().role === 'admin')` 才显示"发起修改提案"按钮
- `_openCovenantProposal()`（`app.js:528-553`）：无 CV 检查，直接打开提案表单
- `proposeConfigChange()`（`app-data.js:555-572`）：无 CV 检查
- 服务端 `sync_shared`（`data.py:436-437`）：`if user.role != "admin": raise 403` — **非 admin 写配置变更直接拦**

**v0.2 的设计意图**（CV ≥ 100 即可提案）与**代码现状**（只有 admin 能提案）矛盾。要实现"CV 门槛提案权"，需要：
1. 前端 `_openCovenantProposal` 加 `checkCvGate(user, 'propose')` 检查
2. 服务端 `data.py:436` 的 admin 门控改为 "admin OR CV ≥ threshold"
3. `proposeConfigChange` 的字段范围扩展（当前只能改 `labor_pricing`，v0.2 想改 `cv.*` / `xp.*`）

### P1-2：spendToPool 扣 CV——消费降贡献值，劳动积极性被惩罚

v0.2 §一 体检表（L25）说"nt-core.js:490 spendToPool 扣减 CV 🔴 应删"。

**实证**：`nt-core.js:490` 确实在 `spendToPool` 中：
```javascript
u.contributionValue = Math.max(0, (u.contributionValue||0) - amount);
```

**v0.2 说应删，但没给理由**。红队补充分析：

- 用户做 chef 得 20 NT + CV +10
- 用户用 20 NT 付住宿 → CV -20
- **净效果**：做了活，CV 反而降了 10

这确实应该删。但 v0.2 没注意到**后端 transfer 也有类似逻辑**（`nt.py:258-262`：转账扣 CV + 75% 转移 + 25% 销毁）。后端的 CV 转账逻辑是否也要改？v0.2 完全没提。

**建议**：
- spendToPool（消费）：删 CV 扣减（花钱不降贡献）
- transfer（转账）：保留 CV 扣减（防 CV 买卖——但 75% 转移 + 25% 销毁的逻辑需要重新审视）

### P1-3：等级加成 ×1.2/×1.5 制造同活不同酬——新手不愿来

v0.2 §2.5 设计（L117-121）：
```
chef 20 × 1.0（新手）= 20 NT
chef 20 × 1.2（熟手）= 24 NT
chef 20 × 1.5（老把式）= 30 NT
```

**问题不在挤兑，在池子**：

同一道菜，新手做花社区池 20 NT，老把式做花 30 NT。但**产出是一样的**——一盘菜。

- 从社区池视角：老把式每次多花 4-10 NT，但 XP 递减已让他该类 XP 涨得慢
- 从新手视角：做同样活拿更少钱——但新手 XP 涨得更快（10 vs 递减后的 1）
- **实际效果**：等级加成是对"持续贡献"的奖励，不是挤兑——但**要让用户看到这一点**

**真正风险**：等级加成叠加 CV 公式 `floor(nt/2)`：
- 老把式做 chef：24 NT → CV +12
- 新手做 chef：20 NT → CV +10
- CV 差距会被等级加成放大——老把式更快拿到提案权/勋章

**建议**：等级加成只加 NT（钱包），不加 CV/XP。否则"富者越富"。v0.2 L123 明确说"CV/XP 也按比例加成"——**这条应该删**。

### P1-4：首月 50% 宽限——缺口来源未说明

v0.2 §2.3 新人配置（L88）：`first_month_discount: 0.5`。

B 标间月租 900 × 0.5 = **少收 450 NT/月·新人**。

**谁补？**

| 方案 | 来源 | 影响 |
|---|---|---|
| 社区池出 | pool.balance -= 450 | 加剧 v0 失衡 1（满载 0 结余） |
| 不做减免 | 新人自己挣 | 引导 45 NT + 首月劳动 1050 NT = 净 +195，能 cover |
| 首月住 A 标间 | 600 而非 900 | 差 300 而非 450，且 A 标间本就有 |

**红队建议**：不做减免（丙方案）。理由：
- 新人首月做完引导 45 NT，再做 30 天 × 35 NT = 1050 NT → 净 +195
- 首月经济已自洽，不需要减免
- 减免 → 池子亏 → 满载时更亏

## 非阻塞的设计判断

### Q1：CV 公式 `floor(nt/2)` — **合理，通过**

| 劳动 | NT | CV (floor(nt/2)) | CV/NT 比 |
|---|---|---|---|
| take_trash | 5 | 2 | 0.40 |
| grocery | 5 | 2 | 0.40 |
| sweep_mop | 10 | 5 | 0.50 |
| chef | 20 | 10 | 0.50 |
| clean_kitchen | 15 | 7 | 0.47 |

v0.1 的反向激励（take_trash CV/NT=1.0 > chef 0.25）**已被堵**。现在重劳动的 CV/NT 比 ≥ 轻劳动。

**刷提案权最优策略**：纯做 chef（20 NT + 10 CV/次）→ 10 次达标（CV=100），拿 200 NT。纯做 take_trash（5 NT + 2 CV/次）→ 50 次达标，拿 250 NT。做 chef 更快且总 NT 更少。**激励方向正确。**

### Q2：XP 递减 `[10,5,3,1,1,1,1]` — **方向对，细节待定**

当周同类递减：第 1 次 10 → 第 2 次 5 → 第 3 次 3 → 第 4-7 次各 1。

- **防刷有效**：一周做 7 次 chef 只得 21 XP（不是 70）
- **专精不吃亏**：XP 按类别独立累积，专精厨房不影响田间 XP 从零开始
- **但"周"的边界**：v0.2 说"当周"（L82），是自然周（周一重置）还是 7 天滑动窗口？需明确

### Q3：3 新劳动项定价 10/8/12 — **合理**

| 新项 | v0.2 定价 | 参照 | 判断 |
|---|---|---|---|
| room_prep | 10 | clean_toilet(15)/clean_kitchen(15) | 偏低但合理（入住房打扫 < 深清） |
| room_inspect | 8 | reception(8)/notice_board(5) | 合理（检查清单式） |
| newcomer_reception | 12 | reception(8)/tour_guide(10) | 合理（比参访重，含规则讲解） |

### Q4：等级与勋章功能 — **不冲突，但表述需清晰**

| 机制 | 来源 | 管什么 | 冲突？ |
|---|---|---|---|
| CV 提案权 | CV ≥ 100（代码实际 500） | 治理参与 | 与勋章不冲突 |
| XP 解锁 | XP ≥ 50（某类） | 高单价劳动准入 | 与等级叠加但不冲突 |
| 等级加成 | XP ≥ 100/300（某类） | 单价倍增 | 与解锁叠加 |
| 勋章 | CV ≥ 200/500 | 荣誉 + 优先选房 | 独立 |

四者各管各的维度。但 v0.2 把"解锁高单价"和"等级加成"分两个阈值（XP=50 解锁 / XP=100 熟手）——**应该合并**：XP ≥ 100 同时解锁高单价 + 获得 ×1.2 加成，避免两个阈值之间（50-100）的尴尬区间。
