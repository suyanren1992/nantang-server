Phase 1 · BE 详细（2 营先动 2h）
═══════════════════════════════════════════

  B1. 建表 storage_items
     字段：
       id (UUID, PK)
       user_id (FK users.id)
       item_name (str)
       category (str: 食物/工具/杂物)
       quantity (int, default 1)
       storage_location (str: 冰箱/储物间/共享)
       added_at (datetime)
       expires_at (datetime, nullable)
     索引：(user_id, storage_location)

  B2. POST /api/storage/items
     入参：item_name, category, quantity, storage_location
     权限：认证用户
     返回：新 storage 记录 + 200 OK

  B3. GET /api/storage/items
     权限：认证用户
     返回：当前用户所有 storage 记录（按 storage_location 分组）
     注意：只返回未过期的（expires_at > now 或 null）

  B4. DELETE /api/storage/items/:id
     权限：本人 OR admin
     返回：204 No Content

  B5-B8. 检查现有端点（不改代码只验证）
     - /api/archive/items 是否存在
     - /api/fields 是否存在 + 字段完整
     - /api/users/me/settings 是否存在
     - /api/verifications 是否存在
     输出：API 契约对照表（已存在/缺失/有但字段不对）

  B9. OpenAPI 3.0 简易契约
     输出：方案/契约/openapi_2026-07-31.yaml
     含：所有 B2-B8 端点定义

  **施工规则**：
    - 1 营 1 窗 串行 B1 → B9
    - 走现有 addVerification 校核闭环
    - 不引第三方库
    - 走 server/ 阵地
    - **只 commit 不 push**（等 FE 接完一起推）
    - pytest 新增 B1-B4 测试

紧急召唤机制
═══════════════════════════════════════════

  **触发条件**：
    1. FE 修项 G1 时发现 B2 端点缺字段 → 1 营立刻 call 丞相
    2. FE 修项 F1 时发现 B5 端点不存在 → 1 营立刻 call 丞相
    3. BE 写端点时发现数据模型需扩展 → 2 营立刻 call 丞相
    4. 任何一营发现「卡面描述 vs 实际代码」不符 → 立刻 call 丞相

  **丞相响应（5min 内）**：
    1. 评估：是补接口（派 2 营）还是改卡（改卡面项）
    2. 派单：立刻写补卡 / 改卡
    3. 同步：通知另一营继续推进

  **砚仁响应**：
    - 砚仁随时可「召唤」一营 / 二营 / 丞相
    - 召唤 = 立刻派单 + 砚仁批
