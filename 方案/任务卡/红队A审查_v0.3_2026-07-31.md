## 一、5 个最严重漏洞

### 漏洞 1：「在地」判定 = 用户自报，零防伪——治理权可被任意欺骗

**严重性：★★★★★（治理根基 · 可被 trivially 绕过）**

**行号证据**：

- v0.3 §2.2 L51-53：提案权 = 连续 3 周 + 在地；投票权 = 在地即有
- `app.js:2801-2810`：`_flipMyPresence()` — **用户自己点击即可切换 onsite/cloud/out**
- `app-data.js:524-539`：`flipPresence(userName, status, location)` — 纯客户端上报，`sync_shared` POST 写入

**反例**：

```
攻击场景（成本 = 0）：
1. 用户 A 住在城里，从未到过南塘
2. 用户 A 每天打开 App，点击翻牌 → 🟢在地
3. 3 周后 → 系统认为 A "连续在地 3 周" → 获得提案权
4. 投票日 → A 翻牌 🟢在地 → 获得投票权 → 投完翻回 ☁️云在线

攻击场景 2（替人翻牌）：
- app-data.js L541: flipForOther() — 允许**其他人**替你翻牌
- 虽然代码有 `targetName === flipperName` 守卫（不能翻自己），
  但 A 可以让 B 替 A 翻成 onsite → A 不需要打开 App 也能维持"在地"
```

**核心矛盾**：v0.3 把治理权（提案权 + 投票权）挂在 presence status 上，但 presence 是一个**无校验、无审计、可自报、可代翻**的前端状态字段。这等于把社区治理权建立在一个 `onclick` 事件上。

**最小修订**：
1. **短期**（P0）：`check_proposal_right()` 不读 presence，改读 **住宿记录**（`Tenancy.status == 'active'` 且 `checkin_date ≤ now - 21 days`）—— 住宿费真金白银交了，骗不了
2. **中期**（P1）：presence 翻牌加服务端审计日志（`presence_log` 表：uid, old_status, new_status, ip_hash, timestamp），异常模式告警（如同一用户 7 天内翻牌 > 20 次）
3. **投票权**：读 `Tenancy.status == 'active'`（在住）而非 presence（自报），离开 = 退房 = 投票权消失

### 漏洞 2：「非冻结全部退」与 v3.1 提现限额直接冲突——两套规则并存

**严重性：★★★★★（涉钱 · 契约冲突）**

**行号证据**：

- v0.3 §八 御批 #3 L218：「**非冻结的全部退**（无限额）」
- v3.1 §6.4 L306：提现门槛「50-200 NT，信誉分 ≥ 60，7 天冷却」
- `nt.py:494-508`：**现行代码已实现** 7 天冷却 + trust_score ≥ 60 + reserve 覆盖检查

**冲突矩阵**：

| 规则 | v3.1 §6.4 | v0.3 御批 #3 | 现行代码 nt.py |
|---|---|---|---|
| 单笔限额 | 50-200 NT | 无限额 | 无单笔上限（但有 reserve 检查） |
| 冷却期 | 7 天 | 未提及 | 7 天（L500-508） |
| 信誉分 | ≥ 60 | 未提及 | ≥ 60（L496-497） |
| reserve 检查 | 未提及 | 未提及 | reserve ≥ frozen + amount（L512-513） |

**反例**：

```
用户 A 余额 5000 NT，无冻结
v0.3 御批说"非冻结的全部退(无限额)"
→ A 一次性提现 5000 NT
→ 但 nt.py L512 要求 reserve ≥ frozen + 5000
→ 若 reserve 只有 3000 → 400 拒绝
→ 用户："皇帝说了无限额，你凭什么拒绝？"

矛盾：御批的"无限额"被 reserve 覆盖检查实质限制，
但用户看到的设计文档说"无限额"——期望不匹配
```

**最小修订**：
1. **v0.3 必须显式声明**：御批 #3 "无限额"是指**不设单笔/单日限额**，但**仍受以下约束**：① 7 天冷却期 ② trust_score ≥ 60 ③ reserve 覆盖检查 ④ 多签窗口（每月某天）
2. 或者：v0.3 御批覆盖了 v3.1 的 50-200 NT 限额 → **v3.1 §6.4 必须标注「已被 v0.3 御批覆盖」**，否则两套规则并存，施工时无所适从

### 漏洞 3：「连续 3 周」无追踪机制——数据结构不支持，无法实现

**严重性：★★★★☆（治理核心 · 无法施工）**

**行号证据**：

- v0.3 §2.2 L51：提案权 = 「连续居住 ≥ 3 周 + 在地」
- v0.3 §五 L150：`routes/governance.py:check_proposal_right(user)`
- **真仓现状**：presence 数据只存 `{status, location, updatedAt}`（`app-data.js:527`）——**只存最新状态，不存历史**
- `data.py:419-431`：sync_shared 写入 presence 时是**覆盖式**（`pr.data = json.dumps(pdata)`），不保留历史

**问题**：

"连续 3 周"需要一个**时间序列**数据结构，但当前 presence 只存一个快照。要实现 `check_proposal_right()`，必须新建：

```
方案 A：presence_log 表（新表）
  uid / old_status / new_status / timestamp
  查询：最近 21 天是否连续 onsite（无 cloud/out 间隔 > N 小时）

方案 B：User 表加 checkin_date 字段
  每次翻牌 onsite 且当前非 onsite → checkin_date = now
  翻牌 cloud/out → checkin_date = null
  提案权 = checkin_date is not null AND (now - checkin_date) >= 21 days

方案 C：复用 Tenancy（入住记录）
  提案权 = Tenancy.checkin_date ≤ now - 21 days
```

**更严重的问题——"连续"的定义**：

| 场景 | 连续 3 周？ | v0.3 有无定义 |
|---|---|---|
| 翻牌 onsite 21 天不中断 | ✅ 是 | 未定义 |
| 中间翻 out 1 小时再翻回 onsite | ❓ 中断？ | 未定义 |
| 中间出差 2 天（翻 cloud），回来继续 onsite | ❓ 累计 21 天 but 不连续 | 未定义 |
| 每天翻 onsite 12 小时、翻 cloud 12 小时 | ❓ 算连续吗？ | 未定义 |
| 系统宕机 1 天，用户无法翻牌 | ❓ 被迫中断？ | 未定义 |

**最小修订**：
1. v0.3 必须定义"连续"：**允许的最大中断窗口**（建议：21 天内允许累计 48 小时非 onsite）
2. v0.3 必须指定数据源：**方案 A/B/C 三选一**（建议方案 C 复用 Tenancy，最防伪且无需新建表）
3. 施工清单 §五 补一行：`新增 presence_log 表` 或 `User.checkin_date 字段` 或 `复用 Tenancy`

### 漏洞 4：cron 会计等式硬检查——无失败处理路径，写进 cron 可能炸掉日结

**严重性：★★★★☆（安全网本身不安全）**

**行号证据**：

- v0.3 §五 L146-148：cron 加三项硬检查（total_issued 等式 / reserve ≥ frozen / escrow_drift = 0）
- `cron.py:55-129`：`tick_daily()` 当前只做两件事——生成周期任务 + 每日住宿结算
- `nt.py:528-562`：`verify()` 端点**已有**等式检查，但 **escrow_drift 未实现**（grep 全文件 0 匹配）
- v0.3 §2.4 L78：`escrow_drift = escrow_pool − Σ未领份额 = 0`

**问题一：escrow_drift 从未实现**

v0.3 声称要检查 `escrow_drift = 0`，但现行代码 `/api/nt/verify`（nt.py:528-562）**完全不计算 escrow_drift**。它只计算 `camp_pool_drift`（L541）和 `total_system vs total_issued`（L543-548）。escrow_drift 的公式 `EscrowPool.balance − Σ(reward × (slots − 已到账人数 − 已退回份额))` 需要遍历所有 open/submitted/verified 状态的多人任务——这是一个**全新计算逻辑**，v0.3 把它当成"已有"是错的。

**问题二：硬检查失败怎么办？**

v0.3 说"加硬检查"，但没定义失败行为：

| 失败行为 | 优点 | 风险 |
|---|---|---|
| 告警 + 记录 | 不影响日结 | 问题被忽视（告警疲劳） |
| 停止日结（住宿不扣） | 强阻断 | 住宿漏扣 → 经济等式偏 |
| 停止一切涉钱操作 | 最安全 | 用户体验极差 + 可能停服 |
| 自动修复 | 最智能 | 自动修可能改错 |

**问题三：cron 里加 verify 可能引入新的失败点**

`cron.py:121-128` 显示住宿结算已经用独立 session 隔离事务。如果会计等式硬检查挂在同一 session 里，检查失败回滚 → 住宿结算也回滚 → 用户住宿费漏扣。

**最小修订**：
1. v0.3 补 escrow_drift 实现位置（`nt.py` 新函数 `_calc_escrow_drift()`，遍历 open/verified 多人任务）
2. 硬检查失败行为明确为：**告警 + 记录快照 + 不阻断日结**（日结独立事务，等式检查独立事务）
3. 施工清单补一行：`新增 nt.py:_calc_escrow_drift()`（不是"已有"）

### 漏洞 5：v0.3 砍了 v0.2 红队 B 盲点 #1 的解法——「不衰减/不降级」是有意设计还是遗忘？

**严重性：★★★☆☆（远期风险 · 但需明确表态）**

**行号证据**：

- v0.3 §三 L112：「CV/XP 不衰减(纯历史)，等级不降(纯荣誉)」——这是**对红队 B ★★★★★盲点的回应**
- v0.2 体检报告 §2.4 L107-113：定义了等级系统（新手/熟手/老把式/金锄头/铁锄头）
- v0.3 §三 L115：「等级加成只加 NT(不挂 CV/XP)+ 纯荣誉化」

**问题**：

v0.3 说"CV/XP 不衰减，等级不降"，但同时 v0.3 §三 L115 说等级加成"只加 NT"——这两个决定组合起来产生一个奇怪的结果：

```
老把式(XP≥300)做 chef:
  NT = 20 × 1.5 = 30 NT (等级加成)
  CV = floor(30/2) = 15  ← 等等，v0.3 说加成"不挂 CV/XP"
  
那 CV 按哪个 NT 算？
  甲：CV = floor(基础NT/2) = floor(20/2) = 10  ← 加成不影响 CV
  乙：CV = floor(实际NT/2) = floor(30/2) = 15  ← 加成影响 CV

v0.3 L115 说"加成只加 NT"→ 甲是对的
但 v0.3 §八 御批 #4 L219 说"CV = floor(nt/2)"→ nt 是哪个 nt？基础还是加成后？
```

**这是一个公式歧义**：`floor(nt/2)` 里的 `nt` 是 labor_pricing 基础价还是等级加成后的实际到手价？

如果甲（基础价）：等级加成对 CV/XP 无效 → 老把式做 chef 得 30 NT 但 CV 只 +10 → 用户："我明明拿了 30 NT，为什么 CV 按 20 算？"

如果乙（到手价）：等级加成通过 CV 公式间接影响了 CV → v0.3 L115 "不挂 CV" 是假的 → 老把式 CV 涨更快 → 治理层（虽然 v0.3 说 CV 不挂治理权，但声望效应仍在）

**最小修订**：
1. v0.3 CV 公式显式写明：`CV = floor(labor_pricing_base / 2)`（基于基础价，不含等级加成）
2. 或：`CV = floor(actual_earned_nt / 2)`（基于到手价，含等级加成），同时删掉"加成不挂 CV"的说法
3. **二者必须选一个并写明**，否则施工时程序员会猜

## 二、附加发现（非严重但需注意）

### 发现 A：v3.1 从未定义「等级加成」——整套等级系统是 v0.2 发明的

v3.1 全文 grep「等级」「加成」「熟手」「老把式」「×1.2」「×1.5」只匹配 2 处，都是无关的（"权限等级"语义不同、"1.5 天"工期）。等级系统（新手/熟手/老把式）和等级加成（×1.2/×1.5）**从未出现在 v3.1 经济规则设计稿中**。

v0.2 发明了整套等级系统，v0.3 继承了它（§三 L115 "等级加成只加 NT"）。这意味着等级系统是体检报告层的概念，还没进过正式设计稿。v0.3 如果要落地等级系统，需要先写入 v3.1（或出 v3.2）。

### 发现 B：v0.3 §五施工清单混了前端改动到「BE 后端(二营)」区

L153-154：`app.js:54` 和 `app.js:66-76` 是前端文件，列在「BE 后端(二营)」表格里。施工分工会混乱——二营不该碰 `nantang-mobile/`（AGENTS.md 禁区铁律）。

### 发现 C：多签「杨振」身份验证——代码层面没有 multisig 机制

v0.3 §2.3 说"组长+杨振两人签"，但 `Camp` 模型（`models.py:110-132`）没有 `multisig_address` 字段，`withdraw` 端点（`nt.py:477-525`）是 admin 单人审批。两人签需要**新审批流**（两 admin 各签一次才执行），v0.3 没有设计这个流程。

## 三、红队 A 判断

### 判决：**有条件 PASS**

v0.3 在真仓对齐方面比 v0.2 有质的飞跃——第一次把契约 v0.2、v3.1 设计稿、链上集成和御批四源合一。技术方向是对的。

但 **3 个涉钱/治理级漏洞必须在施工前修掉**：

| # | 漏洞 | 级别 | 必须修吗 |
|---|---|---|---|
| 1 | "在地"判定 = 用户自报 → 治理权可骗 | ★★★★★ | ✅ 不修 = 治理根基不稳 |
| 2 | "无限额"退出与 v3.1 提现限额冲突 | ★★★★★ | ✅ 不修 = 施工无所适从 |
| 3 | "连续 3 周"无数据结构支持 | ★★★★☆ | ✅ 不修 = 无法施工 |
| 4 | cron 硬检查无失败路径 + escrow_drift 未实现 | ★★★★☆ | ✅ 不修 = 安全网本身不安全 |
| 5 | CV 公式歧义（基础价 vs 到手价） | ★★★☆☆ | 🟡 可施工时再定，但建议先拍 |

### PASS 条件

在 v0.3 或 v0.3.1 补丁中：
1. §2.2 治理权数据源改为 `Tenancy`（入住记录），不读 `presence`
2. §2.6 退出机制补注「受限于 v3.1 §6.4 提现约束（7 天冷却 + trust ≥ 60 + reserve 覆盖）」
3. §2.2 提案权定义补充"连续"的精确含义 + 指定数据源（建议复用 Tenancy）
4. §五 施工清单补 `_calc_escrow_drift()` 为新函数 + 硬检查失败行为定义
5. §2.1 CV 公式显式注明 `nt` 是基础价还是加成后价格

五项补完后 PASS。

**太傅注三行**：
- 真仓对齐是 v0.3 最大的进步，但"对齐"不等于"正确"——escrow_drift 声称"已有"实则从未实现，这是对齐过程中的典型陷阱：文档说要有，代码说没有，两边都没撒谎，但事实错了。
- 治理权建立在 presence 翻牌上 = 把投票权交给一个 onclick 事件。所有治理系统的根基必须是**不可伪造的行为证据**（交了住宿费、签了到、做了劳动），而不是**可自报的状态声明**。
- 两套规则并存（v3.1 限额 vs v0.3 无限额）是施工灾难的起点——程序员不知道该听哪个，测试不知道该验哪个，用户不知道该信哪个。

**下一步建议**：五项 PASS 条件补完后可发卡施工。漏洞 1-3 是阻塞级（治理 + 涉钱），建议优先在 v0.3 本体修订；漏洞 4-5 可在施工卡内附带解决。
