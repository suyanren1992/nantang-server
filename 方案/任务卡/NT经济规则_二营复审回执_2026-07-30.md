## Q1【吸收核验】逐条

**① 否决链上 P2P → §2.1 ✅ 正确吸收**
降级远期蓝图、txHash 仅审计「出系统」的钱、不作内部结算信任根，与二营 Q1/Q6 口径完全一致，附录 B 也留痕。无走样。

**② escrow_drift 交叉校验 → §3.5 ⚠️ 吸收但定义待精化**
公式 `escrow_drift = EscrowPool.balance − Σ(未结任务 reward × 剩余 slots)` 方向对，但「剩余 slots」歧义：现行 escrow 在**部分领取/3 次退回/取消**时分段退给发布者（§5.1 五环节），drift 基准须精确定义为「未领取且未退回份额」，否则部分领取态会误报 drift≠0。**建议**：契约里把口径写死为 `Σ(reward × (slots − 已到账人数 − 已退回份额))`，并作为锁测/迁移验收用例。§5.1 双锁 ✅。

**③ 全局锁序 → §3.6 ⚠️ 吸收方向对，但范围严重低估（见 Q2）**
锁序规范本身完整（固定序 + cron 串行 + user_id 升序 + populate_existing + lock_timeout + 锁测）。走样在**定位**：§3.6 把它框为「拆表开工前置」，但现行单表热路径已普遍违反该序，且已存在潜在 AB-BA，不是拆表才有的问题。**建议**：把锁序降为 P0 全局铁律，先在单表阶段统一现有路径方向（详见 Q2）。

**④ 迁移四件套 → §3.7 ✅ 正确吸收**
单事务原子 / 前后对拍 diff≠0 回滚 / camp_balance 禁猜分摊须账本重建 Σ 校验 / 旧表只读快照 14 天——四件套齐全，SQLite DDL 非事务性也用「文件级备份」兜住。无实质走样。

**⑤ 熔断三维 → §8.4 ⚠️ 吸收但数值互撞（见 Q3）**
双维度 + 滚动 24h + admin/收款双计三点都在，但阈值与现行单笔上限打架，且覆盖面有洞（card-confirm/校核奖绕过）。

**⑥ 即时轻检 → §8.1 ✅ 吸收，实现有单表坑（见 Q4）**
「只算本事务涉及增减和=0」的 delta 式设计正确（避免每笔全表扫），但落地须排除 CV/XP，见 Q4。

## Q2【锁序推演】❌ 现行热路径天然逆序，改造成本被低估

**理由**：v3 §3.6 定序为 `Operating→…→User`（**Pool 先、User 后**），但取证显示现行 `transfer / _grant_from_pool / withdraw / cashout` 全部**User 先、Pool 后**，恰是反序；而 `verify_task` 却是 **Pool 先、User 后**。即**今日单表内部就已锁序不一致**：transfer 持 UserX 等 Pool，verify_task 持 Pool 等 UserX，若 UserX 同为收款方/发布者，PG 生产环境**现在就能 AB-BA 死锁**（SQLite 单写掩盖，上 Neon 即暴露）。另 transfer 锁 from→to 不按 id 升序，并发 A→B / B→A 亦可 AB-BA。所以采用 v3 序 = 必须翻转 nt.py 四条核心热路径的加锁顺序，**不止 camps.py/cron.py**——§3.6/§12 把锁序仅列为拆表前置，低估了这部分改造量与现存风险。

**修改建议**：
1. 锁序统一**提到 P0**，先在单表阶段把 transfer/grant/withdraw/cashout 改为「先锁 Pool 后锁 User」，与 verify_task 对齐（或反之，任选一致方向并写死注释）。
2. transfer 多用户按 `user_id 升序`加锁（v3 已有规则，须落到现有代码）。
3. cron 现状单表单行锁天然无 AB-BA；拆表后划拨/调水 §3.6 串行约束正确保留即可。
4. 补一条「单表阶段 transfer×verify_task 交叉」的 PG 锁测（`requires_pg`），证明翻转后无死锁——不要等拆表才测。

## Q3【熔断数值】⚠️ 顶格相等无余量 + 覆盖面有洞

**理由**：
1. **earn 单笔上限 10000 == earn 单收款人 24h 10000**：一笔顶格发放即打满该用户全天额度，第二笔任何金额被拦，二者数值顶死无并发空间；且 earn **全局 24h 20000** 对 50 人只够 2 笔顶格发放/天，admin 正常发奖易误触 429。
2. **覆盖洞（最关键）**：卡片发现（card-confirm）与校核奖都走 `_grant_from_pool` 但**不经 /earn 端点**（§5.4/§5.3）。若熔断挂在 earn 端点，这两条同样从 OperatingPool 出钱的路径**绕过全部熔断**——三维形同虚设。
3. **transfer 上限 10000 未进熔断表**：单笔有限、无日累计/熔断。钱不出系统风险较低（§8.5 有 receive>10 笔/1h 兜底），但覆盖不一致。
4. withdraw 单用户 500 / 全局 2000 与门槛 50-200 协调，合理。

**修改建议**：earn 单收款人 24h 上调至单笔上限的 ≥3 倍（如 30000）留并发余量，全局按运营池日均规模设（50 人建议 ≥40000）；**熔断下沉到 `_grant_from_pool` 层**按「资金出池」统一计数，覆盖 earn+card-confirm+校核奖，而非绑定单端点；transfer 至少纳入异常告警维度。

## Q4【新引入问题】❌ 发现一处等式破裂被 v3 原样固化 + 即时轻检单表坑

**理由**：
1. **（重大）withdraw 申请三向移动破等式**：现行 §6.4 = 代码 455-479：`user −X` + `frozen +X`（此二者对等式净 0）**再叠加 `reserve −X`**（无对冲项）。而 verify() 把 reserve 计入 total_system → **每笔提现申请令 diff = −X**；确认阶段 `frozen −X + total_issued −X` 也不回补 reserve，diff 恒留 −X。**这极可能就是砚仁 07-29 实证「会计等式×4」的一支**。v3 §3.5 等式仍含 reserve、§6.4 仍写「ReservePool 等额扣减」——**把疑似 bug 原样固化**，未裁定 reserve 究竟在 total_issued 之内还是之外。
   **建议**：P0-2 必须先裁 reserve 语义——要么 reserve 移出会计等式（作链上背书池，不计 total_issued），要么申请阶段**只校验 reserve≥X 不扣减**、确认阶段随 total_issued 一起处理。此项不裁清，拆表只会把破裂搬进四表。
2. **单 admin 下双人复核死锁**：§8.4「earn 超限需第二 admin 确认」，小营队/开发环境常仅 1 admin → 合法大额发奖**无法完成**。建议配置化「最少复核人数」，单 admin 环境降级为二次确认弹窗 + 审计留痕。
3. **即时轻检单表坑**：`_grant_from_pool` 同时改 `nt_balance/contribution_value/experience_value`，transfer 改 `contribution_pool`（CV 域）——delta 轻检若把这些计入 NT 和会**误判破裂**；topup/earn 中 total_issued 是**锚点非池项**，须单列处理。且轻检为 delta 式，只拦「本事务新失衡」，**抓不到既有 ×4 存量漂移**（须靠 P0-2 全量追账 + 日终 verify）。
   **建议**：轻检显式限定「仅 NT 字段（各池 balance + Σuser.nt_balance）增减和=0，排除 CV/XP/contribution_pool，total_issued 单独对账」；在已有行锁内计算，禁止全表扫；文档注明轻检≠存量对账。

## 复审结论

**未通过，不予呈砚仁终审。** v3 对第一轮六条意见吸收方向正确（①④✅，②③⑤⑥ 有走样待修），但复审新查出**两处必须拦截项**：

- **❌ Q4-1**：withdraw 申请 `reserve 等额扣减` 与含 reserve 的会计等式冲突，疑为线上「等式×4」根因之一，v3 原样固化——须先裁 reserve 语义再谈拆表。
- **❌ Q2**：现行四条核心热路径锁序与 v3 定序反向、且存量已有 AB-BA 隐患，锁序统一须提到 P0，非拆表前置。

余 ⚠️：Q1-②drift 定义、Q3 熔断数值顶格相等 + card-confirm/校核奖绕过洞、Q4-2 单 admin 复核死锁、Q4-3 轻检字段边界。

**建议回丞相府补 v3.1**：先落 P0-2（reserve 语义裁定 + 等式追账）与锁序 P0 统一，二营即可复审放行。
