# NT 经济规则 v0/v2 对抗审查回执 · 一营（前端营）

> 审查方：一营（前端营）· 砚仁 2026-07-30 令

## 1.【结算模式对抗】✅ 模式 B（内部即时）通过

模拟 60 后村民"帮我搬柴 15 NT"：

**模式 A：链上 P2P（v0 提案）**
- ① 发布任务 [点1次] → 15 NT 标记 frozen，仍在余额里
- ② 等执行者搬完柴，线下确认完成
- ③ 打开个人加密钱包 App [村民需有 MetaMask/TP 钱包]
- ④ 找到执行者 0x 地址，输入、确认转账 [点4-5次：打开→找地址→输入金额→签名→确认gas费]
- ⑤ 回平台录入 txHash [点2次]
- ⑥ 等服务端查链验证 [可能几分钟]
- ⑦ 解冻 → 闭环
- **卡在第③步**：60 后村民大概率没有加密钱包，即使有也不会操作 0x 地址转账。面向 Web3 原生用户设计，与目标用户完全不匹配。

**模式 B：内部即时结算（当前代码实现）**
- ① 发布任务 [点3次] → 15 NT 从余额扣到托管池
- ② 执行者搬完柴 → App 里点"提交"
- ③ 发布者点"审核通过" [点1次] → 15 NT 即时到执行者账上
- **不卡**：全程 App 内完成，不需要任何外部工具。

| 对比 | 模式 A | 模式 B |
|---|---|---|
| 总点击数 | 8-10 次 + 钱包操作 | 4-5 次 |
| 需要加密钱包 | ✅ 必须 | ❌ 不需要 |
| 到账时间 | 几分钟（链确认） | 即时 |
| 60 后可用性 | ❌ | ✅ |

当前代码已实现模式 B（POST /api/nt/tasks/verify → escrow 释放 → 即时到账）。v0 的模式 A 应明确废弃而非"裁后发卡"。

**修改建议**：v0 模式 A 写入终局蓝图（与"虚拟账本+月结"并列），标注"需全员配备钱包后启用"。本期不倒退回链上 P2P。

## 2.【资金可见性】⚠️ 有疑虑 — 缺前端 UI 改造方案

当前工作台（index.html:117-121）三面板（营队 NT / 个人 NT / 冻结），"冻结"一栏把任务托管、提现待审、住宿应付三种状态糊在一起，村民看到"冻结 45 NT"不知是任务锁的还是提现卡的。

**建议：拆"我的资金分布"折叠面板**

```
💰 可用余额        120 NT
🔒 任务托管         30 NT  （3个进行中任务）
⏳ 提现待审         50 NT  （1笔待管理员确认）
🏠 住宿应付        -15 NT  （已住3天，退房时结算）
━━━━━━━━━━━━━━━━━━━━━━━
📊 实际可用        120 NT
```

UI 方案：现有三卡片下方加小字链接「📊 查看资金分布 →」，点击展开明细。不增页面，不破坏现有布局。

v2 的三种冻结正名非常好，但前端没有对应改造方案——纯改名不改 UI，用户仍看不懂；拆 4 表只是后端干净，前端不改展示就是白拆。

**修改建议**：Pool 拆分卡（P0）同步出前端子卡，改造工作台冻结面板为资金分布折叠视图。

## 3.【契约风险】⚠️ 有疑虑 — 缺字段名契约文件

当前 sync 返回结构（nt.py:164-181）：balance/cv/xp/role/frozen_balance/wallet_address/ledger/tasks/deposit_intents/all_tenancies/accommodation/pending_verifications。

v2 拆 4 表后至少以下字段会变：

| 当前字段 | v2 后预期变化 | 波及前端位置 |
|---|---|---|
| frozen_balance（单值） | 可能拆成 escrow_balance + frozen_balance + accommodation_due | core.js:888, core.js:1255-1256 |
| /api/nt/pools 的 community_pool/task_escrow/reserve/frozen | 4 张独立表，JSON key 必然改名 | ui-camp.js:379-384（映射表）, nt.js |
| /api/nt/verify 的 camp_balance/camp_pool_drift | 加 CampLedger 后等式校验字段变化 | 管理后台 |

波及页面：我的工作台（refreshUserUI 读 frozen_balance）/ 账本页 myTabLedger / 营地资金页 / 管理后台 / NT 会计等式校验页。

**字段名契约锁死方案**：前端统一加 NT_CONTRACT 层（api.js 或新建 nt-contract.js）——SYNC_KEYS / POOL_KEYS 必含字段清单 + ALIAS 别名映射（community_pool→operating_pool、task_escrow→escrow_pool），所有读 API 返回值统一走 `ALIAS[oldKey] || oldKey`，非预期 key 报 warning。

参照 discovery_id/disc_id 422 事故教训：**必须在 v2 定稿前补 NT_FIELD_CONTRACT.md（≤30 行）**，列出所有 API 返回 key 名、类型、必/可选、示例值，提交 git，前后端引用同一份。后端改表先改契约文件，前端对着改。

## 4.【最不同意】❌ v2 把「CommunityPool 拆 4 表」排 P0 第一位

（审查过程记录：起初反对 v0"发布者可自校核"，重审后撤回——钱是发布者自己出的（已扣到 escrow），自审=决定"认可成果、把钱给执行者"，逻辑成立。当前代码 data.js:416-425 也未限制，无实际风险。）

**正式反对项**：拆表是后端重构，用户无体感。当前单表 8 列对 50 人完全够用。真正卡用户体验的是：
1. 社区池=0 导致卡片发现确认卡死（v0 Q4）→ 应该 P0
2. 工作台不显示"我的钱去哪了" → 应该 P0
3. 会计等式 ×4 不成立 → 应该 P0

任务托管显示不清/提现待审看不到/等式不成立——都不需要拆表，需要的是 UI 改造和修 bug。

**替代方案**：P0 = ①修社区池=0 联动 bug → ②工作台加资金分布视图 → ③会计等式排查修复；P1 再拆 4 表。先治标（修 bug + UI），再治本（拆表重构）。

## 5.【最认同】✅ v2 §三「三种冻结正名」

旧代码 frozen 一词五种含义（CommunityPool.frozen=提现锁定 / NTTask.escrow_amount=任务托管 / Tenancy.accommodation_due=住宿应付 / nt-core.js frozenDeposit=保证金 / User.frozen_cv=CV 冻结），村民看不懂、开发者也搞混。

| 旧名 | 新名 | 含义 |
|---|---|---|
| task_escrow | 任务托管 | 钱锁在任务里，等审核 |
| frozen | 提现待审 | 提现排队等管理员批 |
| accommodation_due | 住宿应付 | 欠社区房费，退房结 |

直接解决"为什么余额 100 只有 70 能用"。小改动、大收益。

**唯一建议**：命名确定后，前端所有 toast/提示文案同步更新，如余额不足提示加"（当前 10 NT + 任务托管 30 NT）"，让用户知道不是没钱，是钱锁住了。
