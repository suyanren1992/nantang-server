## C-1 人物头像下方蓝条/块异常

### 判：🟡 已定位——四嫌疑人，"蓝条"可能是 NT 进度条宽度为0% + 头像角色边框颜色错

系统中共 8 处使用蓝色色值 `#4a7a82`（`--g-blue`），追踪至四个与"头像下方蓝条/块"相关的嫌疑人：

### 嫌疑人一（P0 置信度最高）：MyPage NT 余额进度条

[core.js:1224-1241](nantang-mobile/js/core.js#L1224) 存在**双路竞争**：

```
路径1（异步）: API.request('/api/nt/balance') → .then() → 设置 bar 宽度
路径2（同步）: NT.getUser() 本地数据 → 设置 bar 宽度
```

API 失败/超时时路径1不触发、路径2本地余额为0 → bar 宽度永远 0%。分母固定 1250（`Math.round(b/1250*100)`），新用户余额远低于 1250 → 显示为极细条/空白条。**这个位置恰好在头像正下方**。

### 嫌疑人二（P1）：头像角色边框硬编码

[index.html:105](nantang-mobile/index.html#L105) 头像 div 硬编码 `class="my-avatar role-builder"`。CSS 定义（[main.css:140](nantang-mobile/css/main.css#L140)）：
- `role-admin` → 金色 `#c88740`
- `role-builder` → 绿色 `#5d8c52`
- `role-adventurer` → **蓝色 `#4a7a82`**

`refreshUserUI()` 从未动态更新此类名——无论用户是什么角色，头像边框永远是绿色。**冒险者用户本应看到的蓝色边框消失了。**

### 嫌疑人三（P2）：任务状态空蓝徽章

[data.js:261](nantang-mobile/js/data.js#L261) 渲染任务状态蓝色徽章 `sb-blue`（`#e0eaee` 底 + `#4a7a82` 字）。任务状态为空或 undefined 时，仍渲染空蓝色矩形块。

### 嫌疑人四（P3）：人物档案完成率进度条

[ui-social.js:320](nantang-mobile/js/ui-social.js#L320) 档案弹窗进度条。`completionRate` 为 NaN/undefined/0 时显示为空白灰条。

### 修法建议

| 优先级 | 文件:行号 | 修改 |
|--------|-----------|------|
| P0 | [core.js:1224](nantang-mobile/js/core.js#L1224) | 统一 bar 更新逻辑，消除双路竞争；分母 1250 改为动态 |
| P1 | core.js `refreshUserUI` | 加一行：`document.querySelector('.my-avatar').className = 'my-avatar role-' + role` |
| P2 | [data.js:261](nantang-mobile/js/data.js#L261) | `if (t.status)` guard 再渲染 sb-blue |
| P3 | [ui-social.js:320](nantang-mobile/js/ui-social.js#L320) | `completionRate` 加 `|| 0` fallback |

## C-2 角色差异化视图

### 判：🔴 已定位——系统只有"全局角色"无"营地内角色"，导致跨营地数据泄漏

### 核心架构缺陷

`ROLE_CAPABILITIES`（[nt.js:22-33](nantang-mobile/js/nt.js#L22)）定义的 `isMember` 是**系统级**概念——一个 adventurer 对所有营地自动是"成员"。没有 `c.members` 字段记录谁属于哪个具体营地。

### 实际行为 vs 期望

| 角色 | 期望 | 实际 |
|------|------|------|
| admin | 全部营地 | ✅ 正确 |
| builder | 已加入的营地 | 🔴 **可进入全部营地** |
| adventurer | 已加入/公开营地 | 🔴 **可进入全部营地** |
| npc | 有限视图 | 🔴 **可进入全部营地（isMember=true配置疑误）** |
| visitor | 公开营地 | 🟡 看到列表但需邀请码（基本正确） |

### 五处具体泄漏

| Bug | 文件:行号 | 描述 |
|-----|-----------|------|
| 营地列表零过滤 | [data.js:679](nantang-mobile/js/data.js#L679) | `getCamps()` 无任何角色过滤，全员同列表 |
| 门禁过宽 | [ui-village.js:6](nantang-mobile/js/ui-village.js#L6) | `isMemberByRole()` 对 4/5 角色放行，不查营地归属 |
| 跨营地成员泄漏 | [ui-camp.js:556](nantang-mobile/js/ui-camp.js#L556) | 成员列表拉全局所有 adventurer，非营地限定 |
| 归档报告零门禁 | [ui-village.js:44](nantang-mobile/js/ui-village.js#L44) | 任何人可看归档营地完整财务/排行/贡献 |
| NPC 成员身份 | [nt.js:29](nantang-mobile/js/nt.js#L29) | NPC `isMember:true`→可进任意营地内部 |

### 修法建议

1. **`getCamps()`** 加 `filterByRole` 参数，根据用户角色和营地 membership 过滤
2. **`enterCamp()`** 增加营地级 membership 检查，非 `c.builders`/`c.members` 不允许直接进入
3. **`renderCampMembers()`** 只取 `c.builders` 中的人，不从全局 `users` 按 role 拉取
4. **`showCampWindow()`** 归档报告加角色门禁
5. NPC 的 `isMember` 改为 `false`（如果 NPC 不应自由进入营地）

### 爆炸半径

🔴 高。涉及 5 个文件的数据隔离逻辑，改任一处都需回归全部营地视图。

## C-4 点餐订餐

### 判：🔴 已定位——会话内正常、刷新即丢，典型的"半成品陷阱"

### 完整链路追踪

| 步骤 | 位置 | 状态 |
|------|------|:--:|
| 入口（仅 adventurer） | ui-camp.js:26-28 | ✅ |
| 打开 UI | ui-phase4.js:113-118 | ✅ |
| 渲染菜单 | ui-phase4.js:144-199 | ✅ |
| 点餐确认 | ui-phase4.js:38 | ✅ |
| NT 余额检查 | ui-phase4.js:41-44 | ✅ |
| NT 扣费 | ui-phase4.js:43 | ✅ |
| 写订单到内存 | ui-phase4.js:50-51 | ✅ |
| **持久化到 localStorage** | app-data.js:232 | 🔴 **断链** |
| 显示结果 toast | ui-phase4.js:57-58 | ✅ |

### 根因

**`mealOrders` 不在 `_saveShared()` 序列化列表中。** [app-data.js:232](nantang-mobile/js/app-data.js#L232) 显式枚举了 20 个字段，漏了 `mealOrders`。同时 `init()` 中也没有初始化 `mealOrders`。

**触发链路**：
```
点餐→NT扣费(NT系统独立持久化)→写入AppData._data.mealOrders
→_saveShared()序列化(漏了mealOrders)→刷新页面→订单丢失
→NT已扣但订单不在→用户"付了钱没饭吃"
```

### 为什么标了✅

开发者测试路径（打开UI→点餐→确认→toast成功→UI显示"已预定"）一切正常。只有**跨会话**（刷新/重开）才暴露数据丢失。这是典型的"单元测试过、集成测试漏"。

### 修法建议（三行修复）

1. [app-data.js](nantang-mobile/js/app-data.js#L14) `init()` 加：`if (!this._data.mealOrders) this._data.mealOrders = {};`
2. [app-data.js:232](nantang-mobile/js/app-data.js#L232) `_saveShared` data 对象加：`mealOrders: this._data.mealOrders`
3. [app-data.js:237](nantang-mobile/js/app-data.js#L237) 服务端 sync payload 加：`mealOrders: this._data.mealOrders`

### 爆炸半径

🟢 低。纯数据持久化补漏，不改业务逻辑。但需注意：NT 已扣但订单丢失的存量用户会看到"无记录"——修完后历史订单不可恢复。
