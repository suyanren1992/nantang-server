## 返修清单（D1-D5）

### 🔴 D1（BLOCKER）status 端点无 `ok` 字段 → 签署状态判定恒走本地 mock
- **事实**：服务端 `GET /status` 响应键无 `ok`（真跑已证）；前端 `_fetchCovenantStatus`（app.js:636-640）`if (r && r.ok)` 恒 false → `_checkLocalCovenant`（app.js:643-647）读本地 `_covenantSignatures`。
- **后果**：签署状态**从不采信服务端**。判据5（换设备重登服务端权威）**失败**——他设备已签、本机本地空 → 误判未签、错误拦截；未签拦截/已签判定全靠本地。这正是卡面点名的「mock 在真端点下未被真实调用覆盖」。
- **返修**：前端改判 `if (r && typeof r.signed !== 'undefined')`（或后端 status 补 `ok:true`——但改后端属 G-1 范围，建议前端适配）；登录态成功拿到 server status 后**禁用**本地回退。

### 🔴 D2（BLOCKER）sign 响应字段 `nt_earned` 不存在 → 钱动提醒恒不触发
- **事实**：服务端 `POST /sign` 返 `reward`/`reward_granted`/`balance`，**无 `nt_earned`**（真跑已证）；前端 app.js:613 读 `r.nt_earned`。
- **后果**：判据1「+10 NT 到账提醒」🔴钱动提醒**永不出声**（卡面明列必出）。另 app.js:614 `signedAt:r.signed_at`——sign 响应也无 signed_at（仅 status 有），回退 _todayStr 可接受但非权威。
- **返修**：前端改读 `if (r.reward_granted && r.reward) showToast('+'+r.reward+' NT 已到账','warn')`。

### 🟡 D3（中）covenant_text 前端未对接 G-1 `GET /api/covenant/text` → 双份文本可漂移
- **事实**：`_covenantText()`（app.js:161）= `_mlConfig().covenant_text || _defaultConfig().covenant_text`；api.js 仅有 covenantStatus/covenantSign（api.js:132-133），**无 covenantText**。G-1 权威文本存 MapLocation key=`covenant_text`（独立行），前端从不读取。
- **后果**：签署条款/正文实际渲染源 = 前端硬编码 `_defaultConfig`（app.js:83-96，因 `_mlConfig.covenant_text` 空）。判据3「改 config 页面跟着变」只在有人往 _mlConfig 灌 covenant_text 时成立，**与 G-1 权威 store 不同源**，两份可漂移。违「文本一律从 config 渲染、禁硬编码」的同源精神。
- **返修**：api.js 加 `covenantText: GET /api/covenant/text`；`_covenantText()` 首选服务端返回（缓存），_defaultConfig 仅兜底。

### 🟡 D4（中）预定入口未加未签拦截
- **事实**：卡面明列「入住/**预定**前查 status」；`_isCovenantSigned` 仅 checkin 处调用一次（app.js:1770），无预定拦截。
- **判断**：预定功能属《对照清单》F3（未上线）。若平台尚无预定入口则无法拦截——**属挂账候选**，请丞相/砚仁确认 F3 上线时补拦截；本卡不作硬性 BLOCKER。

### 🟢 D5（低·连修建议）离线 mock 分支可伪造签署
- **事实**：`_doSignCovenant` isOffline 分支（app.js:621-631）本地标记已签+toast「+10 NT」。登录态（API.token 存在）不走此分支，但因 D1 本地回退，离线伪造的签署会在在线态被 `_checkLocalCovenant` 采信 → 骗过后续拦截。
- **返修**：D1 修好后，登录态一律以服务端 status 为准，忽略本地签署标记（本地仅纯离线演示用）。

## 太傅注（三行）
- **补课章节**：前后端契约字段对齐（响应键即契约）/ 服务端权威 vs 本地缓存回退的优先级。
- **人话原理一**：前端问服务端「签了没」，却按一个服务端根本不发的 `ok` 字段判断——等于没听见回答，转头查自己的小本本（本地缓存）。换个手机小本本是空的，就误判「没签」。
- **人话原理二**：发钱提醒读 `nt_earned`，服务端发的是 `reward`——名字对不上，钱到账了却不吭声。字段名是前后端的暗号，暗号错一个字，整条链就哑火。
