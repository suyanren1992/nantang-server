## 洞 #1 🔴 CRITICAL — Tenancy.checkin_date 换房时重置，"换房不中断"与数据模型矛盾

**v0.3.1 位置**：§九 #3 "换房不中断、tenancy 关闭才中断" + "用 Tenancy.checkin_date 起算"

**代码实锤**：

```python
# accommodation.py:121-152 — 换房逻辑
old.status = "checked_out"                    # L123: 旧 Tenancy 关闭
t = Tenancy(user_id=user.id, room_id=req.room_id,
            checkin_date=now, status="active") # L151-152: 新 Tenancy，checkin_date = NOW
```

换房 = 旧 Tenancy 关闭 + 新 Tenancy 创建，`checkin_date` 取 `now`（当前时间戳）。如果治理代码读的是 `Tenancy.checkin_date`：

```
用户 A：
  Day 1   入住 Room 101 → Tenancy#1.checkin_date = Day 1
  Day 14  换房到 Room 203 → Tenancy#1.checked_out, Tenancy#2.checkin_date = Day 14
  Day 21  系统检查提案权 → 读 Tenancy#2.checkin_date = Day 14 → 仅 7 天 ❌ 拒
```

用户实际连续住了 21 天，但因第 14 天换了一次房，提案权时钟被重置为 7 天。**"换房不中断"是一句无法用当前数据模型实现的承诺。**

**要真正实现"换房不中断"，治理代码必须**：

1. 查用户所有 Tenancy 记录（含 `checked_out`）
2. 按 `checkin_date` 排序，找最早的**连续链**（checkout_date_A 与 checkin_date_B 间隔 ≤ 允许中断窗口）
3. 用链首 Tenancy 的 `checkin_date` 起算 3 周
4. 如果链中有 gap > 允许中断窗口 → 从 gap 后的第一条重新起算

当前 `routes/governance.py` 不存在，这整套逻辑也不存在于任何已实现文件中。

**修订建议**：
- **方案 A（推荐）**：`User` 表加 `first_checkin_date` 字段，入住时 SET（若已有值不覆盖），退房（所有 Tenancy 关闭）时 SET NULL。治理代码读 `User.first_checkin_date`，一行查询，无跨表链逻辑
- **方案 B**：在 `routes/governance.py` 实现上述跨 Tenancy 链逻辑（查询 + 排序 + 连续判断）
- **方案 C**：承认"换房中断"不可避免，退回 v0.3 原规则，标注"已知限制，换房需重新累计 3 周"

方案 A 改动最小（新增 1 字段 + 1 行入住逻辑），且与 v0.3.1 设计意图完全一致。

## 洞 #2 🔴 CRITICAL — trust_score 只提现才扣 + 劳动就涨，≥60 门槛形同虚设

**v0.3.1 位置**：§九 #2 "沿用 v3.1 §6.4（7 天冷却 + trust≥60 + reserve 覆盖）"

**代码实锤**：

```python
# nt.py:522  — 唯一扣分路径
await _adjust_trust(user, -10)   # 提现时 trust -10

# nt.py:692  — 涨分路径（任务结算）
await _adjust_trust(user, 2)     # 单人任务完成 +2

# nt.py:735  — 涨分路径（多人任务）
await _adjust_trust(a, 5)        # 每个执行者 +5

# nt.py:744  — 涨分路径（发布者）
await _adjust_trust(poster, 3)   # 发布者 +3

# admin.py:182 — 管理员重置
u.trust_score = 100              # 一键回满
```

**净效果计算**：

```
用户典型 1 个月：
  做任务 20 次（单人+多人混合）→ trust +40~+60
  提现 1 次                       → trust -10
  月末 trust = 100（溢出截断）

用户极端刷提现：
  做任务 10 次 → trust +20~+30
  提现 4 次   → trust -40
  trust = 100 + 30 - 40 = 90（仍 ≥ 60）
  
  需连续提现 5 次且中间不做任何任务，trust 才可能跌破 60
  但 7 天冷却期限制下，5 次提现 = 至少 35 天——期间不可能不做任务
```

**结论**：在 7 天冷却 + 正常劳动频率下，trust_score **永远不可能跌破 60**。≥60 门槛对活跃用户是纯摆设。

trust_score 的实际动态范围是 [90, 100]，不是 [0, 100]。`trust_level` 的四个档位（可信/待观察/受限/冻结）中，后三档永远不会被触发。

**修订建议**：
- **方案 A**：加 trust_score 自然衰减——每周无劳动 -5，劳动可抵消（类似驾照分制度）
- **方案 B**：trust_score 改挂钩具体违规行为（退房欠费不还、任务虚假申报被驳回），而非仅提现
- **方案 C（最小改动）**：承认 trust≥60 门槛在现行行为模型下是冗余检查，文档标注"当前仅防止异常高频提现"，不声称有更强作用
- **如果不想动 trust 体系**：至少把提现门槛从 ≥60 降到 ≥40（让"受限"档位有意义），或删掉门槛改为纯冷却期 + reserve 覆盖双重约束

## 洞 #3 🟡 HIGH — Tenancy "假阳性"：付了住宿费 ≠ 人在村，治理权换攻击面而非修根因

**v0.3.1 位置**：§九 #1 "读 Tenancy（真交了住宿费=真在地）"

**问题**：

v0.3.1 把治理权判定从 presence（用户自报，可伪造）换成了 Tenancy（住宿记录，不可伪造）。这是正确的方向——但修复不完整：

```
用户 B：
  Day 1   入住，Tenancy#1.status = "active"
  Day 3   飞回上海上班（物理离开南塘）
  Day 3-30 在上海，Tenancy 仍是 active（没退房，住宿费照扣）
  Day 15  社区投票"是否涨住宿费 30%"
          → check_vote_right() 读 Tenancy → status=active → ✅ 可投票
          → 但 B 在上海写字楼里投票，从未踏足南塘
```

Tenancy 证明的是**合同关系**（你付了钱、占了一个床位），不是**物理在场**。v0.3.1 把问题从"可伪造的状态声明"换成了"不会过期的合同证明"——两个都不是`在地`的可靠代理。

对比三个数据源的防伪能力：

| 数据源 | 可伪造 | 假阳性（人不在但显示在） | 假阴性（人在但显示不在） |
|--------|--------|------------------------|------------------------|
| presence 翻牌 | ✅ onclick | ❌ 用户主动翻 | ✅ 忘翻牌 |
| Tenancy 入住 | ❌ 需付钱 | ⚠️ **付了钱但人走了** | ❌ 没入住但人来了 |
| 理想：蓝牙/WiFi 签到 | ❌ 需物理接近 | ❌ | ⚠️ 手机没电 |

**修订建议**：
- **短期（P0）**：治理权 = Tenancy.active **AND** `presence.updated_at ≥ now - 72h`（双重约束：既要交钱，也要近期翻过牌）
- **中期（P1）**：presence 翻牌加服务端防伪——翻牌时提交 GPS 坐标（如有权限），与南塘 geofence 比对；无 GPS 权限则限制为"云在线"
- **文档标注**：§九 #1 加一句"Tenancy 防止了伪造入住，但不防远程投票——这是居委会模型的已知局限，物理在场需额外机制保障"

## 洞 #4 🟡 MEDIUM-HIGH — reserve 覆盖 = 先到先得竞速，无部分提现/无队列/无公平性

**v0.3.1 位置**：§九 #2 "reserve 覆盖" → 落地 `nt.py:512-513`

**代码实锤**：

```python
# nt.py:512-513 — 硬二进制门控
if (pool.reserve or 0) < (pool.frozen or 0) + req.amount:
    raise HTTPException(400, "储备池不足以覆盖冻结+本次提现...")
```

这是全有或全无（all-or-nothing）的二元门控：

```
场景：reserve = 500 NT，月提现窗口开启，10 人各申请 100 NT

  09:00:00  用户 A 申请 100 → reserve(500) ≥ frozen(0)+100 ✅ 通过，reserve→400
  09:00:05  用户 B 申请 100 → reserve(400) ≥ frozen(100)+100 ✅ 通过，reserve→300
  09:00:10  用户 C 申请 100 → reserve(300) ≥ frozen(200)+100 ✅ 通过，reserve→200
  09:00:15  用户 D 申请 100 → reserve(200) ≥ frozen(300)+100 ✅ 通过，reserve→100
  09:00:20  用户 E 申请 100 → reserve(100) ≥ frozen(400)+100 ❌ 拒绝
  ...      用户 F-J 全部拒绝（reserve 已耗尽）

  结果：前 4 人提完，后 6 人零。无队列、无部分提、无优先级。
```

这与多签窗口的"每月某天集中提"叠加，创造了**午夜竞速**激励——提现窗口一开，所有人抢第一时间提交。网络慢的、手速慢的 → 零提现。

**更隐蔽的问题**：reserve 不足时，FrozenPool 中已经冻结但未确认的 NT 无法释放（它不在用户余额里，也不在可用池里，处于 limbo 状态）。用户的钱"冻住了但提不出来"。

**修订建议**：
- **部分提现**：reserve 不足时，不拒绝，改为提 `min(req.amount, pool.reserve - pool.frozen)`（有多少提多少）
- **优先级队列**：按申请时间排序，先到先服务（而非竞速）
- **reserve 补充机制**：cron 自动调水（§七 #5）已有"Operating→Reserve"路径，但当前只在 Operating > 1000 时触发。建议加"reserve < frozen 时自动从 Operating 紧急调水"

## 洞 #5 🟡 MEDIUM — 告警不阻断无升级路径 + §八§九 两版并存 = 运维盲区 + 实施歧义

**v0.3.1 位置**：§九 #4 "告警不阻断日结" + §八/§九 并存

**问题 A — 告警不阻断但无升级路径**：

```
第 1 天 cron 硬检查失败 → logger.critical() + 邮件告警 → admin 看到，处理
第 2 天 cron 硬检查失败 → logger.critical() + 邮件告警 → admin: "又是这个"
第 3 天 cron 硬检查失败 → logger.critical() + 邮件告警 → admin: "知道了"（已疲劳）
...
第 30 天 cron 硬检查失败 → 告警已被邮件规则自动归档
```

v0.3.1 没有定义：
- 连续失败 N 次后的行为变化（升级？阻断？）
- 告警确认/消音机制（admin 确认已知后不再重复告警？）
- 自动恢复检测（连续成功 M 次后降级）

**问题 B — §八§九 并存导致实施歧义**：

| 主题 | §八（v0.3 终版） | §九（v0.3.1 终版） | 实施者该信谁？ |
|------|-----------------|-------------------|-------------|
| 治理权数据源 | 读 W6-P-FE status | 读 Tenancy | ❓ |
| 退出限额 | 非冻结的全部退（无限额） | v3.1 §6.4 三重约束 | ❓ |
| 连续中断 | 未定义 | 换房不中断、tenancy 关闭才中断 | ❓ |

两份"终版"御批在同一文档里给出互相矛盾的指令。红队 B 如果只读到 §八 就写审查回执，会发现"漏洞"其实已被 §九 修复——浪费时间。

**修订建议**：
- **A**：告警加升级路径——连续 3 次同类型 cron 失败 → 自动阻断日结（避免问题累积）；连续 2 次成功 → 自动降级回告警模式
- **B**：在 §八 顶部加一句 `> ⚠️ 本§已被 §九 v0.3.1 终版覆盖。实施以 §九 为准。` ——一行解决歧义
- 或者：直接把 §八 中已被覆盖的行改为删除线，仅保留未被覆盖的部分
