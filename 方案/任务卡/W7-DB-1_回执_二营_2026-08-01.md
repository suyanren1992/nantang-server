### 重点发现

1. **`nt_helpers.py:46`**：`_get_pool(lock=True)` 是全仓最高频的池锁入口（被 transfer / withdraw / earn / cashout / covenant_sign / confirm_withdraw / reject_withdraw 等 20+ 条路径调用），缺 `populate_existing`。虽然多数调用路径中它是该 session 首次读池（无缓存旧值问题），但 **若有路径在同一 session 中先读池后锁池，锁到的就是缓存旧值**。
2. **`accommodation.py:107,140,167`**：三处入住锁全缺 `populate_existing` → 并发入住有超卖/双份租约风险。
3. **PG 锁确实生效**：10 条并发测试全绿，证明 `with_for_update()` + `populate_existing` 在 PG 16.4 上按预期工作——锁阻塞、重读到最新值、CAS 拦截。

## 📎 未验事项

1. **40 条未被 PG 并发测试覆盖的行锁**：体检表 B 列出 40 处有 `populate_existing` + CAS 但无专门 PG 并发测试。本卡范围仅覆盖卡面点名的 10 条（7 原有 + D-3 + D-4a/b），其余未跑实证。
2. **SQL_ASCII vs UTF8 差异**：因 Windows 中文用户名 bug，PG 用 SQL_ASCII 而非 UTF8 初始化。SQL_ASCII 服务端不验证字节序列，对纯 ASCII 测试数据无影响；但若测试数据含中文（如 D-3 的 `space_name="测试房间"`），数据存取可能行为不同。实测全绿，但严格来说不等同于生产 UTF8 环境。
3. **`nt_helpers.py:46` 缺 populate_existing 的实际影响**：D-4a 测试验证了 `_get_pool` 的并发 clamp 行为，但测试中 `_get_pool` 是首次读池（无 session 缓存）。若某业务路径在同一 session 中先读池再锁池，缓存旧值问题才会暴露。需另开卡做路径级审查。
4. **既有红 test_4pool_view**：`test_a_labor_be.py:154` 断言 `reserve=200` 但 `_get_pool` 的 N-1b clamp 把 `reserve` 收窄到 `balance=100`。这是 W7-NT-1 加入 clamp 后的既有测试红，非本卡引入。
