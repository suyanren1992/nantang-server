## 第二题：契约审查（NT_FIELD_CONTRACT.md v0.1）

**§1 sync keys → ⚠️ 缺 task 字段明细**
契约只列了顶层 key，但 sync 的 tasks[] 数组内部字段（poster/publisher/assignees/escrow_amount 等）没有任何规格。前端 _mergeSyncData（core.js:946-948）和 60s 轮询（core.js:898-906）两条路径对 task 字段的使用不一致：

- 轮询路径（core.js:905）读了 t.escrow_amount、t.settler_id、t.settled_at
- sync_all 路径（core.js:946-948）不读这三个字段

后端如果加/删 task 子字段，哪个路径会炸？契约没写，只能看代码猜。

修改建议：契约加 task 对象内部的必含字段清单（至少 poster、assignees、escrow_amount、status、reward、slots、settler_id）。

**§4 新字段 my_escrow / my_frozen / my_accommodation_due → ⚠️ 语义迁移有坑**
契约 §4 写「frozen_balance 保留一个版本（= my_frozen）」。但现行 frozen_balance 是任务托管合计（nt.py:117-122 从任务 escrow_amount 汇总），不是提现待审。

迁移路径：

```
现况 frozen_balance  = 任务托管合计
     ↓
新增 my_escrow       = 任务托管合计（接管原 frozen_balance 语义）
新增 my_frozen       = 提现待审合计
frozen_balance       → 改为 = my_frozen（语义断裂！）
```

前端 core.js:888 ntUser.frozenBalance = data.frozen_balance || 0 读到的是新语义（提现待审），但 core.js:1254 的 NT.getFrozenBalance(u) 读的是客户端 nt-core.js 的冻结余额（任务托管）。同一个 frozenBalance 名字，服务端和客户端将指向不同的东西——这是比 422 更隐蔽的 bug。

修改建议：不要复用 frozen_balance。服务端直接删 frozen_balance，同时发 my_escrow + my_frozen 两个新 key。前端在一个版本内同时读新旧 key，过渡期后删旧 key 读取。避免语义覆盖。

**§5 ALIAS 代码段 → ⚠️ 结构变化未覆盖**

ALIAS 四个映射只处理了键名变化（flat key → flat key），但 camp_balance → camp_ledgers (int → array) 是值类型变化。ALIAS 的 get() 不能处理「原来读 data.camp_balance（一个数），现在需要 data.camp_ledgers.reduce((s,c)=>s+c.balance,0)（数组求和）」。前端 _mergeSyncData（core.js:937-938）只存一个 _poolBalance 单值，换成数组后需要改代码逻辑，改的不是取值层而是业务逻辑层。

修改建议：契约 §2 的 camp_balance→camp_ledgers 标注 ⚠️ STRUCTURAL CHANGE，ALIAS 层不覆盖，需前端在 POOL_KEYS 校验通过后加手动转换函数。或者拆表时 /api/data/sync_all 仍保留 pool_balance 单值（= operating_pool.balance + camp 汇总），新增 pool_detail 对象提供拆分，前端渐进迁移。

## 第三题：新引入问题

**🆕R1 施工依赖未标注 ⚠️**
v3 §十二 P0-4：「工作台资金分布折叠视图 + NT_FIELD_CONTRACT.md 定稿入 git」——两个任务合并在 0.5 天内。但资金分布视图的数据源（my_escrow / my_frozen / my_accommodation_due）目前在服务端不存在。这三个字段需要后端先加到 /api/nt/sync 返回中，前端才能渲染视图。谁先施工？契约没说后端必须先出字段。

修改建议：P0-4 拆成两步：P0-4a 后端加三个新字段到 sync（二营，0.5 天）→ P0-4b 前端造资金分布视图 + 契约定稿（一营，0.5 天）。不能混在一张卡里。

**🆕R1 停机窗口用户无感知 ⚠️**
v3 §3.7「凌晨停机窗口迁移，50 人规模停机 30 分钟」。但前端没有维护模式提示——用户打开 App 看到 502/503 只会以为坏了。v3 没有提到前端需要加维护页/维护提示。

修改建议：P1 拆表卡加前端子任务——停机前 24h 在村口 banner 显示维护预告，停机期间前端拦截所有涉钱按钮显示「系统维护中」。

**🆕R1 大额熔断 429 前端未处理 ⚠️**
v3 §8.4 大额熔断触发后返回 429。前端 API 层（api.js:15-65）对 HTTP 429 没有专门处理——走通用 catch → '网络异常' toast。用户触发熔断后会看到「网络异常」而非「今日提现已达上限」，极其困惑。

修改建议：api.js 加 if (resp.status === 429) 分支，透传 Retry-After 头或服务端 error message，toast 具体原因而非「网络异常」。

**🆕R1 营队 CampLedger 对前端营地页的冲击 → ✅ 无问题**
前端营地资金页目前通过 /api/nt/pools 只显示 camp_balance 单值。拆表后 camp_ledgers 数组反而能按营队分开展示，UI 更清晰。不构成新增问题。
