## E-1 冰箱不能放东西

### 判：🔴 已定位——三因并发，主因是 `renderMgmtPanel` 调度表缺键

### 根因 1（主因 🔴）：调度表键缺失

[app.js:1408](nantang-mobile/js/app.js#L1408) `renderMgmtPanel` 的调度表：

```javascript
var fn = { cleaning:..., stay:..., field:..., kitchen:renderKitchenPanel }[type];
```

没有 `kitchenAdd` 键。用户点"＋放入物品"→ `_toggleForm('kitchenAdd')`([app.js:1901](nantang-mobile/js/app.js#L1901))→ `renderMgmtPanel('kitchenAdd')`→ `fn = undefined`→ **`mgmtBody.innerHTML = ''`——面板被擦成空白**。

若用户在卡片弹窗中操作（`_openMgmtSheet('kitchen')`），情况更糟：`renderMgmtPanel` 写入的是隐藏的 `mgmtOverlay` 的 `mgmtBody`，而可见的 `.mgmt-sheet-inner` 从不更新——点击按钮**静默无效，什么也不发生**。

### 根因 2（次要 🟡）：`_openKitchenQuick` 权限门脆弱

[app.js:2849](nantang-mobile/js/app.js#L2849)：`userCan({role:(AppData.me()||{}).role||'visitor'}, 'isMember')`——`AppData.me()` 可能返回 `{}`→`.role` 为 `undefined`→回退 `'visitor'`→**已认证成员被误判为访客**→快速入口被阻断。

### 根因 3（次要 🟡）：`renderKitchenPanel` 只读 `inventory.office`

[app.js:2307](nantang-mobile/js/app.js#L2307) 只读 `inventory.office`，不从 `inventory.study` 读取——study 厨房的物品在冰箱面板中不可见。

### 修法建议

| 优先级 | 文件:行号 | 修改 |
|--------|-----------|------|
| P0 | app.js:1408 | 调度表加 `kitchenAdd:renderKitchenPanel, fieldPlant:renderFieldPanel` |
| P1 | app.js:2849 | 权限检查改用 `_me()`→`getUsers()[name].role` 替代脆弱的 `AppData.me()` |
| P2 | app.js:2307 | 拼接 `inventory.office` 和 `inventory.study` |

### 爆炸半径

🟡 中。`fieldPlant` 存在同样调度缺陷。修复 P0 同时救活田间种植表单切换。

## E-2 设置按钮没反应

### 判：🔴 已定位——齿轮入口被动态 DOM 覆盖摧毁

### 追踪链

1. **静态入口存在**：[index.html:124](nantang-mobile/index.html#L124) `<span onclick="openSettings()">⚙️</span>` 在 `myChipRow` 中
2. **函数存在且完整**：[core.js:1431](nantang-mobile/js/core.js#L1431) `openSettings()`——但实际调的是 `renderProfile('edit')`（个人资料编辑器），不是独立设置面板
3. **入口被摧毁**：[data.js:306](nantang-mobile/js/data.js#L306) `row.innerHTML = h`——`updateMyChips()` 把 `myChipRow` 全量替换为任务芯片（🔴待处理/📋进行中/🧾待结算），**不含齿轮图标**

```
showMy() → refreshUserUI() → updateMyChips('tasks') → row.innerHTML = h
                                                         ↑ 杀手行——齿轮消失
```

### "批次5 ③设置面板实装" 真伪

`core.js:1430` 注释自称"U-1b/A-10: 设置面板入口——直接进入编辑模式"——**但从未实现独立设置面板**。`openSettings()` 只是绕道个人资料编辑器（改名字/钱包/密码），不是设置面板。齿轮入口搭了、函数搭了、但面板没做 + DOM 被覆盖 = 用户感知"没反应"。

### 修法建议

**方案 A（推荐）**：齿轮图标搬出 `myChipRow`→放入 `my-topbar`（顶部栏，头像旁），与 `toggleProfile()` 同级。顶部栏不被 `updateMyChips` 覆盖。

**方案 B**：`updateMyChips` 的 `h` 末尾补齿轮图标——但 UI 图标与业务芯片耦合不优雅。

### 爆炸半径

🟢 低。搬齿轮位置不改任何逻辑。

## E-4 重置后动态没清+归属

### 判：🔴 已定位——后端删表完整，前端合并策略只追加不清

### ① 后端删表清单实证

[admin.py:130,133](server/routes/admin.py#L130)：**`Journal` 和 `ActivityLog` 均在 hard/soft 两模式删除清单中**，共删 15 张表。后端删表完整，不存在遗漏。

### ② 前端根因

[core.js:958-965](nantang-mobile/js/core.js#L958) `_mergeSyncData`：`activity_log` 合并策略是**去重追加**（push），不是替换。reset 后服务端返回 `activity: []`（空数组），forEach 空数组不 push 任何条目——**但 localStorage 中旧条目毫发无损**，继续显示。

### ③ 动态流语义

| 维度 | ActivityLog | Journal |
|------|-------------|---------|
| 数据模型 | **无** user 列 | 有 user 列 |
| 服务端查询 | `select(ActivityLog)` 全表 | `where(user==uid)` |
| 前端渲染 | 全量无过滤 | 个人流 |
| 语义 | **社区公共流** | 个人日记 |

所有 5 处渲染函数无一做 user 过滤。

### 设计裁决点（呈砚仁）

| # | 裁决点 | 选项 |
|---|--------|------|
| 1 | 动态流应只显示自己还是全社区？ | A.维持社区公共流 / B.改为个人流(加user列) / C.混合(加scope) |
| 2 | reset后动态应清空吗？ | A.服务端下发`activity_clear:true` / B.客户端主动`AppData.reset()` / C.改合并为覆盖 |
| 3 | ActivityLog 应加 user 列吗？ | 当前 text 拼接用户名靠字符串解析，建议加结构化 user 列 |

### 爆炸半径

🟡 中。改合并策略影响所有 sync_all 路径。

| # | 症状 | 严重度 | 根因行号 | 描述 |
|---|------|:--:|------|------|
| 1 | 字体变大 | 🟢 | — | 非代码缺陷——`.activity-item` CSS 显式 `.65rem`，疑 OS/浏览器缩放。复测时退出 100% zoom |
| 2 | 时间不对 | 🔴 | [ui-archive.js:44](nantang-mobile/js/ui-archive.js#L44) | `logActivity()` 用 `new Date().toISOString()` 而非统一时间源 `Clock.iso()`；`_timeAgo` 同步用 `new Date()` 而非 `Clock.date()` |
| 3 | 内容不对 | 🔴 | [ui-social.js:59-112](nantang-mobile/js/ui-social.js#L59) | `_formatActivityItems` 的 if/else-if 链覆盖 16 种 type，但至少 9 种真实写入的 type（`system`/`pool_refill`/`role_change`/`camp_confirm`/`discovery_*`/`labor_report`）未被处理→保持 `null`→不 push→**条目消失** |
| 4 | 4 条日志 | 🟡 | 同上 | 症状 3 的后果——翻页 size=10 但 6+ 条被丢弃前已过滤，仅剩 4 条命中已知 type |

1. `ui-social.js:111` 最后一个 `else if` 后加 `else { item = {icon:'📋', filterKey:'全部', html:esc(text)}; }`
2. `ui-archive.js:44` 改为 `time: (typeof Clock !== 'undefined' ? Clock.iso() : new Date().toISOString())`
3. `ui-social.js:140` 同步改为 `var now = (typeof Clock !== 'undefined' ? Clock.date() : new Date())`

### 爆炸半径

## E-6 档案室跳错

### 判：🟡 已定位——不是跳错，是 `closeMyPage()` 揭示了背后的全貌页

### 入口路由对比

| 入口 | onclick | 行为 |
|------|---------|------|
| 社区副本 | [data.js:720](nantang-mobile/js/data.js#L720) `closeOverlay(...);openArchive('members')` | 关社区overlay→弹档案overlay ✅ |
| 工作台 | [ui-archive.js:466](nantang-mobile/js/ui-archive.js#L466) `closeMyPage();openArchive('log')` | 关工作台→**揭示villagePage(全貌页)**→弹档案overlay ❌ |

### 根因

[core.js:1763](nantang-mobile/js/core.js#L1763) `closeMyPage()` 执行 `villagePage.classList.remove('hidden')`——把全貌页显示出来。用户看到全貌页 + 覆盖在上面的 overlayArchive，感知为"跳到了全貌页"。

这是 D-5 教训的同类错误：**先销毁上下文，再执行动作。**

### D-5 双轨判定

存在两套 `initArchiveBuilding` IIFE（[ui-archive.js:209](nantang-mobile/js/ui-archive.js#L209) 和 [index.html:1103](nantang-mobile/index.html#L1103)），靠 `hasArchive` 去重——当前无害但冗余。渲染函数散落三个文件（ui-archive.js/ui-camp.js/index.html），均填充同一 `#archiveBody`——不是两套渲染，是**多文件合写一个 overlay**。

### 修法建议（1 行）

[ui-archive.js:466](nantang-mobile/js/ui-archive.js#L466)：`closeMyPage();openArchive('log')` → `openArchive('log')`

overlayArchive 的 z-index 高于 myPage，直接弹在工作台上即可。关闭 overlay 后栈回退，用户仍在工作台。

### 爆炸半径

🟢 极小。一行 onclick，不改任何逻辑。
