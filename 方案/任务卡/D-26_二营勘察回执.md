## a. 现状：住宿费到底怎么算、何时扣、谁触发

**结论：日扣逻辑已经存在，但触发机制有缺口。**

### 现有机制链路（实证）

1. **服务端日扣端点已实装**：`server/routes/nt.py:985-1053` `POST /api/system/daily-tick`
   - 遍历所有 `active` Tenancy
   - 按房间定价扣：BED_RATES 硬编码 `dorm101=20/dorm102=30/dorm103=30/dorm104=60/dorm105=30/dorm106=35/fallback=28`
   - 余额充足：扣 `user.nt_balance` → 回流 `pool.balance` → 写 ledger `accommodation_fee`（status=settled）
   - 余额不足：`t.debt += rate`（累计欠费）
   - `t.last_deducted = today` 标记幂等

2. **池的联动操作**（同端点内）：
   - `pool.balance < 300` → 补填 20（池自发印钱，M2 决策）
   - `pool.balance > 1000` → 超出 500 的盈余划到 `pool.reserve`
   - `pool.balance < 150 且 reserve>0` → 从储备池回调到 300
   - `pool.last_tick_date = today` 幂等

3. **行锁已正确对齐 D-5/D-17**：`select(User)...with_for_update().execution_options(populate_existing=True)` ✅

4. **前端触发**：`nantang-mobile/js/core.js:1026`
   ```js
   if (typeof API !== 'undefined' && API.token) API.request('POST', '/api/system/daily-tick')
   ```
   ——即**用户登录/进入时触发**，客户端带 JWT。

5. **前端防双扣**：`app-data.js:473` 注释 "HTTP 模式由服务端 daily_tick 处理，客户端跳过"，`app-data.js:495 NT.spend(...住宿费...)` 只在 `!API.token` 离线模式跑。

6. **欠费结算**：`accommodation.py:78-105`（退房）+ `accommodation.py:40-49`（换房）——退房/换房时若 `t.debt > 0`，余额够就扣、不够就写 `debt_unpaid` ledger。

### 缺口（关键发现）

| # | 缺口 | 证据 |
|---|---|---|
| G1 | **真正的 cron 没接日扣** | `server/cron.py` 全文 119 行，零 Tenancy/debt/rent 字样，只生成周期任务（读 periodic_tasks.json）。cron.py 每日 00:05 跑但从不调 daily-tick。 |

## b. 自动日扣缺什么

按现状已经跑起来了一半，缺口主要是**触发可靠性 + 数据一致性**：

| 需要补的 | 类型 | 复杂度 |
|---|---|---|
| G1+G2：把 daily_tick 接入 cron.py（每日 00:05 自动跑，不依赖用户上线） | 触发链 | 低（cron.py 已经在跑，加一段 import 调用 daily_tick 逻辑即可） |
| G2'：daily_tick 应该补扣 `last_deducted → today` 之间漏扣的天数 | 幂等完善 | 低（已存 last_deducted，算 daysPassed 即可，复用 app-data.js:480-482 客户端旧算法） |
| G3+G6：房费率从 map_locations JSON 读（和前端 pricePerBed 对齐），fallback 统一 30 | 数据一致性 | 中（要从 map_locations 反序列化） |
| G4：NT 到账路径（verify_task/transfer/topup）在 commit 前查 `debt>0` 自动扣欠费回流社区池 | 追缴触发器 | 中（要在 nt.py _adjust_balance 类函数挂钩子） |
| G5：daily_tick 仅管理员/系统 cron 可触发（或从 cron 直接调函数不走 HTTP） | 鉴权 | 低 |

## c. 最小施工方案 + 影响面

### 最小方案（P0，1 张中卡）
1. **cron.py 日触发接入**（解决 G1+G2）：cron 每日 tick 时直接调一个新函数 `_run_daily_accommodation()`（从 nt.py daily_tick 抽出核心逻辑，避免走 HTTP）
2. **补扣漏扣天数**（解决 G2'）：`daysPassed = (today - last_deducted).days`，循环扣 N 天费 + N 次写 ledger
3. **鉴权收敛**（解决 G5）：`/api/system/daily-tick` 端点加 `require_admin` 或改为内部函数，前端 core.js:1026 改为"登录后由服务端顺带返回 tick_ran 标志，不主动 POST"

### 后续卡（P1，另发）
- 房费率读 map_locations.pricePerBed（G3+G6）
- NT 到账时自动追缴欠费（G4）

### 影响面
- 资金路径：daily_tick 已经加了行锁（D-5/D-17 对齐），本方案只补触发和补扣，**不新增无锁资金操作**
- 跨端：前端 core.js:1026 要删或改（配合 G5），其他前端不动
- 回滚：cron 改回不调 daily_tick 即可；数据库 last_deducted/debt 字段不动
- 测试：D-20 e2e 骨架可扩一条"造 active Tenancy + last_deducted=昨天 → 触发 daily_tick → 断言扣款/欠费 + last_deducted=今天"

## 太傅注（卡面必附）

**为什么"日扣"和"退房一次结算"在经济闭环里不是一回事？**

退房结算本质是**事后清算**——用户享受了 N 天住宿，退房时才结账。这有两个致命问题：

1. **坏账风险**：住到第 30 天退，欠了 900 NT，退的时候发现余额 0——这 900 成了死账（accommodation.py 现在就是写 `debt_unpaid` ledger，但永远讨不回来）。日扣是**预付/日清**，每天先扣后住，最多坏账 1 天，风险敞口 28-60 NT。
2. **货币回笼速度**：社区池靠任务发放 NT、靠消费回流 NT 形成闭环。退房结算把回笼推迟到退的那一天，如果平均入住 14 天，池里就永远压着 14 天×均价的 NT 在"应收账款"里，池会干涸，必须靠 M2 补填（nt.py:1021 pool.balance<300 补 20）——这就是印钱税，稀释所有持币者。日扣让 NT 每天回流，池补填触发频次下降，货币更稳。

补课数据库/后端章的一句话：**资金类操作的原子单位是"天"，不是"会话"**。cron 00:05 是天的边界，退房是会话边界——前者是结算的唯一合法时点，后者只是最后的清账窗口（兜底扣 debt）。现在的实现是"客户端登录触发日扣"，等于把门钥匙交给了最后一个进门的人，能跑但不该长期这样。
