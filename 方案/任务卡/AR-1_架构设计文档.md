## 一、与现状图的分工（防双源）

- **架构现状图** = 快照（代码此刻长什么样，commit 锚点随码走，arch_check 黄灯报警）。
- **架构设计文档** = 道理（为什么这样分层/模块边界为什么在这/数据为什么这样流/哪些是有意设计、
  哪些是历史包袱）。写「为什么」，不重复抄「是什么」——现状描述一律指现状图，不复制。
- 铁律 8 联动：本文档头部同样带 commit 锚点，动结构的卡仍只强制更新现状图；
  设计文档按批修订（每批收官复核一次是否需改），不随单卡走（YAGNI）。

## 二、必答章节（人话四段标准，砚仁能复述为度）

1. **分层道理**：客户端静态站 / FastAPI 服务端 / Neon PG / OP 链四层——为什么是这么切，
   每层只许干什么不许干什么（边界即承重墙）。
2. **模块边界**：`server/` 路由模块划分（nt/tasks/data/admin/accommodation/cron…）与
   `nantang-mobile/js/` 模块划分的对应关系；跨端契约（API 面）在哪定义、谁有权改
   （宪法级改动口径：触发源/调用方/幂等键）。
3. **数据流主干**：NT 资金闭环（账本=nt_ledger 唯一真源，双池）· presence/共享数据同步链路
   （sync_shared 透传）· 离线队列→服务端合并；每条流指到数据模型.md 对应节，不重复画。
4. **有意设计 vs 历史包袱**：如实标注——哪些结构是 v11 设计落地，哪些是开荒期权宜
   （例：presence 单字段混维、3 条 FK、cashout 残留），包袱项挂批③/远期线索引。
5. **拆分差距**：E-1 差距清单的现状更新——哪些已补（S2/批①），哪些仍缺，给「何时该拆」的
   触发条件（规模判据，不提前拆）。
6. **已知限制**：Render 冷启动 / Neon 免费层 / SQLite 行锁失效 / PWA 缓存——每条带应对口径。

## 三、可证伪验收判据（丞相复核时逐条跑）

1. 全文 `文件:行号` 引用**全量机检**（宪法 §三.2），全符才交付。
2. 抽查 3 处「现状描述」与架构现状图一致；发现复制粘贴大段现状图内容 → 打回（双源）。
3. 每个「历史包袱」标注可在代码中实证（grep 出病灶行）。
4. 模块边界表与 `server/routes/`、`nantang-mobile/js/` 实际文件清单逐一对上。
5. 砚仁测试：指「为什么前端不用框架」「为什么账本和钱包分两处」两问，读文档能答。
6. 版本号与 frontmatter 一致（太傅老毛病自查）。
