## ① 田间管理后端：3 个前端提交入口，服务端统一走 verification

### 入口清单

| # | 前端入口 | 文件:行号 | verification type | 定价来源 | 服务端落点 |
|---|---|---|---|---|---|
| A | `_submitFarmEntry()`（田地快捷面板） | `app.js:3024-3040` | `field_action` | `farming_pricing` | POST `/api/data/verifications` |
| B | `_harvestCrop()`（点击作物收割） | `app.js:969-978` | `field_harvest` | 硬编码 `15` | POST `/api/data/verifications` |
| C | `openSelfReport({cat:'farming'})` → `_submitSelfReport()`（卡片室上报） | `ui-cardroom.js:1094-1131` | `labor_report` | `labor_pricing`（经 `_getLaborNT`） | POST `/api/data/verifications` |

### 服务端入口（唯一）

三个前端路径最终都调 `AppData.addVerification()` → `app-data.js:336-354` → HTTP POST `/api/data/verifications`。

服务端 handler：`server/routes/data.py:203-220`。写入 `Verification` 表，status=pending，等待校核。

**结论：服务端只有 1 个写入入口（`POST /api/data/verifications`），三入口在服务端是统一的。** 但三入口的 **verification type 不同**（`field_action` / `field_harvest` / `labor_report`），且 **nt_amount 由客户端传入、服务端不校验定价合理性**。

## ② 提交是否接校核？—— 三入口全部接校核

### 校核闭环证据

| 入口 | addVerification 调用 | 校核状态 |
|---|---|---|
| A `_submitFarmEntry` | `app.js:3035` `AppData.addVerification('field_action',...)` | 走校核 ✅ |
| B `_harvestCrop` | `app.js:973` `AppData.addVerification('field_harvest',...)` | 走校核 ✅ |
| C `_submitSelfReport` | `ui-cardroom.js:1105-1106` `AppData.addVerification('labor_report',...)` | 走校核 ✅ |

`addVerification` 函数（`app-data.js:336-354`）在 status=pending 写入后，HTTP POST 到服务端 `/api/data/verifications`。

### 结算在服务端 approve 时发生

校核通过端点：`server/routes/nt.py:1016-1050`。
- 金额从 `Verification` 表取（`vfy.nt_amount`，`nt.py:1018`），**不信任客户端**（注释原文）——但写入时信任客户端。
- 扣社区池 → 发 NT 给 doer + verifier reward → 写 ledger（`nt.py:1023-1049`）。

### ⚠️ 潜在绕过路径（非本卡症状，但须留证）

服务端存在 `/api/nt/earn-sync`（`nt.py:1094-1133`）：用户可直接 POST 离线 earn，从社区池直接扣款结算，**不经过校核**。
- 日上限 5 次（`nt.py:1099`）
- 前端当前**未调用**此端点做田间/打扫结算（grep `earn.sync` 前端 0 匹配）
- 但任何客户端可调 → **设计稿应考虑封堵或收编**

服务端存在 `/api/nt/earn`（`nt.py:323-325`）：admin 直接发奖，不经过校核。admin 门控，风险低。

## ③ 定价分裂：4 套定价表 + 多处硬编码

### 田间动作定价对比（同一动作，4 套数值）

| 动作 | farming_pricing | labor_pricing | LABOR_ACTIONS 硬编码 | _LABOR_NT_DEFAULTS |
|---|---|---|---|---|
| | `app.js:51` | `app.js:66-76` | `ui-cardroom.js:63-73` | `ui-cardroom.js:25-34` |
| 收割 harvest | **15** | **15** | **15** | **15** |
| 浇水 water | **3** | **3** | **5** | **3** |
| 种植 plant/sow | **5** | **5** | **8**（sow） | **5** |
| 施肥 fertilize | **5** | **15** | **8** | **15** |
| 除草 weed | **5** | **15** | **10** | **15** |
| 查看 view | **2** | —（无） | —（无） | —（无） |

**分裂核心**：`farming_pricing` 和 `labor_pricing` 在 fertilize（5 vs 15）、weed（5 vs 15）上差 **3 倍**。LABOR_ACTIONS 硬编码又是第三套数值。

### 路径 A 用 `farming_pricing`，路径 C 用 `labor_pricing`

- `_submitFarmEntry()`（app.js:3033）：`var pricing = _mlConfig().farming_pricing`
- `_submitSelfReport()`（ui-cardroom.js:1101）：`var ntAmount = _getLaborNT(_srDraft.actionId)` → 读 `labor_pricing`

**同一农活（如除草），从田地面板提交=5 NT，从卡片室上报=15 NT。**

### 收割硬编码（入口 B）

`_harvestCrop()`（`app.js:973`）：`AppData.addVerification('field_harvest', _me(), '收割 '+crop.name+' @'+plot.name, { plotId:plotId, crop:crop.name }, 15, ...)`

NT=15 直接写死在函数调用中，不读任何配置表。

### 大扫除定价对比

| 来源 | 文件:行号 | 定价结构 |
|---|---|---|
| cleaning_pricing | `app.js:61` | `{ dirty:20, warning:15, clean:5 }` |
| nt_rewards.cleaning | `app.js:64` | `cleaning: 10` |
| 周期任务配置 | `config/periodic_tasks.json:4` | `reward: 12`（"周末大扫除"） |

打扫定价按**脏污等级**三档（red→dirty:20 / yellow→warning:15 / green→clean:5），与田间的按动作定价是不同模型。

## ④ 大扫除后端：数据结构、结算路径、与田间的异同

### 数据结构

打扫数据**纯前端本地**，存 `map_locations` 的 config 段：
- `cleaning.spaces`：`{ [buildingId]: { dirtiness: number } }`
- `cleaning.history`：`[{ date, person, roomName, nt, note }]`
- `cleaning.nextDate`：下次大扫除日期
- `cleaning.mySelections`：用户选择的打扫房间列表

服务端无专用打扫表。脏污度数据随 `sync_shared` 的 `map_locations` 上行持久化到 `MapLocation key="shared"` 的 JSON 中。

### 结算路径（3 条前端入口，全部走校核）

| # | 前端入口 | 文件:行号 | 定价逻辑 |
|---|---|---|---|
| D | `_submitMyCleaning()`（管理面板"我完成了打扫"） | `app.js:2048-2076` | 按房间脏污等级：red=dirty / yellow=warning / green=clean |
| E | `_toggleForm('cleaning')`（大扫除表单展开→直接打扫按钮） | `app.js:2560-2577` | 同上 |
| F | `openSelfReport({cat:'cleaning'})` → `_submitSelfReport()` | `ui-cardroom.js:1094-1131` | 走 `_getLaborNT(actionId)` 读 `labor_pricing` |

三条路径都调 `AppData.addVerification('cleaning', ...)` → POST `/api/data/verifications` → 等 approve → `nt.py:1016-1050` 结算。

### 田间 vs 大扫除：异同对比

| 维度 | 田间 | 大扫除 |
|---|---|---|
| 服务端专用端点 | ❌ 无（共用 verifications） | ❌ 无（共用 verifications） |
| 结算方式 | 校核 approve 后社区池出 | 校核 approve 后社区池出 |
| 定价模型 | 按**动作类型**定价（收割/浇水/…） | 按**脏污等级**定价（红/黄/绿） |
| 定价统一性 | ❌ 4 套数值分裂 | ❌ 3 套数值（cleaning_pricing / nt_rewards / periodic_tasks） |
| 数据结构 | plots 存在 map_locations JSON | cleaning.spaces 存在 map_locations JSON |
| 持久化 | `MapLocation key="shared"` | `MapLocation key="shared"` |
| 卡片室联动 | ✅ 同时写 cardDiscoveries | ✅ 同时写 cardDiscoveries |

## ⑤ 统一改造点清单（"选对象→选劳动→提交→校核"一套流程）

### 后端需改 / 需建的点

| # | 改造点 | 现状 | 改动方向 | 影响范围 |
|---|---|---|---|---|
| 1 | **服务端定价校验** | `data.py:203-220` 写入 Verification 时 `nt_amount` 由客户端传入，服务端不校验合理性 | 新增服务端定价表（从 MapLocation config 读 or 硬编码），写入时校验 `nt_amount` 不超合理范围 | `server/routes/data.py` |
| 2 | **earn-sync 封堵或收编** | `nt.py:1094-1133` 允许用户直接 earn 不经校核 | 要么废除此端点、要么限制只能同步"已校核通过"的离线 earn | `server/routes/nt.py` |
| 3 | **统一 verification type** | 田间有三种 type（`field_action` / `field_harvest` / `labor_report`），打扫有 `cleaning` / `labor_report` | 统一为 `labor` 一种 type，detail 中携带 category（farming/cleaning/cooking）和 actionId | `server/routes/data.py` + 前端 |
| 4 | **服务端结算函数统一** | 校核 approve 结算已在 `nt.py:1016-1050` 统一，但 earn-sync 绕过 | 确保所有 NT 发放只走 approve 路径 | `server/routes/nt.py` |
| 5 | **定价单一真源** | 4 套前端定价表（farming_pricing / labor_pricing / LABOR_ACTIONS / _LABOR_NT_DEFAULTS）+ 服务端无定价 | 前端收敛为 1 套（公约配置 `labor_pricing` 为唯一源）；服务端建立对照表 | 前端 `app.js` + `ui-cardroom.js` + 服务端 `data.py` |
| 6 | **打扫定价模型改造** | 打扫按脏污等级定价（red/yellow/green），与田间的按动作定价模型不同 | 若要统一为"选劳动"模型，需将打扫也改为按动作定价（如"扫地拖地 10 NT"），脏污等级可作为 bonus 系数 | 前端 `app.js` |
| 7 | **证据字段标准化** | 各入口 detail 结构不一致（field_action 有 plot/actionKey，cleaning 有 roomId/status） | 统一 detail schema：`{ spaceId, actionId, category, evidence? }` | 前端 + 服务端 |

### 不需要改的点

- **校核流程本身**：服务端 approve 结算逻辑（`nt.py:1016-1050`）已经是统一的，不需要重构
- **持久化**：田间/打扫的空间数据都存 `MapLocation key="shared"`，结构已统一
- **卡片室联动**：三入口都写 cardDiscoveries，已统一

### 前端改造点（不在二营阵地，留证供一营参考）

- 收敛 `_openFarmQuick` / `_harvestCrop` / `openSelfReport` 三条前端入口为一条
- 收敛 `_submitMyCleaning` / `_toggleForm('cleaning')` / `openSelfReport` 三条打扫入口为一条
- 消除 `farming_pricing` 与 `labor_pricing` 的数值冲突
- `_harvestCrop` 的硬编码 `15` 改为读配置

## 太傅注（三行）

- 服务端没有"田间端点"也没有"打扫端点"——所有劳动结算都走 Verification 校核闭环，这是好基础，统一改造不必从零建。
- 定价分裂是真病根：4 套前端数值 + 服务端零校验 = 同一动作不同入口报不同 NT，且客户端可以虚报。设计稿必须先定"单一真源在哪"。
- earn-sync 是校核闭环的后门——设计稿若不封堵或收编，任何统一流程都会被这条旁路绕过。
