## 盲点 #1 🔴 CRITICAL — 投票无最低法定人数 + 退出无限额 = 双重治理与经济脆弱性

**v0.3 位置**：§2.2 治理表 + §八 御批 #3

**问题 A — 投票无 quorum，存在"三人定乾坤"风险**：

v0.3 全文未定义投票最低法定人数。投票权 = "在地即有，一人一票"（§2.2）。极端场景：

```
南塘 20 人，春节期间 17 人返乡/旅行，仅 3 人在村。
这 3 人可投票通过任何提案——包括修改劳动价目、
调整住宿费率、甚至解散营地。
```

这不是理论推演——中国农村居委会组织法也要求村民会议须过半成年村民参加方为有效。物理居委会的"在场"有天然 quorum（人到不了就是到不了），数字化治理的"在地"反而消除了物理约束——**3 人足以形成合法多数**。

**问题 B — 退出无限额与 v3.1 设计矛盾，形成资本外逃通道**：

v0.3 内部存在三重矛盾：

| 出处 | 规则 |
|------|------|
| v0.3 §2.6 | 换外部 NT **限额 10%** |
| v0.3 §四 #3（待皇帝拍） | 10% / 全免 / 你来定 |
| v0.3 §八 御批 #3 | **非冻结的全部退（无限额）** |
| v3.1 §6.4（真仓设计） | 50-200 NT 门槛 + 7 天冷却 |

御批选择了"无限额"，但这与真仓 v3.1 的提现熔断体系（门槛 + 冷却 + 熔断上限）**结构性冲突**。如果御批优先，意味着：

1. 长期居民可一次性提走全部非冻结 NT（可能数千 NT）
2. 多人同时退出 = 社区流动性枯竭
3. 会计等式依然成立（NT 从 Σuser 移到外部），但社区运营池可能瞬间归零
4. ReservePool 只担保 FrozenPool，不担保大规模提现

**问题 A + B 叠加的极端场景**：

```
第 1 周：3 人在村 → 投票通过"降低劳动报酬 50%"
第 2 周：劳动收入腰斩，5 人不满决定搬走
第 3 周：5 人各提走 3000+ NT（无限额），运营池从 5000 跌至 500
第 4 周：运营池 < 300 → cron 自动补水（Reserve→Operating）
         但 Reserve 也只够补几次
```

治理失控 → 经济崩溃。两个机制相互放大。

**修订建议**（入 v0.4）：
- **投票 quorum**：≥ 在地人数的 30% 或 ≥ 5 人（取大者），方为有效投票
- **退出限速**：非冻结余额 > 1000 NT 部分，分批释放（如每月最多 1000 NT），防瞬时抽干
- **紧急制动**：运营池 < 500 NT 时自动冻结所有提现（仅保留住宿/消费）
- **解决矛盾**：v0.3 §2.6 与 §八 择一统一，建议走御批方向但加限速

## 盲点 #2 🟡 HIGH — 荣誉系统（等级/勋章）无刷新机制，1 年内激励衰竭

**v0.3 位置**：§2.2 "CV/XP/等级/勋章纯荣誉，全不挂治理权" + §三 B★★★★★

**问题**：

v0.3 将等级/勋章定性为"纯荣誉"，且明确"等级不降"（§三 B★★★★★："等级不降（纯荣誉）"）。这意味着：

```
2026 年 8 月：砚仁升"老把式·厨房"，社区首批，大家祝贺 🎉
2027 年 8 月：砚仁仍是"老把式·厨房"，没有任何变化
              新住户淑惠看到：砚仁一年前就是老把式了，
              我永远追不上 → 放弃追求
              砚仁看到：我已经是老把式了，没有更高目标
              → 失去动力
```

游戏化设计研究（Deterding 2011, Hamari 2014）反复验证：**纯荣誉徽章在无刷新机制下，激励半衰期约 6-12 个月**。在小社区（20-50 人）中，社会认可已通过日常互动充分传递，徽章提供的边际信号价值递减更快。

v0.3 做了正确的第一步（治理权与荣誉分离），但把荣誉系统留在了"一次性勋章"阶段，没有生命周期设计：

- ❌ 无季节性重置（如"季度劳动之星"）
- ❌ 无新层级（老把式之后是什么？）
- ❌ 无轮换/挑战（同一人永久持有 = 榜单冻结）
- ❌ 无社区投票成分（勋章只是算法结果，不含社会认可）

**修订建议**（入 v0.4）：
- **季节性勋章**：每季度重置的荣誉称号（如"春季厨房之星"），由社区投票+算法混合产生
- **终身成就**：永久勋章只保留极少数（如"创始居民"），其余设 6-12 月有效期
- **导师路径**：老把式解锁"带徒弟"功能，徒弟升级给师傅 CV 加成——把静态荣誉转化为动态社会关系

## 盲点 #3 🟡 HIGH — 多签单点故障 + 账号继承真空

**v0.3 位置**：§2.3 多签 "持有人:组长+杨振" + §2.2 投票权 "离开即消失"

**问题 A — 多签是双点串联，任一点失效 = 全系统冻结**：

```
多签出账 = 组长签 + 杨振签，两人缺一不可
提现窗口 = 每月某一天集中提

场景 1：杨振 12 月去海南过冬 3 个月
       → 12 月、1 月、2 月的提现窗口全部失效
       → 所有用户提现冻结 3 个月

场景 2：杨振生病住院 2 周，跨越提现窗口
       → 当月提现全部阻塞

场景 3：杨振决定搬离南塘
       → 多签永久失效，需重新部署合约
```

这是串联系统（series system）的可靠性问题：R_system = R_组长 × R_杨振。任何一方的可用性 < 100%，系统可用性就是乘积。两人都是自然人，都会生病、旅行、离开——这不是"故障会不会发生"，而是"什么时候发生"。

**问题 B — 死亡/退出时账号继承完全空白**：

v0.3 和 v3.1 均未涉及：
- 用户去世，NT 余额归谁？转入社区公益池？继承人？
- 已冻结的 NT（在 EscrowPool 中的任务托管）如何处理？任务由谁完成？
- 如果去世者是**多签持有人**（组长或杨振）→ 多签永久失效 + 账号余额无法处置 = 双重死锁

这不是低频场景。50 人社区在 5 年运营期内，按中国 2023 年死亡率（7.87‰）估算，期望死亡人数 ≈ 2 人。

**修订建议**（入 v0.4）：
- **多签备份**：指定 1 名备用签署人（如丞相/太傅角色），杨振不可用时自动激活
- **提现窗口弹性**：多签任一人在窗口期不可用 → 自动顺延至下一个可用日（最长不超过 7 天）
- **数字遗产**：注册时可选填"NT 继承人"（默认 = 社区公益池）；死亡确认后（社区公告 + 7 天异议期），余额自动转移
- **Escrow 兜底**：发布者死亡时，其托管任务自动取消 → EscrowPool → 社区公益池

## 盲点 #4 🟡 MEDIUM-HIGH — 照护劳动定价编码价值观偏差

**v0.3 位置**：§三 B★★★★★ + §八 御批 #6

**问题**：

v0.3 新增 3 项照护劳动，定价如下：

| 劳动 | NT |
|------|-----|
| chef（做饭） | **20** |
| care_elderly（照顾老人） | 15 |
| care_sick（照顾病号） | 15 |
| mentor_newbie（带新人） | **12** |
| take_trash（倒垃圾） | 5 |

这个价格表编码了一套价值观：

```
做饭（20） > 照顾老人/病号（15） > 带新人（12） > 倒垃圾（5）
```

在一个**以"相互照护"为核心叙事**的共居社区中，这是自反的：
- 照顾失能老人需要体力 + 情感投入 + 可能的排泄物处理 + 不可预测的时间
- 做饭有明确的起止时间，成果可见，社会认可度高
- 但做饭定价比照护高 33%

**实际后果**：
- 如果淑惠需要赚 NT 付住宿费，她会优先抢 chef 而非 care_elderly
- 照顾老人的工作会落在"不需要赚 NT"的人身上（退休老人照顾更老的老人？）
- mentor_newbie(12) 是最低价——带新人是社区长期存续的命脉，却定最低价
- 这形成了一个**隐性的"男性劳动/女性劳动"价格双轨**（照护工作全球范围内由女性承担 76%，ILO 2023）

**修订建议**（入 v0.4）：
- care_elderly → **25 NT**（高于 chef，体现代际照护的社区优先级）
- care_sick → **22 NT**（临时性+紧急性溢价）
- mentor_newbie → **18 NT**（至少不低于 chef 的 90%，体现新人融入的战略价值）
- 或引入**"照护者住宿折扣"**：月照护 ≥ 40h → 住宿费减半（比涨价更优雅，不破坏劳动定价体系）

## 盲点 #5 🟡 MEDIUM — 新住户心理被剥夺感 + checkbox 文化挤出效应

**v0.3 位置**：§2.2 治理门槛 + §三 B★★★ 志愿劳动 checkbox

**问题 A — 3 周提案冷却期无紧急例外通道**：

提案权 = "连续居住 ≥ 3 周 + 在地"。新住户前 3 周：
- ✅ 可以投票（在地即有）
- ❌ 不能提案
- ❌ 不能发起 D-15 公约修改
- ❌ 不能对影响自己住宿/生活的决策提出正式替代方案

如果新住户入住第 2 天，社区投票"即日起住宿费涨 50%"——新住户只能投反对票，不能提案"新住户首月免涨"。

这种"你可投票但不可提案"的半权利状态，比"完全无权利"更容易产生**相对剥夺感**（relative deprivation, Runciman 1966）——因为投票权给了"你已是我们一员"的幻觉，提案权的缺失则提醒"你其实还不是"。

**问题 B — 志愿 checkbox 的框架效应**：

v0.3 §三 B★★★："留'志愿劳动'checkbox，不计 NT，只加 CV/XP"

行为经济学经典发现（Gneezy & Rustichini 2000, Frey & Jegen 2001）：

> 引入"不计报酬"的选项，本身就是在提醒用户"默认选项是计报酬的"。

checkbox 的设计逻辑是"给用户不拿钱的选择"——但 UX 上的呈现是：

```
☑ 本次劳动领取 NT（默认勾选）
☐ 志愿劳动，不领 NT，只加 CV/XP
```

这重构了用户的心理框架：劳动 = 交易（默认），不拿钱 = 特殊（需主动操作）。在社区早期（劳动换 NT 的文化尚未固化），这个 UI 可能**加速**而非延缓"一切劳动货币化"的文化形成。

**修订建议**（入 v0.4）：
- **新住户紧急提案**：涉及住宿/安全/权益的决策，新住户可申请"紧急动议"，经 2 名 3 周+住户联合署名即可立案
- **checkbox 反向默认**：社区前 3 个月，checkbox **默认不勾选 NT**（劳动默认 = 贡献，拿 NT 需主动勾选）。3 个月后由社区投票决定是否翻转默认值。这是"用 UI 保护文化"的最小成本手段
- 或者更激进：取消 checkbox，改为"每季度 1 次社区投票：哪些劳动类型免 NT"——把"什么不算钱"变成社区集体决策，而非个人 checkbox
