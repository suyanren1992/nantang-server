# U-1 一营勘察回执 · 硬重置后全貌页数据消失案

> 派工：丞相 U-1（砚仁督办）
> 施工：Claude Code（一营，只读勘察）
> 案情：硬重置后全貌页面内容被清除，全貌页卡片消失

## ① 硬重置触发了什么清理路径？清了哪层？

### 触发入口

**admin 测试台硬重置** → `devReset('hard')` [core.js:1304](nantang-mobile/js/core.js#L1304)

### 清理链路（三层全清）

| 层 | 清理动作 | 锚点 |
|----|---------|------|
| **服务端** | `POST /api/admin/dev-reset?mode=hard` → 清空全部 DB 数据（用户/任务/营地/MapLocation 等） | [api.js:183](nantang-mobile/js/api.js#L183) |
| **localStorage** | `localStorage.clear()` → 清空 `nt_app_v2_shared`/`nt_local_users`/`nt_local_roles` 等所有 key | [core.js:1310](nantang-mobile/js/core.js#L1310) |
| **内存 AppData** | `AppData._data = {}` + `AppData._currentUser = ''` + `AppData.init()` | [core.js:1312](nantang-mobile/js/core.js#L1312) |

### AppData.init() 的补救尝试

`AppData.init()` [app-data.js:11](nantang-mobile/js/app-data.js#L11) 在 `_data = {}` 之后：
1. `_load('nt_app_v2_shared')` → `null`（localStorage 已清）
2. 补默认值：`map_locations = { buildings: [], plots: [], accommodations: {}, ... }` [app-data.js:33](nantang-mobile/js/app-data.js#L33)
3. `_seedIfEmpty()` → 补种子数据（住宿 6 间/田地 5 区/配置参数） [app-data.js:262-297](nantang-mobile/js/app-data.js#L262-L297)
4. **但 `map_locations.buildings` 始终为空** —— `_seedIfEmpty` 不补 buildings

### 结论

清了三层（服务端/lStorage/内存），`AppData.init()` 试图补救但只补了 accommodations/plots/config，**未补 buildings**。随后 sync_all 的破坏性覆盖（见 ③）又清掉了补救的数据。

## ② 全貌页卡片的数据真源——服务端还是本地？若是双源，谁覆盖谁？

### 数据流全链

```
renderContent()                       [app.js:189]
  → getBuildings()                    [app.js:29]
    → Game.getData()                  [core.js:98]
      → AppData._data.map_locations   [app-data.js:33]
```

### 双源对撞

| 源 | 写入时机 | 写入方式 |
|----|---------|---------|
| **本地种子** | `AppData.init()` → `_seedIfEmpty()` | 设置 `map_locations.accommodations/plots/config/state` |
| **服务端 sync** | `enterVillage()` → `API.syncAll()` → `_mergeSyncData()` | **全量覆盖** `AppData._data.map_locations = data.map_locations` |

### 覆盖逻辑（致命）

[core.js:973-975](nantang-mobile/js/core.js#L973-L975)：
```javascript
if (data.map_locations && window.AppData) {
    AppData._data.map_locations = data.map_locations;
}
```

**`data.map_locations = {}`（服务端空响应）在 JavaScript 中是 truthy** → 条件通过 → 全量覆盖。

服务端返回 [data.py:499-500](server/routes/data.py#L499-L500)：
```python
ml_r = (await db.execute(select(MapLocation).where(MapLocation.key == "shared"))).scalar_one_or_none()
map_locations = _safe_json(ml_r.data) if ml_r else {}
```
硬重置后 DB 空 → `ml_r` 为 None → `map_locations = {}`。

### 结论

**双源，服务端无条件覆盖本地。** 服务端返回 `{}`（空对象）时，客户端的 truthy 检查未拦截，导致本地种子数据被空对象全量覆盖。

## ③ 重置后为什么不重拉/重渲染？断在哪一环？

### 时序追踪

```
enterVillage()  [core.js:991]
  ├─ 1. refreshUserUI()             [core.js:1021] — 首次渲染
  ├─ 2. _initMap() → goTo(4)        [app.js:2654] — 渲染地图全貌页
  │     → render() → renderContent()
  │     → getBuildings() → HARDCODED_BUILDINGS (fallback) ✅
  │     → _refreshTopBar()           [app.js:2660]
  │         → AppData._data.map_locations.accommodations → ✅ (seed 数据还在)
  └─ 3. API.syncAll() → 异步回调    [core.js:1025]
        → _mergeSyncData(data)       [core.js:927]
          → data.map_locations = {} (服务端空对象)
          → AppData._data.map_locations = {} ⚡ COVERS SEED
```

### 断裂点

**`_mergeSyncData` [core.js:973-975](nantang-mobile/js/core.js#L973-L975)**：用服务端空对象 `{}` 全量覆盖了 `AppData._data.map_locations`。

**重拉发生了**（syncAll 调了），**重渲染也发生了**（renderContent 跑了的），但渲染时读的是**被覆盖后的空数据源**。

### 用户可见症状

| 数据 | 覆盖前 | 覆盖后 |
|------|--------|--------|
| 建筑卡片 | HARDCODED_BUILDINGS ✅ | HARDCODED_BUILDINGS ✅（fallback 幸存） |
| 住宿信息 | 6 间房种子数据 | `{}` — 空 |
| 田地数据 | 5 区种子数据 | `{}` — 空 |
| 房间动态 | `_getRoomLiveData()` 从种子渲染 | `undefined` — 不渲染 |
| 顶栏统计 | 住宿人数/在场人数/待领任务 | 全 0 |
| dirtyness | `AppData._data.cleaning`（独立存储） | **幸存**（未受 map_locations 覆盖影响） |

### 为什么 building 卡片本身没消失

`getBuildings()` [app.js:29-36](nantang-mobile/js/app.js#L29-L36) 有三层保护：
1. 优先从 `AppData._data.map_locations.buildings` 读
2. 无 → 返回 `HARDCODED_BUILDINGS`（硬编码 fallback）
3. 即使 `map_locations = {}`，`{}.buildings` = `undefined` → falsy → 触发 fallback

**但 rooms 内的动态内容（住宿/在场/物品）全部来自 `AppData._data.map_locations`，这些因覆盖而消失。**

## ④ 是否 AppData 双轨制的活标本？若是，记入统一战教材

### 判定：是。这是双轨制最纯粹的活标本。

**双轨**：
- **本地轨**：`AppData.init()` → `_seedIfEmpty()` → `localStorage nt_app_v2_shared`
- **服务端轨**：`API.syncAll()` → 服务端 `MapLocation(key="shared")` → `_mergeSyncData()` → 全量覆盖

**无合并逻辑**：两条轨之间没有任何差异合并、字段级覆盖、或时间戳比较。`_mergeSyncData` 的行为是**无条件全量赋值**（`AppData._data.map_locations = data.map_locations`），等于「服务端说什么就是什么」。

**而当服务端说「什么都没有」（`{}`）时，客户端也照单全收，丢弃了本地的一切。**

### 同类双轨覆盖点（同一次 sync 回调中）

| 数据 | 覆盖锚点 | 覆盖方式 |
|------|---------|---------|
| `map_locations` | [core.js:974](nantang-mobile/js/core.js#L974) | 全量覆盖 |
| `tasks` | [core.js:934-943](nantang-mobile/js/core.js#L934-L943) | 逐条 merge（**安全**） |
| `journal` | [core.js:944-951](nantang-mobile/js/core.js#L944-L951) | 去重追加（**安全**） |
| `presence` | [core.js:980-981](nantang-mobile/js/core.js#L980-L981) | 全量覆盖 |
| `pendingConfigChanges` | [core.js:984-985](nantang-mobile/js/core.js#L984-L985) | 全量覆盖 |

**tasks 和 journal 是安全的 merge 模式，map_locations 和 presence 是不安全的覆盖模式。** 统一战应记录这种差异。

## 附评：同一勘察中顺记的其他问题

1. **`_seedIfEmpty` 不补 buildings** [app-data.js:262](nantang-mobile/js/app-data.js#L262)：种子数据补了 accommodations/plots/config/state/camps/canteenMenu，唯独漏了 buildings。虽因 HARDCODED_BUILDINGS fallback 未造成严重问题，但属不完整初始化。

2. **`getPlots()` 的 fallback 链脆于 `getBuildings()`** [app.js:37-44](nantang-mobile/js/app.js#L37-L44)：依赖 `getBuildings().find({id:'field'})` — 若 HARDCODED_BUILDINGS 的 field 条被修改，plots 会丢失。不如直接维护独立的 `HARDCODED_PLOTS` 常量。

3. **`enterVillage()` 的渲染和 sync 无顺序保证** [core.js:1021-1027](nantang-mobile/js/core.js#L1021-L1027)：`refreshUserUI()`（同步）+ `API.syncAll()`（异步）之间无 barrier → 用户可能先看到种子数据再看到空数据 → 「闪烁」体验。

## 太傅注（三行）

- **`{}` 是 truthy**：JavaScript 中 `if ({})` 为真，空对象不等于 falsy。`if (data.map_locations && ...)` 在服务端返回 `{}` 时仍然通过——这是本案根源。
- **全量覆盖 vs 合并**：`a = b` 无论 b 是什么都照单全收。`merge(a, b)` 只更新 b 有的字段。sync 时应区分「服务端权威」（如 tasks.journal）和「混合源」（如 map_locations，本地有结构、服务端有动态值）。
- **双轨制不怕有两条轨，怕的是两条轨互踩无规则**。本案中的 `_mergeSyncData` 对 map_locations 是无条件覆盖（踩），对 tasks 是逐条 merge（不踩）——同一函数内两种行为，教材应记这个差异。
