## 一、前端现状（选型的硬约束）

grep 实证的架构事实——决定了选型不能照搬「现代前端」教科书：

| 事实 | 实证 | 对测试的影响 |
|------|------|-------------|
| **无构建工具/无 package.json** | `nantang-mobile/` 根目录无 package.json、无 node_modules、无 webpack/vite 配置 | 不能假设有打包/转译；引入测试需从零建 npm 工程 |
| **纯全局脚本，非 ES Module** | `api.js` 等 18 文件 grep `export/import/require` 全零命中；`index.html:520-537` 18 个 `<script src>` 顺序加载 | 无法 `import { fn }`；测试须靠「全局对象注入」或「整文件 eval 到 jsdom window」 |
| **强依赖 window/DOM 全局** | `app.js` 遍地 `window.App / window.AppData / AppData._data`；`api.js` 用 `fetch`+内存 token | 纯 Node 跑不起来，需 jsdom 或浏览器环境 |
| **单体巨文件** | `core.js` 141KB、`app.js` 200KB、`ui-camp.js` 85KB | 函数间强耦合，单元测试隔离成本高；宜先攻可隔离的纯函数+关键流程 |
| **少量纯函数孤岛可测** | `utils.js` Clock/`_p2`/`_shift`（9KB，逻辑内聚）；`api.js` 的路径拼接逻辑 | 这些是「低成本高回报」首批单测目标 |
| **加载顺序即依赖顺序** | index.html script 顺序：utils→mobile-bundle→nt→auth→...→app | 集成测试须按此顺序注入，否则 ReferenceError |

**结论**：南塘前端是「legacy 全局脚本 + DOM 重耦合」形态。选型核心矛盾＝**测试价值 vs 接入成本**。三条路线（下节）本质是「投入多少改造成本换多少覆盖」。

## 二、选型三方案（成本/覆盖对照）

### 方案 A：Node + jsdom 轻量单测（🟢 低成本）

- **工具**：`node --test`（Node 内置，v24 已具）或 Vitest + jsdom；仅测**可隔离的纯函数**。
- **做法**：把 `utils.js`（Clock 时区/日期）、`api.js` 路径拼接、`data.js` BRANCH_TITLES 阈值等「无 DOM 依赖」逻辑，用 `vm`/eval 载入 jsdom window 后断言。
- **覆盖**：纯逻辑单元（时间/称号/金额格式化/路径拼接），约占代码 15%。
- **成本**：🟢 低——建 package.json + 1 依赖（jsdom）；不碰业务代码；CI 可接 deploy_check 同款门。
- **回报**：立竿见影守住「工具函数被误改」，但**碰不到交互流程**（登录/发任务/结算 UI）。

### 方案 B：Playwright 端到端（🟡 中成本，⭐ 推荐核心）

- **工具**：Playwright（自带浏览器，无需真设备），跑真 `index.html` + 真后端（或 mock fetch）。
- **做法**：起本地 uvicorn（复用 `server/` + SQLite 临时库，同 pytest conftest 思路）→ Playwright 开页 → 脚本走「注册→登录→发任务→认领→提交→审核→结算」核心路径 → 断言 DOM/余额。
- **覆盖**：**真实用户路径**（下节清单），端到端含前后端联调，最贴近「219ce8b 类整页 parse 死」这种冒烟漏网的病。
- **成本**：🟡 中——建 npm 工程 + Playwright；需起后端；首批脚本约 6-8 条核心路径。
- **回报**：最高。补上「pytest 管后端、冒烟只验 HTTP 200」之间的**前端交互黑洞**，与 S-2 API 契约机检形成「静态契约 + 动态跑通」双保险。

### 方案 C：Jest + jsdom 组件级（🔴 高成本，不推荐）

- **做法**：为单体巨文件做 DOM 挂载 + 交互模拟的组件测试。
- **成本**：🔴 高——core.js/app.js 强耦合，mock 依赖链极长，投入产出比差。
- **判定**：现阶段**不推荐**。待前端做模块化重构（远期）后再议。

## 三、最小核心路径清单（供 B 方案首批脚本）

按「爆炸半径 × 涉钱」优先级排序，建议首批 8 条：

| # | 路径 | 涉及前端文件 | 涉及后端端点 | 优先级 |
|---|------|-------------|-------------|--------|
| 1 | 注册→登录→进村口页 | auth.js / index.html | POST /api/auth/register·login | P0（入口） |
| 2 | 登录失败限速锁定→解封 | auth.js | POST /api/auth/login（P1-2 已修） | P0（安全） |
| 3 | 发任务→认领→提交→审核→结算 | nt.js / ui-cardroom.js | /api/nt/tasks/*、/api/tasks | P0（涉钱主链） |
| 4 | NT 转账 + 余额刷新 | api.js / core.js | POST /api/nt/transfer | P0（涉钱） |
| 5 | 提现申请→admin confirm（一次成功） | api.js / 管理面板 | /api/nt/withdraw·/api/admin/withdraw/confirm（P0-1 行锁） | P0（涉钱禁区） |
| 6 | 住宿 checkin→checkout 结算 | app.js | /api/accommodation/* | P1 |
| 7 | 公约签署首签发 NT（幂等） | app.js | POST /api/covenant/sign | P1 |
| 8 | 全貌页整页加载无 JS 报错（防 219ce8b） | 全部 18 js | —（纯前端 parse） | P0（回归门） |

> 第 8 条是「整页冒烟」——Playwright 开页监听 `page.on('pageerror')`，任一未捕获 JS 异常即 FAIL。这正是 219ce8b `};}` 语法错的动态兜底（T-1 是静态 node --check，本条是运行时二道门）。

## 四、二营建议（呈裁）

1. **推荐 A + B 组合分两步走**：
   - **第一步（本波次可落）**：方案 A 轻量单测，锁 utils.js/api.js 纯逻辑——成本最低，先建起 npm 测试工程骨架。
   - **第二步（呈裁后另开卡）**：方案 B Playwright 攻上表 8 条核心路径——这是补前端交互黑洞的主力。
2. **工程落点建议**：新建 `nantang-mobile/tests/`（或仓根 `frontend-tests/`），独立 package.json，不污染现有零构建结构；CI 接入 deploy_check 或独立 npm script。
3. **禁区纪律**：测试代码只读引用业务 js，不改一营阵地源码。若测试暴露前端 bug，如实列出移交制卡（同 S-2 口径）。
4. **待丞相裁定项**：
   - ① A/B 是否分两卡、先做哪个？
   - ② 工程落点放 `nantang-mobile/tests/`（一营阵地内）还是仓根独立目录？涉及归属营。
   - ③ Playwright 起后端方式：真 uvicorn+SQLite 临时库 vs 纯 mock fetch？
