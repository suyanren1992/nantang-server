# K-2 · PG 集成测试：行锁静默失效修复

- **档位**：中卡（四步直道+影响面声明）
- **阵地**：二营（Codex）施工 · 一营（Claude Code）验收
- **来源**：K-1 补课审计硬伤 8——`server/tests/conftest.py:17` 写死 SQLite，29 处 `with_for_update()` 在 SQLite 下静默失效，锁路径从未被 PG 真实验证
- **定档人**：太傅（Claude Code）· 2026-07-26

## 施工内容（三步）

1. **conftest.py 加方言告警**：如果 `engine.dialect.name == "sqlite"`，在测试启动时打印 WARNING"锁相关测试在 SQLite 下不验证 FOR UPDATE 语义，锁序/漏锁需 PG 集成测试验证"
2. **锁相关测试加 skipIf 标记**：`test_nt_camps.py` 中 D-5 并发提现测试、`test_e2e_smoke.py` 中资金闭环锁路径——添加 `@pytest.mark.skipif(engine.dialect.name == "sqlite", reason="FOR UPDATE not supported by SQLite")`
3. **新增 PG 集成测试**（`server/tests/test_pg_locks.py`）：
   - 用 Neon dev 分支（`neon branches create --name lock-test`）或 Docker testcontainers 跑真实 PostgreSQL
   - 最少测 3 条锁路径：提现并发双扣（D-5）/ populate_existing 漏锁（D-17）/ 住宿费日结行锁（D-26）
   - 每条：2 个并发请求同时打 → 断言只有 1 个成功修改 + 最终余额正确
   - 测试可跳过（`pytest.mark.skipif` 无 PG 连接串时跳过），不阻塞 CI

## 铁律

- 不改业务代码。PG 集成测试只验证「已有的 `with_for_update()` 在 PostgreSQL 下真的生效」
- 若测试揭示锁序错/漏锁——只记录不修，发新卡（K-3）

## 判据（验收方实跑）

1. `pytest tests/ -v` SQLite 下 conftest 打印 WARNING 日志（贴输出）
2. 锁相关测试 SQLite 下标记为 skipped（贴 skip 摘要）
3. PG 测试（有 PG 连接串时）`test_pg_locks.py` 三条锁路径全绿，并发断言「只有 1 个成功」

## 影响面声明

- 纯测试代码改动 + 新增 1 个测试文件
- 不改 server/routes/ 业务代码
- SQLite 下现有 22 条测试行为不变（仅加 WARNING 日志 + skip 标记）
- 回滚=删 `test_pg_locks.py` + 还原 conftest.py

> **太傅注**：对应补课 `26`（测试——闭环保真） + `17`（验收——不听说完成，看实证）。
> 人话原理：SQLite 下跑通的锁测试跟没跑一样——测试环境和生产环境用了不同的数据库引擎，相当于在沙地上试刹车然后说能在冰面上停住。
