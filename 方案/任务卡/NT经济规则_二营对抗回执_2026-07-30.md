## Q1【结算模式对抗】❌ 必须修改 — 否决 A 链上 P2P，选 B 内部即时托管

A 的 txHash 匹配攻击面对 50 人小社区完全不成比例：
1. **重放**：同一 txHash 二次录入解第二个冻结——除非建 used_tx_hash 唯一约束+行锁，否则必被刷。
2. **金额拆分/聚合**：统一结算一笔转账解多冻结（v0 Q2 未定），"按收款人+总额匹配"给攻击者构造空间——多转 1 NT 或凑单解本不该解的冻结。
3. **假转账**：无自建索引器时只能信用户填的 txHash，链上"存在且金额对"≠"这笔是给这个任务的"，备注字段可伪造。
4. **地址绑定**：换钱包地址、共用地址、内部转账伪装，都能骗过"双方地址匹配"。
5. A 依赖 RPC/索引器（v0 自评"开发量大"），是外部可用性依赖——链拥堵/RPC 挂=结算全线卡死。

B 内部托管风险可控且已是现状：托管池超发/双花已由 D-17 锁型（with_for_update+populate_existing）+ 金额服务端取 + 同事务提交 + 会计等式兜住。v2 已选 B（EscrowPool），正确。

**修改建议**：v0 链上 P2P 结算降级为远期蓝图（与 v2 附录 A 口径一致）；txHash 仅用于"出系统"的钱（提现/充值确认）审计回写（v2 §7.2），不作为任务解冻的信任根。删除 v0 §二"解冻=链上记录确认"作为主路径。

## Q2【等式漏洞】⚠️ 有疑虑 — 扣到托管池更难做平但更安全，须配 escrow 明细交叉校验

**两种记法等式形式**：
- 冻结不转账（v0 §二.1）：钱留发布者余额标 frozen，available = balance - frozen。等式：total_issued = Σbalance（frozen 是 balance 子集，不进等式）。
- 扣到托管池（v2 EscrowPool）：balance -= r，escrow += r。等式：total_issued = Σbalance + escrow + …（现况 nt.py:505 即此型）。

**扣到托管池更难做平**——多一个可变项 escrow，任何"扣 balance 未加 escrow"或"释放 escrow 未加收款人 balance"的半事务都会破裂；但正因显式记账、破裂立即被 verify 抓到，反而更安全。冻结不转账"看似"简单，但 available 是派生量不入等式，frozen 累加/释放错误等式照样平——错误被隐藏，双花直到提现才暴露，是更危险的"假平"。

**各自破裂序列**：
- 扣托管池：①balance -= r 后异常回滚不彻底→escrow 未加，钱凭空消失；②并发两请求同读 escrow 旧值（无 populate_existing）→后写覆盖前写；③释放时加错收款人。
- 冻结不转账：①frozen 累加超过 balance→available 负数但等式仍平；②并发冻结同一余额（无行锁）→frozen 双计或双花；③任务取消漏减 frozen→永久锁死用户资金，等式无感。

**修改建议**：确认采用 v2 扣托管池型（现况已是）。补两点：(1) EscrowPool 释放/退回必须池行+收款方行双锁（沿 _grant_from_pool 锁型）；(2) 新增 escrow 与"未结任务托管明细求和"的交叉校验（类比 camp_pool_drift），把 escrow 从"信任单值"升级为"账本可推导值"，堵住半事务假平。

## Q3【并发与锁】❌ 必须修改 — 拆 4 表+CampLedger 必须先定全局锁序，否则死锁

v2 §二把单表拆成四单例 + N 行 CampLedger，跨表事务从"锁一行"变"锁多行多表"，不定锁序必死锁。现况单表天然无死锁（只有一行），这是拆表引入的新增风险，v2 完全未提锁序。

**可能同时被锁的并发场景**：
1. 营队任务审核通过（CampLedger.escrow→User.nt_balance）× 结营结算并发（CampLedger.balance→OperatingPool）→ 同锁 CampLedger + OperatingPool，方向可能相反。
2. 每日 cron 盈余划拨（OperatingPool→ReservePool）× 自动调水（ReservePool→OperatingPool）→ 两池互锁，经典 AB-BA 死锁。
3. cron 补填/调水 × 提现申请（FrozenPool + ReservePool 等额扣，v2 §5.4）→ ReservePool 被两路争抢。
4. 多营并发结营 → 多 CampLedger 行 + 同一 OperatingPool。

**修改建议**：
1. 定死全局锁序（写入设计稿硬约束）：`OperatingPool → EscrowPool → ReservePool → FrozenPool → CampLedger(按 camp_id 升序)`，所有涉钱事务一律按此序 acquire，禁止逆序。
2. cron 的盈余划拨/自动调水串行执行（同一事务或加互斥），杜绝两池互锁。
3. 多营结算按 camp_id 升序循环加锁。
4. 所有 with_for_update() 加 populate_existing（拆表后每行都要），并设锁超时（Postgres lock_timeout）。
5. 补一条 S-1 锁测：模拟场景 1/2 的 AB-BA 并发（requires_pg 门控），证明锁序生效。

## Q4【迁移风险】❌ 必须修改 — 迁移须单事务原子+前后等式对拍+全量备份回滚

单表拆 4 表 + camp_balance 分摊到 CampLedger 是一次性不可逆结构变更，v2 §2.6 只给字段映射，未给原子性、分摊算法、回滚：

1. **中途崩溃**：拆到一半→等式两侧对不上，旧表已改，无干净状态可回。
2. **camp_balance 无法按营分摊**：现况 camp_balance 是单值汇总（models.py:101），不含营队维度明细。若无每营"已注资-已退回"账本流水，无法反推每营应得多少→分摊只能猜，必然破裂 camp.allocated 等式。
3. **contribution_pool 归属**：CV 磨损归集（CV 域），迁移映射到 OperatingPool.contribution_pool 正确，但绝不能计入 NT 等式——现况 verify 已正确排除，迁移后须保持排除。
4. **total_issued 锚点**：拆表后只应留在 OperatingPool 一处，多处冗余=多处不一致。

**回滚方案设计**：
1. 迁移全程单事务（Postgres DDL+DML 尽量同事务；SQLite 先全库文件级备份）。
2. 迁移前跑 verify 存快照（各池值+total_issued+diff），迁移后立即重跑 verify 对拍，diff≠0 直接 ROLLBACK。
3. camp_balance 分摊前置校验：若现有账本流水无法逐营还原，先从 NTLedger camp_pool 明细按 camp_id 重建每营 CampLedger 初始账本，重建 Σ 必须 == 旧 camp_balance，否则中止迁移。
4. 旧表保留只读快照（community_pool_backup）N 天，回滚=切读回旧表+还原备份。
5. 50 人规模建议停机窗口迁移（凌晨，禁涉钱写入）。

## Q5【大额熔断绕过】⚠️ 有疑虑 — 阈值方向对，但可绕过且 withdraw 500 偏严、earn 50000 偏松

**绕过路径**：
1. 拆多笔：earn 日累计 50000 若按"单用户日累计"，admin 给 A 发 5 万后给 B 发 5 万，总发放无天花板——只拦单用户不拦系统总量。
2. 跨零点边界：23:59 一笔 + 00:01 一笔，日累计清零→两日内实际翻倍。自然日窗口必被利用。
3. 多 admin 账号：熔断按操作者计则每人一份额度；按收款人计才有效。
4. withdraw 单用户日 500 可被多账号分散提现绕过（信誉≥60+7 天冷却部分缓解）。

**阈值合理性**：50 人社区，earn 日累计 50000 偏松（人均千元级，够刷穿运营池）；withdraw 单用户日 500 与提现门槛 50-200 NT 尚协调；topup 100000 对 admin 手动是合理上限。

**修改建议**：
1. 熔断双维度：既拦"单用户日累计"，也拦"系统单日总发放"（earn 全局日上限，如 20000）。
2. 时间窗改滚动 24h，或明确自然日+跨零点告警。
3. earn/topup 熔断按操作 admin + 收款用户双计，多 admin 不放大额度；关键操作留双人复核（可后置）。
4. earn 日阈值下调至与运营池规模匹配（建议 ≤ 运营池日均补填×N），并接入 §7.5 异常告警（运营池 1h 下降>50%）。

## Q6【最不认同】❌ v0 §二"链上转账记录查到才解冻"作为主结算路径

全案最危险的设计。把任务闭环的信任根挂在外部链+用户手填 txHash 上，攻击面（Q1）对 50 人社区收益全为负；引入 RPC/索引器外部可用性依赖，链故障=结算瘫痪。更矛盾的是 v2 附录 A 砚仁已裁定"维持即时结算+社区池实持"，v0 链上 P2P 与 v2 即时托管直接冲突，不明确否决则施工方两头摇摆。

**替代方案**：任务结算走 v2 内部即时托管（EscrowPool），txHash 仅用于"出系统"的钱审计回写。v0 §二整节标注"降级为远期蓝图，本期不施工"。

## Q7【最认同】✅ v2 §七的自动对账（§7.1）+ 等式 diff 最高优先级告警（§7.5）

把现况被动的 GET /verify（要人手调）升级为每日 cron 主动对账 + 破裂即告警 + 断裂快照，是涉钱系统最后一道兜底。砚仁 21:19 实证的"会计等式不成立×4 + 池=0"正是因为没有主动对账才积压到线上。有了 §7.1+§7.5，任何半事务/双花/迁移破裂 24h 内被 diff>0 抓到并留快照。不阻止 bug 发生，但保证 bug 无处藏身——与二营"会计等式守恒"铁律同频，成本低收益最高，应列 P0（v2 已列，赞同）。

**加强建议**：对账不止每日，关键涉钱写入路径（earn/transfer/withdraw 确认）事务提交后即时轻量校验 diff，破裂立即回滚+告警，把发现窗口从 24h 压到秒级。

## 太傅注（三行）

1. 结论倾向：否决 v0 链上 P2P 主结算，全案收敛到 v2 即时托管+txHash 仅审计；这是资金安全与工程可行性的唯一自洽解。
2. 拆 4 表最大真实风险不在功能而在并发锁序（Q3）与迁移原子性（Q4）——这两项无硬约束就别开工，须先出锁序规范+迁移回滚脚本+对拍测试。
3. 熔断（Q5）方向对但单维度可绕，须补系统总量维度+滚动窗口+多 admin 计额；等式交叉校验（Q2 escrow drift）应作为拆表的验收硬门槛。
