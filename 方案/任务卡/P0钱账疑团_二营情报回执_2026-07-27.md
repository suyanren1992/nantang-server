## 疑团①：任务双重创建（T1/T2）

### 1. 涉及文件（路径:行号）
- `nantang-mobile/js/core.js:683-721`（`doPublish()`）
- `nantang-mobile/js/core.js:722-748`（`publishDraft()`）
- `nantang-mobile/js/app-data.js:118-133`（`AppData.addTask`）
- `nantang-mobile/js/api.js:139-148`（`API.syncTask`）
- `server/routes/tasks.py:84-132`（`POST /api/tasks` = `create_task`）
- `server/routes/tasks.py:42-43`（`_task_id()` 生成器）
- `nantang-mobile/js/core.js:933-939`（`_mergeSyncData` 任务去重逻辑）
- `nantang-mobile/js/core.js:431-433`（`renderTaskCard` 渲染 `esc(t.name)`）

### 2. 归因分类
🔴 现有功能坏（bug）——HTTP 在线模式下**同一次发布向服务端 POST 两次**，服务端建两条任务、冻结两份 NT。

### 3. 证据链（锚点 → 推论）
**事实 A（双写第一发）**：`doPublish()` 第一步调 `AppData.addTask(data)`（core.js:695）。
`addTask` 内部（app-data.js:125-131）判断 `API.token` 存在时，**自己就调了一次** `API.syncTask(task, cb)`（app-data.js:127）。→ 这是第 1 次 `POST /api/tasks`。

**事实 B（双写第二发）**：回到 `doPublish()` 的 HTTP 分支（core.js:710-719），代码**又调了一次** `API.syncTask(data, cb)`（core.js:712）。→ 这是第 2 次 `POST /api/tasks`。

**事实 C（服务端每次都扣款冻结）**：`create_task`（tasks.py:84-132）每收到一次 POST，就 `nt_balance -= reward*slots`（tasks.py:124）+ `task_escrow += reward*slots`（tasks.py:126）+ 写一条 escrow 冻结流水（tasks.py:130）。两次 POST = 两次扣款。

**推论 1（T2 扣款数额对得上）**：发 1 个奖励 1NT 的任务，两次 POST 各冻结 1NT，合计扣 2NT，余额 5→3。**与砚仁实测「扣 2NT」完全吻合**——每次各托管 1NT，正是双写。

**事实 D（服务端 id 带 hex 尾号）**：`_task_id()`（tasks.py:43）= `"T" + 年月日时分秒 + "-" + secrets.token_hex(3)`，尾号是 6 位十六进制（如 `...-a1fc2d`），可含 `fc`。→ 「FC 尾号」即服务端任务 id 的 hex 尾段。

**事实 E（乱码任务的名字来源）**：`_mergeSyncData` 处理服务端回传任务时，若本地去重未命中（`!dup`），新建本地条目用 **`name: t.id`**（core.js:937）——即把服务端 id 当成任务名。而任务卡渲染的正是 `esc(t.name)`（core.js:433）。→ 这就是「乱码 FC 尾号任务」的 id/名字渲染出处：本地条目的 `name` 字段被塞进了服务端 `T...-xxfc` 形式的 id。

**推论 2（T1 一个变俩 + 乱码）**：两次 POST 产生两个不同的服务端 id（srvId_A、srvId_B）。
- `addTask` 的回调（app-data.js:128）把任务对象额外挂到 `tasks[srvId_A]` 键；`doPublish` 回调（core.js:714-715）又 `updateTask` 本地 `tasks[标题]` 键。→ 本地 `TASKS` 立刻出现**两个键指向同一发布**（标题键 + srvId_A 键），大厅 `Object.values(TASKS)` 遍历即渲染出「2 个」。
- 下一次全量 `sync` 回传两条服务端任务，去重键为 `title===t.title && publisher===t.poster`（core.js:935）。当 `publisher`（本地存 `CURRENT_USER` 显示名）与服务端 `t.poster`（`user.id`）不一致、或去重对已被改键的条目失配时，第二条走 `!dup` 新建分支（core.js:937），`name=t.id` → **渲染出带 FC 尾号的乱码任务**。

### 4. 影响面初判
- 每次在线发布：**服务端多建 1 条任务 + 多冻结 1 份 NT**（金额随 reward×slots 放大，非固定 1NT）。
- 用户余额被超额冻结，任务大厅出现重复卡 + 乱码卡。
- `publishDraft()`（core.js:722-748）路径**不叠加此双写**：它自己只调一次 `API.syncTask`（core.js:730），且**不经过 `AppData.addTask`**（草稿早已在 `TASKS` 里）。但注意——它调 `_finalizePublish` → `AppData.updateTask`（core.js:752），`updateTask` 在 HTTP 模式会 `syncTaskUpdate`（app-data.js:142），是 PUT 不是 POST，不重复建任务。**故 T1/T2 双重创建根因锁定在 `doPublish()` + `addTask` 的双 POST，publishDraft 无二次建单**。

### 5. 未明项
- 去重失配的确切触发条件（`CURRENT_USER` 显示名 与 服务端 `user.id` 是否相等）需在真机／seed 环境下打印二者比对确认；本报告只读代码，未跑运行时。
- 服务端是否有幂等/去重（同 title+poster 短时间内拒绝第二次）——`create_task`（tasks.py:84-132）**未见任何幂等键或重复校验**，倾向「无」，但未穷举中间件。

## 疑团②：余额数据源普查（T3）

### 1. 涉及文件（路径:行号）
- `nantang-mobile/js/core.js:1188-1208`（工作台/顶栏 `refreshUserUI` 余额）
- `nantang-mobile/js/core.js:1395,1398`（资料页 `renderProfile` view 余额）
- `nantang-mobile/js/core.js:1448-1450`（充值表单余额）

- `nantang-mobile/js/nt-core.js:64-69`（HTTP 模式清空本地 NT 存档）
- `nantang-mobile/js/nt-core.js:601`（`getUser` 读内存 USERS）
- `server/routes/nt.py:59-61`（`GET /api/nt/balance`）
- `server/routes/nt.py:93-175`（`GET /api/nt/sync` 全量）

### 2. 归因分类
🔴 多处余额不同源——**顶栏读服务端、资料页/充值/提现读本地内存 NT**，而本地 NT 在 HTTP 模式被主动清空。

### 3. 各显示点数据源（逐个列出）
| 显示位置 | 代码锚点 | 读的字段/来源 | HTTP 模式下取值 |
|---|---|---|---|
| 工作台顶栏 `.my-nt-val` / 个人卡 `#myNtBalance` / 进度条 | core.js:1191-1203 | 异步 `API.request('GET','/api/nt/balance')` → `srv.balance`（服务端权威） | **服务端 `users.nt_balance`**（如 3） |
| 顶栏 fallback（无 token 或 b=0 时） | core.js:1204-1208 | `NT.getUser(u).ntBalance`（本地内存 USERS） | 本地，HTTP 下多为 0 |
| 资料页（点头像）NT 余额 | core.js:1395,1398 | `NT.getUser(CURRENT_USER).ntBalance`（**仅本地**，不查服务端） | **0**（见下） |
| 充值表单顶部余额 | core.js:1448-1450 | 同上，本地 NT | 0 |
| 提现表单「可提现余额」+ 校验 | core.js:1474-1475 | 同上，本地 NT | 0 |

### 4. 证据链（锚点 → 推论）
**事实 A**：`_loadState`（nt-core.js:64-69）在非 `file:` 协议（即 HTTP）下**直接 `localStorage.removeItem(NT_STORE_KEY)` 并 return**，不加载任何本地 NT 数据 → 内存 `USERS` 为空。
**事实 B**：`getUser`（nt-core.js:601）= `USERS[userId] || null`。USERS 空 → 返回 null。
**推论（资料页显示 0）**：资料页 `NT.getUser(CURRENT_USER)||{}).ntBalance||0`（core.js:1395）→ null → 0。**这正是「资料页显示 0」的根因**：它从未调服务端，只读被清空的本地 NT。
**事实 C**：顶栏 `refreshUserUI` 有 token 时走 `GET /api/nt/balance`（core.js:1195），该端点直接返回 `user.nt_balance`（nt.py:60-61）。**推论**：这就是「另一处显示 3」的来源——服务端权威余额。

### 5. users.nt_balance 与 nt_ledger 的对账点
- **写侧**：扣款/加款直接改 `user.nt_balance`（如 tasks.py:124、nt.py 各处 `nt_balance -= / +=`），同时 `_add_ledger` 记流水（nt_helpers.py、tasks.py:130）。二者**分别写、无强约束**。
- **唯一对账点**：`server/routes/nt.py:395`（accounting 等式校验）`total_system = total_user_balance + pool.balance + pool.task_escrow + pool.camp_balance + reserve + frozen`，与 `total_issued` 比对。前端 NT 也有对应等式（nt-core.js:571-584）。
- **读侧无对账**：`GET /api/nt/balance`（nt.py:60）直读 `nt_balance` 字段，**不与 ledger 汇总核对**。→ 若双写 bug（疑团①）令 nt_balance 与 ledger 冻结流水不一致，读接口不会发现。

### 6. 影响面初判
资料页/充值/提现三处在 HTTP 模式恒显 0（或过期本地值），与顶栏服务端值割裂；用户据资料页 0 会误判无钱，据顶栏 3 又能操作，体验错乱。提现校验用本地 0 会**误拦所有提现**（core.js:1475 `amt>ntBal` 恒真）。

### 7. 未明项
- 顶栏 fallback（core.js:1204）在 `b===0` 且服务端真为 0 时是否会用本地覆盖显示，需运行时确认异步时序。
- 服务端 nt_balance 与 ledger 是否已因疑团①双写而失衡，需查 nt_ledger 实际流水对账（只读代码无法取运行数据，属 T2 待查）。

### 2. 归因分类
🔴 显示与账本不同源——**村口资金池卡读本地内存 `COMMUNITY_POOL`，而非服务端 `pool_balance`（500）**。

### 3. 证据链（锚点 → 推论）
**事实 A（服务端确为 500）**：dev-reset hard 建池 `balance=500`（admin.py:134）、soft 重置 `pool.balance=500`（admin.py:157）、dev-seed 补至 500（admin.py:271-280）。全量同步经 `sync_all` 把它作为 `pool_balance` 回传（data.py:482,508）。
**事实 B（前端把服务端值存进了另一个字段）**：`_mergeSyncData` 收到后写入 `AppData._data._poolBalance = data.pool_balance`（core.js:930-931）。
**事实 C（村口池卡读的是本地内存变量，不是 `_poolBalance`）**：`_renderPoolCard`（app.js:608）= `NT.getCommunityPool()`；`getCommunityPool`（nt-core.js:498）返回内存 `COMMUNITY_POOL`（nt-core.js:57）。**二者是两个不同的数据源，服务端 500 从未流入 `COMMUNITY_POOL`**。
**事实 D（本地 COMMUNITY_POOL 在 HTTP 模式初值 0）**：`_loadState` 在 HTTP 下不加载存档（nt-core.js:64-69），`COMMUNITY_POOL` 保持初始 `0`（nt-core.js:57）。
**推论（村口 50 = 本地自动补池残值，倾向）**：`_dailyPoolRefill`（app-data.js:633-648）在 `pool<500` 时执行 `NT.depositToCommunityPool(50)`（app-data.js:644），令本地 COMMUNITY_POOL `0→50`。该函数在有 `API.token` 时本应提前 return（app-data.js:637），但若曾在离线/`file:` 态或 token 未就绪时跑过一次，就会在本地留下 **恰好 50** 的残值。→ **村口显示 50 = 本地补池 +50 的残值，而非服务端 500**。
**对照旁证**：校核室的池提示读的是**正确的** `_poolBalance||999`（ui-cardroom.js:404），说明服务端值确实进了 `_poolBalance`，只是村口卡没用它。

### 4. 影响面初判
村口社区资金池金额恒错（显示本地 50 而非服务端 500），且「资金池详情点不开」——`_renderPoolCard` 只渲染静态卡（app.js:621-626），未见详情点击入口，入口缺失。

### 5. 未明项
- 「50」这一确切数值的产生时机（哪一次 `_dailyPoolRefill` 在有 token 前跑过）无法由静态代码确证，需运行时或 `_lastPoolRefill`/activity_log（app-data.js:645）实测佐证。列为未明，不硬猜。

## 太傅注（DeepSeek 教学 · 三行）
- 补课章节：《前端-服务端双写与幂等》《单一数据源（SSOT）原则》《乐观更新 vs 权威读》。
- 人话原理①（双写）：发一次任务点了两次"寄快递"——`addTask` 寄一次、`doPublish` 又寄一次，服务端当成两单各扣一份钱；修复方向是让"扣款建单"只走一个门（要么 addTask 内、要么 doPublish 里，不能都调）。
- 人话原理②（不同源）：同一个"余额/池子"数字，有的窗口问服务器、有的窗口问被清空的本地缓存，于是一个显 3/500、一个显 0/50——根子是"数字只从一个门出"没落到前端每个显示点。
