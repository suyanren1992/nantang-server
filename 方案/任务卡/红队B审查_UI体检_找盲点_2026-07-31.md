## 〇、扫描范围（5 类盲区）

| 维度 | 定义 | 扫描方法 |
|------|------|----------|
| **场景盲区** | 用户想做的事，UI 没有对应页面/入口 | 对照用户原话 → 真仓代码 grep |
| **路径盲区** | 有页面但走不通：入口→操作→反馈链路断裂 | 追踪关键操作点击路径（从入口到完成） |
| **角色盲区** | 5 种角色（visitor/npc/builder/admin/营地长）共用同一 UI，缺少角色专属视角 | 按角色遍历全部可见入口 |
| **数据盲区** | 数据已存在（app-data.js 字段/服务端表），但 UI 没有渲染 | 对照数据模型 → 现有 UI 渲染 |
| **文化盲区** | 违背「游戏照进现实 / 卡片化 / 进度条 / 上下贯通」产品哲学 | 逐条对照哲学原话 → 现有表达 |

## 一、P0 盲点（阻塞体验，不出则关键路径断裂）

### P0-1 · 楚门展示层缺失——云村民看不到"村正在发生什么"

**场景描述**：
砚仁原话「楚门的世界」——云村民（visitor）打开 App 应该像打开一面窗户，看到实景村庄的实时动态：谁在田里、谁在扫地、刚刚发生了什么、现在天气怎样。目前 App 打开后是建筑列表 + 翻牌区 + 时间线，但这三者是**独立模块**，没有形成"实景直播"的沉浸感。

**为何是盲点**：
- `_renderPresenceSection`（app.js:796）只做翻牌卡片网格，不做"此刻动态"
- `_renderTimelineSection`（app.js:725）只做事件时间线，不聚合"实时状态"
- `_renderAnnounceTicker`（app.js:280）有公告走马灯，但零数据、零样式效果
- **真正的楚门层 = 公告 + 动态 + 翻牌 + 天气 + 劳动快照 五合一实时面板**——没有

**影响面**：
- visitor 打开 App 看到的是静态建筑列表，与"实景游戏"定位断裂
- 现有翻牌机制依赖手动操作，缺少"被动观看"的愉悦感
- 没有"南塘此刻"就没有实景游戏的「在场感」

**建议落点**：
- 阶段 3 立卡 `E-TRUMAN-LAYER`：南塘此刻实时面板（公告走马灯 + 劳动快照 + 天气 + 在地人数）
- 复用 W6-UI-CARD-API 的 Card/StatusBadge 组件
- 数据源：现有 `announcements` + `presence` + `timeline` + `dirtiness` 已就绪，只差 UI 聚合层

### P0-2 · 空态/错误态/加载态——全站"三态"缺失是隐藏的 UX 杀手

**场景描述**：
现有 UI 32 处（grep `_render` 渲染函数），只有 4 处有空态占位（app.js:723-725 的 `empty` 字段），其余 28 处的空态是一片白或"什么都没有"。错误态更严重：API 失败时没有统一错误提示模式，部分页面静默失败。加载态只有 index.html 顶部的骨架屏（scrollSkeleton），但子页/浮层数据 loading 完全无感知。

**为何是盲点**：
- 空态是**教育用户的第一触点**——"还没有任务"和"点右下角➕创建你的第一个任务"是两种完全不同的体验
- 错误态是**信任的最后一公里**——用户报"点了没反应"（皇帝铁律 §提醒规范）大半是静默错误
- 加载态是**焦虑管理**——数据来了没有、还要等多久，用户不知道就是"卡了/坏了"

**真仓证据**：
```
app.js:723  empty: '还没有人在线，翻一下自己的牌吧~'     ← 仅 4 处有
app.js:724  empty: '🏕️ 暂无活跃营地'                    ← 其余 28+ 处全无
app.js:725  empty: '时间线还是空的——完成了校核后会出现在这里'
```
错误态/加载态：**全站 0 处统一处理**。`_openQuickSheet` 内部的表单提交用 `showToast` 提示成功，但失败路径未覆盖。

**影响面**：
- 新用户首屏看到空白时间线 → 以为 App 坏了，不会知道"要做校核才会出现"
- visitor 被权限门拦截 → 看到 `!userCan` 返回 false 后的静默失败，不知道"你需要先入住"
- 数据加载 3 秒无反馈 → 用户刷新建重试，导致重复请求

**建议落点**：
- 阶段 3 立卡 `UI-EMPTY-ERROR-LOADING`：三态统一组件（`UI.EmptyState` / `UI.ErrorState` / `UI.LoadingState`）
- 卡片化范式补充：Card 组件增加 `empty` / `error` / `loading` 三态 prop
- 与 W6-UI-CARD-API 同仓不改：新组件追加到 `ui-primitives.js`，用 `?v=2` bump
- 优先覆盖：时间线/营地/物品/任务 4 个最高频空态场景

### P0-3 · 角色专属仪表盘缺失——5 种身份看同一套 UI

**场景描述**：
砚仁原话「每个身份对应显示什么」——目前 5 种角色（visitor/npc/builder/admin/营地长）看到的 `subBar` + 顶部导航 + 工作台内容完全相同。唯一的差异化是 `_renderCovenantOverlay` 中 `role === 'admin'` 的一段（app.js:523），以及物品/打扫的权限门检查（app.js:2920/3071）。

**为何是盲点**：
- **visitor 视角**：打开 App 看到一堆操作入口（快速打扫/放取物品/农活记录），点了全被拒——体验是"你不配"。应该看到的是"你可以：入住 / 翻牌 / 浏览"。
- **npc（在地伙伴）视角**：日常高频 = 劳动录入 + 打扫 + 校核待办，但这些散在 app.js:1995-3083 各处，没有聚合为"在地伙伴工作台"。
- **admin 视角**：待校核队列 / 配置变更审批 / 公告发布 / 成员管理——目前全在代码逻辑里，**无独立管理面板**。
- **builder 视角**：营地贡献 / 提案进度 / 共建任务——零 UI。

**真仓证据**：
```
app.js:523     if (_me().role === 'admin')  ← 全站唯一角色分支 UI（公约覆盖页的一段）
app.js:2920    !userCan({role:...}, 'isMember')  ← 权限门只做拒绝，不做引导
app.js:3071    同上
app.js:723-725 卡片室三段（在地人员/活跃营地/时间线）——所有角色看到一样的内容
```

**影响面**：
- visitor 体验最差：到处被拒，无处可去
- 在地伙伴体验最碎：高频操作散落在 5+ 个入口
- admin 效率最低：没有管理面板，操作靠记忆/代码搜索

**建议落点**：
- 阶段 3 立卡 `UI-ROLE-DASHBOARD`：角色自适应工作台
  - visitor → 「云游南塘」：楚门层全景 + 入住引导 + 浏览权限
  - npc → 「在地工作台」：快捷劳动录入 + 打扫状态 + 校核待办
  - admin → 「管理中心」：待审批队列 + 公告发布 + 成员管理
  - builder → 「营地看板」：贡献进度 + 提案状态
- 复用 W6-UI-CARD-API 的 Card/TaskCard/StatusBadge

### P0-4 · 校核人视角完全缺失——劳动经济的"确认"环节无 UI

**场景描述**：
劳动流的核心是「提交→校核→结算」，校核是 NT 发放的最后闸口。当前：
- 提交人端 UI：`_openQuickSheet` 4 种快速表单（打扫/物品/农活/公约签署）
- 校核人端 UI：**不存在**。校核逻辑走 `/api/nt/verify` 接口，但确认/拒绝操作没有独立面板。
- 校核人不知道"有哪些待校核"——需要自己记住或等通知。

**为何是盲点**：
- 劳动定价 4+3 套分裂（W6-RECON 勘察），校核是唯一防错层——没有 UI 就靠人工记忆
- 砚仁原话「校核人视角」——用户已明确提出，说明真实场景中有校核人找不到入口的痛点
- 校核人得 15% NT 激励——没有"待校核队列"就没有激励效果

**真仓证据**：
```
app-data.js:26    pendingVerifications: []   ← 数据层已就绪
app.js:671        _renderCardVerifyRow()     ← 有渲染函数名但未 grep 到实际调用
```
卡片室有 `_renderCardVerifyRow`（app.js:671），但未被任何 section 引用——疑似死代码或半成品。

**影响面**：
- 校核人是劳动经济闭环的关键角色，没有 UI = 闭环断裂
- 提交人提交后看不到"有人在看我的提交"——信任感缺失
- 校核人错过待办 → 劳动 NT 延迟发放 → 提交人不信任系统

**建议落点**：
- 阶段 3 立卡 `UI-VERIFIER-DASHBOARD`：
  - 待校核队列（Card 列表，每张含提交人/劳动类型/时间/NT 金额）
  - 一键确认/拒绝（复用 StatusBadge + Card.onAction）
  - 校核历史 + 已赚取校核 NT 统计
- 后端已就绪：`pendingVerifications` 数据 + `/api/nt/verify` 端点

### P0-5 · "少点几步"未落地到具体度量——头等 UX 原则没有量化标准

**场景描述**：
皇帝 07-30 拍板「少点几步 = 头等 UX 指标」——但全站没有任何操作点击路径的度量。现有"快捷入口"（`_openQuickSheet` 4 种）散落在代码各处，没有集中入口，也没有度量"原来要点几步，现在减到几步"。

**为何是盲点**：
- 「少点几步」是原则，不是功能——需要先度量现状，再量化改善
- H 抽屉（设计系统底座 §三·H）已设计但未连接真实快捷操作
- 快速打扫的防刷代码（app.js:3083）已写，说明设计上想过"快捷"，但入口被埋

**真仓证据**：
```
app.js:3068   _openQuickSheet('🧹 快速打扫', body)   ← 入口触发路径不明确
app.js:1995   // ── 快速完成表单 ──                      ← 注释存在，函数散落
app.js:3025   _openQuickSheet('🌿 农活记录', body)     ← 同上
app.js:2954   _openQuickSheet('📦 放取物品', body)     ← 同上
```

**影响面**：
- 高频操作（打扫/录入/放物品）需要 3-5 步才能完成——每步都是流失
- 没有度量就没有优先级——应该先优化"用户最常用且步数最多的操作"
- H 抽屉只停留在设计稿，没有连上真实操作

**建议落点**：
- 阶段 3 立卡 `H-DRAWER-CONNECT`：将 H 抽屉连接现有 4 种 `_openQuickSheet`
- 增加埋点：每个快捷操作记录从"点击抽屉"到"提交成功"的步数和时间
- 目标：高频操作 ≤2 步（打开抽屉→选择操作→一键完成，if 无需额外参数）

## 二、P1 盲点（体验削弱，应在阶段 3 解决）

### P1-1 · 时间线/档案室/卡片室——三套信息架构未统一

**场景描述**：
同一份"村里发生的事"，有三个不同入口和三种不同的 UI：
- **时间线**（workspace timeline）：在卡片室第三段，列表式，W6-UI 已修字号
- **档案室**（archive）：app.js:2239 有代码引用但无独立页面（4 Tab 只完成 1-2）

三套视图的数据源重叠（都从 `interactions` / `verifications` / `discoveries` 读取），但 UI 分裂。

**真仓证据**：

app-data.js:28   discoveries: []         ← 校核制记录
app-data.js:29   cardDiscoveries: []     ← 卡片室发现

**建议落点**：阶段 3 立卡 `UI-INFO-ARCH-UNIFY`：统一信息架构——时间线/档案室/卡片室共享 Card 组件，用 filter/tab 区分视图。

## 三、P2 盲点（锦上添花，阶段 4+ 解决）

### P2-1 · 文化叙事层缺失——每栋建筑都有故事，UI 只展示了功能

**场景描述**：
大地书房曾是学校、敬字亭有焚烧字纸的文化传统、戏台每年有演出——这些"地方故事"完全不在 UI 中。App 当前展示的是功能数据（几层几间/干不干净/住了谁），而不是"这是一个有故事的地方"。

**为何是文化盲点**：
「游戏照进现实」= 现实空间 + 游戏化叙事。但如果 UI 只有功能没有故事，用户看到的就是"物业管理 App"而非"实景游戏"。建筑图卡片（P1-3）+ 地方志文案 + 用户产生的内容（翻牌/互动）= 叙事层。

**建议落点**：阶段 4 立卡 `E-NARRATIVE-LAYER`：每栋建筑的 Card 增加 `lore` 字段（一段 2-3 句话的故事），与建筑图卡片同卡出。

---

### P2-2 · 渐进式信息披露缺失——新用户被 30+ 建筑淹没

**场景描述**：
新人签署公约后进入全貌页——30+ 建筑/房间/田块一次性全部显示。没有任何"先看这个→再探索那个→解锁新区域"的渐进引导。现有新手引导（app.js:315 `_renderNewbieCard`）只是一个 check list，不做 UI 层的渐进解锁。

**建议落点**：阶段 4 立卡 `D-PROGRESSIVE-ONBOARDING`：新手首日只显示 3-5 个核心建筑（社区大厅/厨房/宿舍），完成引导任务后逐步解锁更多区域。

## 四、34 项体检清单的盲区维度梳理

将现有体检报告 34 项按 5 类盲区重新分类——哪些是"缺场景"、哪些是"断路径"、哪些是"少角色视角"：

| 盲区维度 | 匹配的体检项 | 盲区本质 |
|----------|-------------|----------|
| **场景盲区** | #1田间/#2大扫除/#5订餐/#6活动页/#11住宿 → 场景UI存在但不完整；#13厨房接龙/#14茶馆/#16拍卖/#17议事厅 → 零代码 | 用户想做的事，要么没页面，要么有页面但只是"代码在、UI没接" |
| **路径盲区** | #32快速填/#31大扫除集成 → 入口散乱；#15集市半成品 → 前端翻状态不落服务端；#21公告通知 → 数据层有 UI 不渲染 | 入口→操作→反馈链路中某一段断裂 |
| **角色盲区** | #8身份显示/#23个人页/#24顶部nav/#25角色降级/#26校核人视角 | 5 种角色共用 UI，缺少专属视角 |
| **数据盲区** | #22图卡片/#33档案室/#10"答案"→确认是档案室；#12宿舍订餐后端未做 | 数据/逻辑在 app-data.js 或后端，但 UI 层缺失 |
| **文化盲区** | #3建筑图卡片(视觉灵魂)/#9工作台(简陋)/#20赞赏样式(土老)/#27空态/#28加载态/#29移动端/#30暗色模式 | 产品哲学（游戏照进现实/卡片化/进度条）在 UI 中没有充分表达 |

**关键发现**：34 项中有 **19 项是路径盲区或角色盲区**（占 56%）——说明核心问题不是"没有代码"，而是**代码写了但用户走不到**（入口散/角色不对/路径断）。

## 五、跨模块一致性建议——8 模块共用 Card 范式的执行细节

阶段 1 已落 `<Card>` 通用组件，但 8 模块落地时需要统一以下细节，否则范式先行变成"各模块各写各的 Card"：

### 5.1 卡片尺寸统一

| 场景 | 推荐宽度 | 推荐高度 |
|------|---------|---------|
| 列表中的卡片（田间/住宿/活动） | `100%`（父容器宽） | 自适应内容，min 120px |
| 网格中的卡片（营地/物品） | `calc(50% - 4px)`（两列） | 固定 160px |
| 独立大卡片（TaskCard/Profile） | `100%` | 自适应，min 140px |

### 5.2 卡片状态机统一

所有 Card 必须支持以下 4 态（与 StatusBadge 4 态对齐）：

| 状态 | StatusBadge | Card 表现 |
|------|-------------|----------|
| 🟢 正常/可用 | `status:'green'` | 完整渲染，actions 可点击 |
| 🟡 警告/将满 | `status:'yellow'` | 完整渲染，border 橙色提示 |
| 🔴 异常/已满/锁定 | `status:'red'` | 完整渲染，actions 灰掉或替换为"不可用"文案 |
| ⚫ 离线/未激活 | `status:'offline'` | 灰度渲染，actions 隐藏 |

### 5.3 卡片数据契约

```js
// 所有 8 模块共用的 Card 数据契约（建议写入 ui-primitives.js 注释）
{
  id: string,           // 对象唯一 ID
  type: string,         // 'field'|'room'|'activity'|'camp'|'task'|'item'|'discovery'|'profile'
  icon: string,         // emoji 或 icon name
  name: string,         // 显示名称
  status: string,       // 'green'|'yellow'|'red'|'offline'
  subtitle: string,     // 副标题（位置/时间/数量）
  progress: { value, max, label },  // 可选进度
  actions: [{ action: string, label: string }]  // 动作列表
}
```

### 5.4 emoji 双轨执行标准

Icon 组件的 `name` prop：优先 emoji，特殊场景允许 icon 库回退。建议维护一个 `ICON_MAP`（在 ui-primitives.js 顶部），8 模块共用：

```js
// 营地/议事厅/田地等无通用 emoji 的场景 → icon 库回退
var ICON_MAP = {
  camp:     '🏕️',   // 营地 — emoji 可用
  assembly: '🏛️',   // 议事厅 — emoji 可用
  auction:  '⚖️',   // 拍卖 — emoji 凑合
  // 以下 emoji 表达不准，建议阶段 3 补 icon 库
  booking:  '📅',   // 预订 — 暂用 emoji
  verify:   '✅',   // 校核 — emoji 可用
};
```
