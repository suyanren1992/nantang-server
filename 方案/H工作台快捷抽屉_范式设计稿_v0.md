## 一、本范式要解决的痛（皇帝原话）

- "每次要快速输入东西都得打开全貌页多点几下"
- "对天天用的软件，这是劝退点"
- "少点几步 = 用户最大问题"
- "操作台非常重要"

**结论**：所有高频操作 → 工作台抽屉入口；不绕全貌页。

## 三、按身份动态显隐（核心规则）

> 不同身份看到的快捷条目**不同**。从 W6-P-FE 已落地的三态 status 取身份。

| 身份 | 应显示的快捷条目 |
|---|---|
| **🟢 在地居住**（onsite+在线） | 厨房录入 / 田间 / 大扫除 / 营地活动 / 提现 / 设置 |
| **🟡 外出**（away+云在线） | 营地活动 / 提现 / 设置（**无**厨房/田间/大扫除——人不在村无法操作） |
| **⚫ 离线** | 不显示 ⚡ 按钮（用户不在场，禁用整个抽屉） |
| **🟢 营地共建人**（camps.active 成员） | 在地基础上 +「营地提案区」（接 C 议事范式入口） |

**实现**：抽屉挂载时调 `AppData.getMyQuickEntries()`，根据 `user.status + camps.active` 动态生成条目。

## 五、动画 / 交互细节

- **打开动画**：从底部 `slideUp`（W6-UI 已落地，**直接复用**，不重写）
- **遮罩**：半透黑，点击关闭（W6-UI 已落地）
- **z-index**：高于全貌页所有层（≥1000），参考 W6-UI 的 z-index 设定
- **物理行为**：
  - iOS 橡皮筋下滑关闭（**待议**，P2）
  - 桌面端 esc 关闭（**待议**，多端未做）

**太傅注三行**：
- H 范式是"少点几步"总则的**唯一落地形态**——所有高频操作都该入抽屉，否则就是违反总则。这是底座 v0 之后**第一范式级硬约束**。
- 首批条目集中在 A 范式（P0 三条），是"治痛感最高" + "接 A 落地"双重逻辑——一营把 A 范式施工完，抽屉同时完工，不分两轮。
- 按身份显隐规则**不只看 role**，更看** W6-P-FE 已落地的 status 三态**——这是"楚门窗口"和"快捷抽屉"两个独立设计的**数据接点**首次在产品上打通。
