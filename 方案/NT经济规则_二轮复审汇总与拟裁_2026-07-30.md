## 二、丞相府对两条 ❌ 的实证核验（意见审查制，不盲从）

**❌ Q4-1 withdraw 破等式 → 实锤，且找到「等式×4」的候选根因**

| 阶段 | 代码 | 池/账变动 | 对 total_system 净效果 |
|---|---|---|---|
| 申请 | nt.py L478-480 | user −X, reserve −X, frozen +X | **−X（破）** |
| 确认 | admin.py L66-67 | frozen −X, total_issued −X | 两边同减，−X **永久留存** |
| 拒绝 | admin.py L87-91 | frozen −X, reserve +X, user +X | +X（回补，无残留） |

即：**每完成一笔提现，diff 永久 −提现额**。07-29 实测「×4」极可能 = 历史已完成提现累计 4 NT。可用一条 SQL 证伪/证实：`SELECT SUM(amount) FROM nt_ledger WHERE type='withdraw' AND status='settled'`，若 = |diff| 则根因坐实（写入 P0-2 卡为第一步）。

**❌ Q2 锁序不一致 → 实锤**
transfer(L219→L241)/_grant_from_pool(L261→L269)/withdraw(L453→L473)/cashout(L425→L430) 四路全部 **User先→Pool后**；verify_task(L669→L685) 是 **Pool先→User后**。PG 上 transfer×verify_task 交叉即 AB-BA 死锁对；transfer 的 from→to 亦未按 id 排序。**这不是拆表前置，是现网存量风险**，二营定位正确。

## 三、核心裁点：reserve 语义（唯一需要砚仁拍板的设计决策）

二营给出两个修法，丞相府拟裁 **方案 A**：

| 方案 | 内容 | 优劣 |
|---|---|---|
| **A（拟裁采纳）** | reserve 移出会计等式：定性为「链上兑付背书台账」，与 contribution_pool 同级（不计 total_system）。等式变为 `Σuser + operating + escrow + camp + frozen == total_issued`。withdraw 申请只动 user/frozen（净 0），reserve 扣减照旧但只作背书台账 | ✅ 等式最简、职责最清（NT 记账域 vs 链上背书域分离）；✅ 改动最小（只改 verify() 一行 + 文档正名）；⚠️ reserve 需另设独立校验（reserve ≥ frozen 待付合计） |
| B | reserve 留在等式内：申请阶段只校验 reserve≥X 不扣减，确认阶段 reserve −X 与 total_issued −X 同步 | ✅ 等式覆盖面大；❌ 确认阶段 reserve−X 与 total_issued−X 双减仍需 frozen−X 三方对齐，会计推演复杂，易再引 bug |

拟裁 A 的附带动作：P0-2 卡内含①上面那条 SQL 追账证实根因 ②verify() 改等式 ③补 `reserve_covers_frozen`（reserve ≥ frozen）独立检查 ④历史 diff 一次性核销（追账后出报告，砚仁签字后调平）。
