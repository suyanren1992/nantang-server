## P-1 · `activity_log` 表的真相

### 1. 完整 schema

```sql
-- models.py:215-220
CREATE TABLE activity_log (
    id    INTEGER PRIMARY KEY AUTOINCREMENT,   -- SQLite; PG 上为 SERIAL
    time  TEXT    NOT NULL,                      -- ISO 时间字符串，非 TIMESTAMP 类型
    type  TEXT    NOT NULL,                      -- 活动类型标签
    text  TEXT                                   -- 活动描述文本（可空）
);
```

| 属性 | 值 |
|---|---|
| 字段数 | 4（id / time / type / text） |
| 主键 | id（自增） |
| 外键 | **无** |
| 索引 | **无**（`_INDEX_DDL` 清单 30 条索引中无 activity_log） |

| 收件人字段 | **无** —— 不做小红点 |

## P-2 · `/api/notifications/list` 的真相

### 1. 实际 SQL

```python
# community.py:229-276
# 三条独立查询，各自 LIMIT lim（默认 30），然后 Python 端合并排序

# ① 公告表
select(Announcement).order_by(Announcement.created_at.desc()).limit(lim)

# ② 活动日志表
select(ActivityLog).order_by(ActivityLog.time.desc()).limit(lim)

# ③ 校核表（非 pending）
select(Verification).where(Verification.status != "pending")
    .order_by(Verification.verified_at.desc()).limit(lim)

# 合并后按 time 倒序，取前 lim 条
items.sort(key=lambda x: x.get("time") or "", reverse=True)
return items[:lim]
```

**不是从 `activity_log` 单表读**，是三表聚合（Announcement + ActivityLog + Verification）。`activity_log` 只是三个数据源之一。

### 2. 类型筛选参数

**无**。端点签名只有 `limit: int = 30`，没有 `?type=` 或 `?source=` 参数。三表总是全取。

### 3. 前端消费者

搜索结果显示 `/api/notifications/list` 只在 `community.py` 自身定义，**没有前端直接调用**。前端通知相关在 `ui-archive.js` 的"信箱系统"（`logActivity` / `updateInboxBadge` / `getInboxLastOpened`），但那套逻辑读的是 `AppData._data.activity_log`（内存），不调 `/api/notifications/list`。

> **推断**：`/api/notifications/list` 是后端预留端点，前端尚未对接。前端当前的"最近动态"展示全部走 `sync_all` → `AppData._data.activity_log` 内存态。

### 4. 设计原因

代码注释 `community.py:233`：
> "通报列表（聚合公告 + 活动日志 + 校核动态）"

历史 commit 未深挖（超出勘察范围）。但从代码结构看：Announcement 是校核系统的广播（doer/verifier/action/nt_amount），ActivityLog 是操作流水，Verification 是待校核/已校核动态——三者被归为"通知"聚合是合理的工程直觉，但**前端没接**，等于半成品。

## P-3 · 三件"动态流"的关系

### 明确回答：三者不是同一份数据的三个副本，而是三个不同维度的东西

| 名字 | 本质 | 持久性 | 数据结构 | 角色 |
|---|---|---|---|---|
| `activity_log`（DB 表） | **源头真值** | ✓ DB 持久 | 4 字段，无 user | **唯一写入源** |
| `/api/notifications/list` | **聚合视图** | ✓ 实时计算 | 三表合并，每表限 30 | **后端预留的"通知聚合"，前端未接** |
| `AppData._data.activity_log` | **前端缓存** | ✗ 内存 + localStorage | 与 DB 同构 + 本地未同步条目 | **前端的运行时镜像** |

### 谁是源头、谁是缓存、谁是镜像

```
前端写入（打赏等）
  │
  ├─→ 1. 写内存 AppData._data.activity_log（即时显示）
  └─→ 2. API.syncActivity() → POST /api/data/activity_log → DB activity_log（fire-and-forget）

页面加载
  │
  └─→ sync_all → activity 字段（最近 50 条 DB 记录）→ 智能合并到 AppData._data.activity_log
      合并规则（core.js:991-1000）：
        · 若服务端下发 activity_clear=true → 清空本地全量重建
        · 否则按 time+type+text 去重追加，不覆盖本地未同步条目

/api/notifications/list  ← 独立于上述链路，三表实时聚合，前端未使用
```

### 内存态刷新后

刷新后 `AppData._data.activity_log` 从 `localStorage` 恢复（`app-data.js:62` 初始化为 `[]`，然后 `_load` 从 localStorage 读回）。同时 `sync_all` 重新拉取服务端最近 50 条合并。

**但有一个边界**：本地用 `logActivity()` 写了但 `API.syncActivity()` 尚未完成就刷新的条目——因为 `syncActivity` 是 fire-and-forget，如果网络慢，刷新后这些条目会丢（内存未持久到服务端，服务端也未返回）。

## P-5 · 性能与并发

### 1. 写入事务

| 写入点 | 事务 | 回滚 |
|---|---|---|
| `data.py:131-137` `add_activity_log` | `db.add()` → `await db.commit()`，单条独立事务 | ✅ 写入失败即回滚（FastAPI 异常自动 rollback） |
| `tasks.py:265-267` `_log_activity` | 仅 `db.add()`，**不单独 commit**——依赖外层路由的 `await db.commit()` | ✅ 外层路由有 `with_for_update()` + 统一 commit，失败整体回滚 |

> `_log_activity` 是**半事务安全**：它自己不做 commit，依赖调用方。若外层路由 commit 前抛异常，activity_log 写入会一并回滚。但如果外层 commit 成功、后续逻辑抛异常（在 commit 之后），则 activity_log 已写入无法回滚——不过 tasks.py 的调用点都在 commit 之前，所以实际是安全的。

### 2. 读取索引

**activity_log 表无任何索引**。所有读取都是：
```sql
SELECT * FROM activity_log ORDER BY id DESC LIMIT N
```

在 SQLite 上 `ORDER BY INTEGER PRIMARY KEY` 走主键索引，影响不大。在 PG 上取决于数据量：
- **当前 3 行**（亲验）：无任何性能问题
- 10 万行：`ORDER BY id DESC LIMIT 50` 走主键索引（PG 自动用），仍然不慢
- 100 万行 + 无 `WHERE time > ...` 过滤：主键倒序扫描 LIMIT 50 依然很快（只扫 50 行）

**真正的问题不是全表扫描，而是没有时间范围过滤**——如果要"最近 7 天"动态，现在做不到（time 是字符串非 TIMESTAMP，无索引）。

### 3. 限流/分页

**全无**。所有读取端点只有 LIMIT 无 OFFSET，无法翻页。

### 4. "最近 7 天"索引

**无**。time 字段是 `String` 类型（非 `DateTime`/`TIMESTAMP`），无法建高效的时间范围索引。要做时间过滤需先改字段类型或至少加一个 `created_at TIMESTAMP` 索引。

## 结论：三档分类

### ✅ 可直接复用

| 资源 | 原因 |
|---|---|
| `activity_log` 表 + `POST /api/data/activity_log` 端点 | 通用写入通道已通，前端 `logActivity()` 已对接 |
| `sync_all` → `activity` 字段 | 启动 + 定时拉取最新 50 条，合并逻辑（去重）已就绪 |
| `AppData._data.activity_log` 内存态 | localStorage 持久 + 智能合并，刷新不丢 |
| `_log_activity()` 模式（tasks.py） | 后端内部写 activity_log 的标准范式，可直接照搬 |

### 🔧 需改造

| 资源 | 需要什么 | 原因 |
|---|---|---|
| `activity_log` 表结构 | 加 `user_id`（发起人）、`created_at`（TIMESTAMP 索引）、可选 `recipient`/`is_read` | 当前 4 字段无法做"我的动态"/"小红点"/时间过滤 |
| 读取端点 | 加 `?type=` / `?since=` / `?offset=` 分页过滤 | 当前只有 LIMIT N，无法按类型/时间翻页 |
| 写入覆盖 | 营地开营/结营/任务完成/物品流转 → 补 `_log_activity()` 调用 | 当前只有 task_retract/unclaim + 前端 tip 两类写入 |
| `/api/notifications/list` | 加收件人维度 + 前端对接 | 当前全员同一份，前端未使用 |
| 前端社区窗口渲染（`data.js:774`） | 从内存 activity_log 扩展为带类型图标/过滤的渲染 | 当前只无差别展示 text 字段 |
| `API.syncActivity()` fire-and-forget | 改为返回确认或加入重试队列 | 当前刷新时可能丢未同步条目 |

### 💀 死代码/半成品

| 资源 | 原因 |
|---|---|
| `/api/notifications/list` 端点 | 后端实现完整但**前端零引用**，等于僵尸端点。如果后续启用通知系统，需加收件人字段后重新设计 |
| `initActivityLog()`（`ui-archive.js:191` 起） | 一次性补历史：从 journal 提取 tip/encourage/role_change/camp_launch 写入内存 activity_log。**只写内存，不写服务端**，刷新后有效（localStorage），但不与后端同步 |
| `archive.py` 的 activity_log → "log" 分类 | 档案室里 activity_log 和 journal 被合并为同一分类 `"log"`，统一展示，但 activity_log 无作者字段（hardcoded `"system"`），journal 有作者——同一分类里两条目来源不一致 |
