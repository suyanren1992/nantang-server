# 异体对抗回执 · 反对派攻《授权分级三档草案》

> 受丞相令扮反对派，攻三轮。**立场声明**：本回执为受命对抗，非二营真实主张；
> 目的是压力测试草案防线，替砚仁探漏。每轮＝攻击点→草案防线是否成立→修补建议。

## 草案要旨（复述备查）
- **御笔亲裁**：push / 朝会终裁 / 席位 / 出口 / 立法
- **丞相代行·事后报备**：P 类小卡 / ZX 小卡 / 验收副署 / 挂账 / 派工行文
- **制度自动**：施工流程已覆盖事项
- **附则**：涉钱路径 / 禁区 / 跨营阵地 → 一律升档御笔

---

## 【前置攻击 · 程序合法性】
**攻击点**：授权草案由**被授权方（丞相府）自拟**，砚仁仅「批原则」未批细则。授权范围的定义权若也归被授权方，等于自我授权——「谁划范围谁得权」，程序上先天偏向扩权。
**草案防线**：无（草案未处理拟制方=受益方的利益冲突）。→ **不成立**。
**修补建议**：细则终稿须由**异体（非丞相府）或砚仁本人**主持定稿；草案通过后，其**修订权**亦不得由丞相府单方行使，须走朝会/御笔。此为后三轮的公共前提。

---

## 第一轮：代行范围会不会被「小卡」名义蚕食？

**攻击点**
1. 「P 类小卡 / ZX 小卡」**无客观分级标尺**——「小」由谁定义？若施工营/丞相自报「此系小卡」即落入事后报备档，**分类权 = 定档权 = 实权**，扩权只需改个称呼。
2. **实据打脸**：本轮刚办的 **P1-3** 卡面写「二营小卡」，改的却是 `covenant.py:157` 签署**发 NT** 路径（紧邻 `u.nt_balance += reward`）。按附则「涉钱路径升档御笔」它该御笔；按档位名称它是「P 类小卡」可代行。**同一张卡同时命中两档，草案内部打架**——证明「小卡」标签能盖住「涉钱」实质。
3. 「跨营阵地」同样模糊：G 系列多为「跨端卡」，二营可动前端、一营可动 server 端点，**阵地边界本就流动**，何谓「跨营」缺定义。

**草案防线是否成立**
- 附则「涉钱/禁区/跨营升档御笔」是唯一防线，**方向对但有致命定义缺口**：(a)「涉钱路径」边界未定——间接触钱（如行锁补丁、config 里的金额常量、退房结算单文案）算不算？(b)**分类由谁裁、争议如何处置未定**。若丞相自裁分档，则监察者兼分类者，既当运动员又当裁判。→ **部分成立，实操可被绕过**。

**修补建议**
- **标尺客观化**：分级用**可枚举硬指标**（改动是否触达 `nt_balance/pool.balance/ledger`、是否碰 withdraw/confirm/reject、是否改 `?v=`+push、LOC/文件白名单），而非「大/小」形容词。
- **争议默认升档（fail-safe）**：任一指标命中或分类有歧义 → **默认御笔**，不默认代行。宁可错升不可错降。
- **分类可回溯**：每次「判为小卡走代行」的分类决定本身**须记档并纳入报备**，砚仁/异体可追认或驳回。
- **月度抽检**：随机抽 N 张「小卡代行」由异体复核档位是否被错降。

## 第二轮：事后报备若砚仁长期不看，代行是否变默认授权？

**攻击点**
1. **报备是「推送」不是「确认」**。砚仁沉默 ≠ 同意，但代行**已既成事实**。长期不看 → 沉默被事实解读为默认授权 → **报备沦为形式，代行升格为常态授权**。
2. **实据打脸**：交接回执口径备忘 5.1 明载——`510cbf9..74374f8` **六个 commit 在丞相不知情下已上远程**，「事后才发现」。这证明**「事后发现」机制已经失灵过一次**；把更多事项交给「事后报备」是在失灵的机制上加载。
3. 报备**无状态机**：没有「已读/追认/驳回/时限」，报了就算尽责，砚仁的知情权被单向推送稀释。

**草案防线是否成立**
- 草案隐含假设「砚仁会及时看报备」。**此假设无任何保障**：无 SLA、无未读升级、无追认时限、无对账台账。→ **不成立**。

**修补建议**
- **可逆性作为硬门槛**：**不可逆操作**（push / 发钱 / 删分支 / 删数据）**一律不得走事后报备**，必须事前御笔。事后报备只允许承载**可回滚**事项。
- **追认时限 + 担责**：可逆代行事项设 T 时限，T 内砚仁未驳回则「暂生效但保留撤销权」，且代行方**对未追认期的后果担责**（防「先斩不奏」）。
- **强制已读回执**：涉钱/高频代行须砚仁**主动「已读」**方生效，纯沉默不视为同意。
- **独立台账周期对账**：所有代行事项进单独台账，异体或月度对账，防「报备散落无人汇总」重演六 commit 事故。

## 第三轮：与「push 闸口不可代行」「丞相不施工」两条既有铁律是否冲突？

**攻击点 A — push 闸口**
1. 草案把 push 列「御笔亲裁」，表面一致。但**后门在「制度自动」档**：若把 push 触发条件写进「施工流程已覆盖」的自动化规则（如「验收全绿 → 自动 push」），就等于用「制度自动」**实质代行了 push**，绕过御笔。
2. 「出口操作」定义与实践打架：批②第 4 条 `git push origin --delete fix/6-critical-bugs` 是出口操作，却由**一营执行**（砚仁亲批例外）。**御笔亲裁 = 每次亲批，还是一次性/条件式预授权？** 草案未界定；若允许条件式预授权，push 闸口形同虚设。

**攻击点 B — 丞相不施工**
1. 草案通篇未提**施工权归属**，却把「验收副署」列入丞相代行事后报备。**事实层面丞相已多重角色**：派工（P1-3 派工行文）+ 监察 + 代 commit（`219ce8b`）+ 偶尔亲工（K-2 `ee971b2` 破例）。**丞相既派工又副署验收 = 执行与监察合一**，违分权本意。
2. 「丞相不施工」若仍是铁律，则 K-2 亲工属破例，草案**未规定破例的授权与复检程序**，等于默许「监察者随时下场施工」。

**草案防线是否成立**
- push 一项**方向对**（列御笔），但**未封「制度自动」后门 + 未界定亲裁粒度** → **有缺口**。
- 丞相多重角色的利益冲突**草案完全未触及** → **不成立**。

**修补建议**
- **封后门**：明订「**制度自动**档产出的任何动作，若其效果等价于御笔级事项（push/发钱/删分支），必须**停在御笔前等亲批**，自动化不得跨越御笔线」。
- **界定 push 粒度**：御笔亲裁 push = **单次单笔亲批**，**禁一次性/条件式预授权**；出口操作（含删远端分支）同规格。
- **代行与监察分离入附则**：丞相**不得自我副署自己派工的验收**（须异体验收）；丞相**破例亲工须砚仁事前授权 + 事后异体复检**（K-2 已是范式，应写死为规则而非个案）。
- **角色声明**：每份行文标注丞相当前角色（派工/监察/代收/亲工），同一事项禁一人身兼裁判与运动员。

## 总裁决（反对派结论）
- 草案**大方向合理**（三档分权+涉钱升档），但**三处系统性漏洞**必须补齐方可法定：
  1. **分级无客观标尺 + 分类权归被授权方**（第一轮）——可被「小卡」名义蚕食，P1-3 已现形。
  2. **事后报备无状态机 + 不可逆事项误入代行档**（第二轮）——六 commit 事故证机制曾失灵。
  3. **「制度自动」后门 + 丞相多重角色利益冲突**（第三轮）——push 可被自动化实质代行，监察执行未分离。
- **一句话**：草案缺的不是「档位划得对不对」，而是**「谁来划、争议怎么办、不可逆的怎么办、自动化会不会越线」**这四个程序性护栏。补齐前，建议**只试行「制度自动」档 + 可逆的 ZX 小卡代行**，涉钱/push/验收副署**暂留御笔**，跑一个对账周期看报备机制是否真被查阅，再逐档解冻。
