## 壹、服务端

> 运行环境：Python 3.14（Render 默认），依赖清单在 [requirements.txt:1-9](../requirements.txt#L1-L9)。
> 共计 9 个依赖，以下逐条交代。

### 1.1 FastAPI — Web 框架

- **这是什么**：Python 写 API 的框架。一句话：你告诉它"这个网址干什么"，它帮你处理请求、校验参数、生成文档。
- **为什么选它**：① 砚仁已踩过 Flask 的坑——Flask 缺参数自动校验，手写一堆 `if not request.json.get("name")` 又脏又容易漏（补课 11 的血泪教训）；② FastAPI 自带 Swagger 文档页（`/docs`），前端和后端不用额外沟通参数格式；③ 异步原生支持——Neon Postgres 用 asyncpg 驱动，FastAPI 的 `async def` 天然匹配，不会像 Flask 那样异步是后装的补丁。
- **用在哪**：
  - App 入口：[server/main.py:54-59](../server/main.py#L54-L59) —— FastAPI 实例化，含 lifespan
  - 路由注册：[server/main.py:81-89](../server/main.py#L81-L89) —— 8 个路由模块挂载
  - 安全头中间件：[server/main.py:92-96](../server/main.py#L92-L96) —— X-Content-Type-Options
  - CORS 白名单：[server/main.py:62-77](../server/main.py#L62-L77) —— 四个精确域名，不含通配符
- **怎么算好**：① `/docs` 页面能打开且参数说明正确；② CORS 白名单不含 `*`（含 `*` + `allow_credentials=True` = CSRF 敞口）；③ 新加端点自动出现在 Swagger 里（FastAPI 自动生成，人工不需要动）。不这样会怎样：换 Flask 的话，参数校验要手写、API 文档要手写、异步要后装——三个手工活的出错率加起来够修一整天。

### 1.2 uvicorn — ASGI 服务器

- **这是什么**：让 FastAPI 真正跑起来的引擎。FastAPI 是"设计图"，uvicorn 是"发动机"——它接收互联网请求，转给 FastAPI 处理，再把结果送回。
- **为什么选它**：FastAPI 的官方标配。uvicorn 用 `uvloop`（C 写的底层事件循环），比纯 Python 的事件循环快 2-4 倍。Render 免费层只有 512MB 内存——用 uvicorn 单 worker 够用，不浪费。
- **用在哪**：
  - 本地启动：`uvicorn main:app --reload`（命令行，不写在代码里）
  - Render 启动命令：`uvicorn main:app --host 0.0.0.0 --port $PORT`（配置在 Render Dashboard，不在代码仓库）
  - 自部署 systemd：[server/deploy.sh:38](../server/deploy.sh#L38) —— `ExecStart` 指向 uvicorn
  - 生产依赖声明：[requirements.txt:2](../requirements.txt#L2)
- **怎么算好**：启动后 `curl localhost:8000/api/health` 返回 `{"status":"ok"}`（[server/main.py:99-101](../server/main.py#L99-L101)）。不这样会怎样：不用 ASGI 服务器（比如用 Flask 自带的开发服务器）上线——并发一上来就挂，Render 日志全是 `connection refused`。

### 1.3 SQLAlchemy — ORM（对象关系映射）

- **这是什么**：让你用 Python 代码操作数据库，不用手写 SQL 字符串。比如 `select(User).where(User.name == "砚仁")` 而不是 `"SELECT * FROM users WHERE name = '砚仁'"`。
- **为什么选它**：① 双库切换的核心——本地 SQLite 开发，线上 Neon Postgres 部署，SQLAlchemy 帮你翻译成正确的 SQL 方言，同一套代码两个库都能跑；② 异步支持（`AsyncSession`）——配合 asyncpg/aiosqlite，数据库操作不阻塞其他请求；③ 砚仁已踩过裸写 SQL 的坑——手写 `INSERT INTO` 拼接字符串容易被 SQL 注入，ORM 自动参数化。
- **用在哪**：
  - 引擎创建：[server/database.py:21-22](../server/database.py#L21-L22) —— `create_async_engine` + `async_sessionmaker`
  - 模型基类：[server/database.py:25-26](../server/database.py#L25-L26) —— `DeclarativeBase`
  - 所有模型定义：[server/models.py](../server/models.py) —— 18 张表的 Table 定义
  - 数据库初始化：[server/database.py:34-144](../server/database.py#L34-L144) —— `init_db()` 创建表 + 索引 + 轻量迁移
- **怎么算好**：① 同一个 `User` 模型在 SQLite 和 Postgres 上跑同样的查询不出错；② 参数化查询——所有用户输入走 `:param` 绑定，不会拼进 SQL 字符串。不这样会怎样：裸写 SQL 的话，换数据库要重写全部查询（Neon 和 SQLite 的 SQL 语法有差异），而且手写拼接 `f"WHERE name = '{user_input}'"` 等于给 SQL 注入开门。

### 1.4 aiosqlite — 本地 SQLite 异步驱动

- **这是什么**：让 Python 异步操作本地 SQLite 数据库的驱动程序。SQLAlchemy 是翻译官，aiosqlite 是嘴巴——真正跟 SQLite 文件对话的那一层。
- **为什么选它**：本地开发用的是 SQLite 文件（`nantang_fresh.db`），不需要装 PostgreSQL。aiosqlite 是 SQLAlchemy 官方推荐的异步 SQLite 驱动，配合 `AsyncSession` 不会阻塞事件循环。
- **用在哪**：
  - 依赖声明：[requirements.txt:4](../requirements.txt#L4)
  - 本地连接 URL：[server/database.py:8-9](../server/database.py#L8-L9) —— 默认 `sqlite+aiosqlite:///...`
- **怎么算好**：本地不装 PostgreSQL 也能跑完整 API（`python main.py` 启动）。不这样会怎样：不用异步驱动（用同步 sqlite3）的话，每次查询都阻塞整个服务——一个慢查询卡住所有人的请求。

### 1.5 asyncpg — PostgreSQL 异步驱动

- **这是什么**：让 Python 异步操作 Neon Postgres 的高性能驱动。比同步驱动（psycopg2）快 2-3 倍，专为 asyncio 设计。
- **为什么选它**：① Neon 只支持 PostgreSQL 协议——本地用 SQLite、线上用 Postgres，所以必须有一个 Postgres 驱动；② asyncpg 是 Python 生态最快的 PG 异步驱动（用 C 写的二进制协议，比 psycopg2 的文本协议快）；③ 已在 `DATABASE_URL` 转换链里落地——Render 给 `postgres://` 开头，代码自动转成 `postgresql+asyncpg://`。
- **用在哪**：
  - 依赖声明：[requirements.txt:5](../requirements.txt#L5)
  - URL 自动转换：[server/database.py:13-19](../server/database.py#L13-L19) —— `postgres://` → `postgresql+asyncpg://` + `sslmode` → `ssl`
- **怎么算好**：① 连接 Neon 不报 `unknown dialect`；② `sslmode=require` 被正确翻译成 `ssl=require`（asyncpg 不认 `sslmode` 参数）。不这样会怎样：用 psycopg2 的话，它是同步驱动——在 `async def` 里调用会阻塞整个事件循环；不翻译 `sslmode` 参数的话，asyncpg 直接拒绝连接。

### 1.6 python-jose — JWT 令牌

- **这是什么**：生成和验证 JWT（JSON Web Token）的库。登录后服务端给你一串加密字符串(token)，下次请求带着它，服务端就知道你是谁——不用每次输密码。
- **为什么选它**：无状态认证的标准实现。南塘云村用 JWT 是因为：① 移动端和 Web 端共用同一套 API，JWT 不依赖服务端 Session（适合 Render 免费层 15 分钟休眠后冷启动的场景——Session 在内存里，休眠就没了，JWT 不会丢）；② python-jose 是 Python JWT 生态最成熟的库，支持 RS256/HS256 多种算法。
- **用在哪**：
  - 依赖声明：[requirements.txt:6](../requirements.txt#L6) —— `python-jose[cryptography]`，带 cryptography 后端
  - 令牌生成与验证：[server/auth_utils.py](../server/auth_utils.py) —— `create_access_token()` / `decode_token()`
  - 环境变量 `JWT_SECRET`：[server/deploy.sh:77-83](../server/deploy.sh#L77-L83) —— 随机 32 字节 hex
- **怎么算好**：① 未带 token 的请求 → 401；② 带过期 token 的请求 → 401；③ 自带 token 的请求 → 正常返回数据。不这样会怎样：用 Session 认证的话，Render 休眠后 Session 全部丢失，所有人被踢下线重新登录；用自己写的加密拼接字符串——等于没加密。

### 1.7 bcrypt — 密码哈希

- **这是什么**：把用户密码变成不可逆的乱码存起来。即使数据库被拖走，攻击者也反推不出原始密码。
- **为什么选它**：bcrypt 是行业标准密码哈希算法——自带"盐值"(salt)防彩虹表、计算慢防暴力破解（故意让每次哈希花 ~0.3 秒，正常登录没感觉，撞库攻击跑不动）。比 SHA-256 安全不止一个数量级——SHA-256 太快了，一秒能算几百万次。
- **用在哪**：
  - 依赖声明：[requirements.txt:7](../requirements.txt#L7)
  - 密码哈希与校验：[server/auth_utils.py](../server/auth_utils.py) —— 注册时哈希、登录时校验
- **怎么算好**：数据库中 `users.password_hash` 字段存的是 `$2b$...` 开头的 60 字符字符串，不是明文。不这样会怎样：用 SHA-256 存密码 → 数据库泄露后攻击者跑彩虹表/GPU 撞库 → 几个小时撞出大部分密码；用明文存 → 直接看光。

### 1.8 pydantic — 数据校验

- **这是什么**：定义"什么样的数据算合格"的库。你说"名字必须是字符串，NT 数量必须是正整数"，pydantic 自动帮你拦下不合格的请求。
- **为什么选它**：FastAPI 的底层校验引擎。你写了 pydantic model，FastAPI 自动生成 Swagger 文档 + 自动校验参数 + 自动返回清晰的错误信息。不需要手写 `if not isinstance(name, str): return 400`。
- **用在哪**：
  - 依赖声明：[requirements.txt:8](../requirements.txt#L8)
  - 所有 API 请求/响应模型：[server/models.py](../server/models.py) —— 每个端点入参/出参定义
- **怎么算好**：发一个 `{"name": 123}` 给需要 `name: str` 的端点 → 返回 422 + 具体哪个字段错了、期望什么类型。不这样会怎样：手写校验的话，每个端点 N 行 `if` / `isinstance` / `ValueError`，漏一个就是 bug；而且没有 Swagger 自动文档——前端要挨个端点猜参数格式。

### 1.9 web3 — 链上交互

- **这是什么**：Python 与以太坊兼容链（OP 链）通信的库。读链上数据、监控转账事件、验证交易。
- **为什么选它**：南塘云村的 NT 代币在 OP 链上，需要监控链上转账来实现"充值到账"。[server/chain_scanner.py](../server/chain_scanner.py) 用它连接 OP RPC 节点、订阅 ERC-20 Transfer 事件、匹配用户充值意图。
- **用在哪**：
  - 依赖声明：[requirements.txt:9](../requirements.txt#L9)
  - 链扫描器：[server/chain_scanner.py:10](../server/chain_scanner.py#L10) —— `from web3 import Web3`
  - RPC 连接与合约监听：[server/chain_scanner.py](../server/chain_scanner.py) —— 全文件
  - 环境变量 `OP_RPC_URL`：[server/chain_scanner.py:13](../server/chain_scanner.py#L13) —— 可选，未配则扫描器静默跳过
- **怎么算好**：① 配置了 `OP_RPC_URL` → 服务启动后链扫描器在后台 run；② 没配置 → 静默跳过，不影响其他功能。不这样会怎样：自己写 RPC 调用（裸 HTTP + 手动 ABI 编码）→ 半年后 OP 链升级协议，你的手写代码全挂，web3.py 有人维护。

## 贰、数据库

### 2.1 Neon Postgres（线上）

- **这是什么**：Neon 是一个 Serverless PostgreSQL 服务。你创建一个数据库，它给你一个连接 URL，你用就扣 CU（计算单元），不用不计费。数据存在云端，不会因为 Render 休眠而丢失。
- **为什么选它**：① 免费层 100 CU-小时/月——南塘云村目前的小规模完全够用（数据库操作极少，大部分时间在 0 CU）；② Serverless 不操心运维——不用自己装 PG、调参数、做备份，Neon 自动处理；③ 分支功能——可以像 git 一样给数据库开分支，测试新功能不影响线上数据。
- **用在哪**：
  - 连接 URL 转换：[server/database.py:13-19](../server/database.py#L13-L19) —— Render 注入的 `DATABASE_URL` 环境变量
  - 生产连接：SQLAlchemy → asyncpg → Neon PG（自动链路，不需要代码改动）
- **怎么算好**：① 连接串以 `postgresql+asyncpg://` 开头，能成功建立连接；② Neon Dashboard 显示 CU 用量 < 100/月。不这样会怎样：自建 PostgreSQL → 要自己管备份、升级、安全补丁 → 砚仁的待办多一项"半夜收到数据库挂了"；而且 Render 免费层 512MB 内存跑不动 PG 实例。

### 2.2 SQLite（本地开发）

- **这是什么**：一个单文件数据库。没有服务端、不需要安装、不需要连接串——就是一个 `.db` 文件，Python 标准库自带。
- **为什么选它**：① 本地开发不需要网络——SQLite 文件在本地磁盘，启动即用；② 零配置——不像 PostgreSQL 要装服务、建用户、授权；③ 文件可以复制/备份——把 `nantang_fresh.db` 拷走就是完整数据库备份。
- **用在哪**：
  - 本地数据库文件：[server/database.py:8](../server/database.py#L8) —— `nantang_fresh.db`
  - 本地连接 URL：[server/database.py:8-9](../server/database.py#L8-L9) —— `sqlite+aiosqlite:///...`
  - 本地专属 PRAGMA：[server/database.py:37-39](../server/database.py#L37-L39) —— WAL 模式 + 外键约束
  - 种子数据：[server/db_dump.json](../server/db_dump.json) —— JSON 格式，可导入 SQLite 用于测试
- **怎么算好**：本地 `python main.py` 启动成功，访问 API 返回数据（不需要装 PostgreSQL）。不这样会怎样：本地强制用 PG → 每个新加入的开发者先花 30 分钟装 PostgreSQL、建库、配权限才能跑起来。

### 2.3 双库差异与锁陷阱 🔴

- **这是什么**：SQLite 和 PostgreSQL 有一个致命的差异——**行锁**。SQLite 不支持 `SELECT ... FOR UPDATE`（行级锁），但 SQLAlchemy 在 SQLite 下不会报错，而是**静默跳过**。结果：D-5（转账）/D-17（托管金）/D-26（日扣）的锁逻辑——在本地测试全部显示"锁住了"，上线到 Neon PG 后才真正生效。
- **为什么重要**：这是真金白银的 bug 来源。两个用户同时操作同一笔资金 → 本地 SQLite 测试时看起来串行化了（SQLite 整个数据库只有一个写锁），以为锁写对了 → 上线 PG 后并发写入，锁如果没写对 → 钱可能被重复扣/重复发。
- **用在哪**：
  - SQLite 静默失效的事实：[database.py](../server/database.py) 使用 SQLAlchemy AsyncSession，`with_for_update()` 在 SQLite 下发 SQL 但不生效
  - 受影响的三条资金路径：D-5 转账、D-17 托管金释放、D-26 每日住宿费扣款（宪法汇编 §二.1 编码规范第 2.1 节）
  - PG 集成测试：[K-2 任务卡](../方案/任务卡/K-2.md) —— 用真 PG 验证锁有效
- **怎么算好 / 不这样会怎样**：编码规范已落地（宪法汇编 §二.1）：① 资金/权限写路径必带 `with_for_update()` + `populate_existing`；② 锁有效性不以 SQLite 测试为凭——上线前必须跑 PG 集成测试。不守这规矩 → 本地测 100 次全绿，上线后被并发请求搞出负余额。

## 叁、前端

### 3.1 无框架原生 JavaScript

- **这是什么**：前端不用 React/Vue/Angular 任何框架，直接写原生 JS 操作 DOM。18 个 JS 文件，最小的 10 行（seed-test-data.js），最大的 2715 行（app.js）。
- **为什么选它**：① 南塘云村是**移动端 Web 应用**，不是 SPA——页面结构稳定（村口 → 三卡片 → 地图/任务/我的），不需要虚拟 DOM diff 那一套；② 零打包工具链——改了 JS 直接刷新浏览器，不需要 `npm run build`；③ 体积控制——18 个文件总计约 10,000 行 JS，用 React 光框架本身（react + react-dom）就有 ~130KB gzip，相当于现有全部 JS 的 3-4 倍；④ 砚仁能直接读代码改文案——不需要先学 JSX/Hooks/状态管理。
- **用在哪**：
  - 全部 18 个前端 JS 文件：[nantang-mobile/js/](../nantang-mobile/js/) 目录
  - index.html 引用清单：见下节 3.2
- **怎么算好**：① 改一行 JS → 浏览器刷新 → 立刻看到效果（无编译等待）；② 新加入的人打开 `index.html` 就能看完整页面结构。不这样会怎样：上框架的话 → 每次改文案要重新 build → 砚仁自己改不了（要先学 React）→ 一个文案改动也要走"发卡→AI 施工→验收"流程，三天等一个逗号。

### 3.2 index.html 引用清单

- **这是什么**：前端所有 JS/CSS 资源的入口清单。`index.html` 通过 `<script>` 和 `<link>` 标签声明每一个依赖。
- **为什么交代这个**：部署总检（deploy_check.py）的第二个检查就是"index.html 引用的每个 js/css 是否带 ?v="。引用清单是缓存刷新的唯一入口——漏一个文件，用户就拿不到更新。
- **CSS 文件（2 个）**：
  | 文件 | 版本 | 用途 |
  |------|------|------|

### 3.3 ?v= 缓存刷新机制

- **这是什么**：每个 JS/CSS 文件引用后面带 `?v=数字`，数字变了浏览器就知道"这不是同一个文件，重新下载"。铁律 2：凡改 `nantang-mobile/` 下 js/css，**同 commit 升 index.html 对应 ?v= 版本号**。
- **为什么选它**：最简方案——不需要 Webpack 的 content hash，不需要 Service Worker 的缓存策略。改文件 → 改版本号 → 提交。Render 自动部署 → 用户刷新拿到新文件。已经踩过两次"修了等于没修"的坑（缓存不刷新），所以上了机检强制。
- **用在哪**：
  - 所有 js/css 引用：[index.html:10-11](../nantang-mobile/index.html#L10-L11) (CSS) + [index.html:513-530](../nantang-mobile/index.html#L513-L530) (JS) —— 共 20 个 `?v=` 标注
  - deploy_check 检查②：[deploy_check.py:109-121](../server/scripts/deploy_check.py#L109-L121) —— 扫描所有本地 js/css 引用是否带 `?v=`
  - 铁律声明：[CLAUDE.md](../CLAUDE.md) —— 铁律 2
- **怎么算好**：deploy_check.py 检查②全 PASS = 20 个本地 js/css 引用全部带 `?v=`。不这样会怎样：没 ?v= 机制 → 浏览器缓存旧 JS → 前端 bug 修了但用户看到的是旧版本 → 浪费半小时排查"明明改了啊怎么还报错"。

### 3.4 PWA / 离线支持

- **这是什么**：PWA（渐进式 Web 应用）让网页像 App 一样——可以添加到手机桌面、离线也能看、有启动画面。目前**未实现**，在皇帝一页纸挂账在册。

## 肆、部署运维

### 4.1 Render Web Service

- **这是什么**：Render 是一个云部署平台。你把代码推到 GitHub，Render 自动拉取、安装依赖、启动服务、分配域名。南塘云村的生产环境就跑在 Render 上。
- **为什么选它**：① 免费层够用——512MB 内存 + 每月 750 小时（等于不停机），刚好覆盖南塘云村的用量；② push main 自动部署——git push 之后 Render 自动拉代码 + 装依赖 + 重启，不需要登服务器手动操作；③ 与 Neon 同一个生态——Render Dashboard 里能直连 Neon 数据库。
- **用在哪**：
  - Render 配置：在 Render Dashboard（不在代码仓库），关键参数：
    - Build Command: `pip install -r requirements.txt`
    - Start Command: `uvicorn main:app --host 0.0.0.0 --port $PORT`
    - 环境变量 `DATABASE_URL`：指向 Neon 连接串
  - CORS 白名单含 Render 域名：[server/main.py:65-66](../server/main.py#L65-L66) —— `nantang.imeeting.club` + `nantang-server.pages.dev`
- **怎么算好 / 不这样会怎样**：① Render Dashboard 显示 `Deployed` 绿色；② deploy_check 冒烟测试 PASS（[deploy_check.py:157-184](../server/scripts/deploy_check.py#L157-L184)）。**代价**：免费层 15 分钟无请求 → 自动休眠（冷启动首次请求约 3-10 秒慢）→ 不花钱 vs 速度，选不花钱。如果需要一直醒着 → 升付费层 $7/月，或加一个外部 cron 每 14 分钟 ping 一次 `/api/health`。

### 4.2 deploy_check.py — 部署总检

- **这是什么**：部署前跑一次的四合一检查脚本。纯 Python 标准库，不依赖任何第三方包（可以在没装任何东西的机器上跑）。
- **为什么选它**：丞相设计的部署闸口——push 上线前必须跑这个脚本，四个检查全绿才允许部署。不是"建议跑"，是"不跑不部署"。
- **四项检查**：
  1. **依赖对账**（[deploy_check.py:84-106](../server/scripts/deploy_check.py#L84-L106)）：扫描所有 `server/*.py` 的 `import`，逐一对照 `requirements.txt` 是否声明——多一个/少一个都报红。
  2. **?v= 一致性**（[deploy_check.py:109-121](../server/scripts/deploy_check.py#L109-L121)）：扫描 `index.html` 中所有本地 js/css 引用是否带 `?v=`。
  3. **环境变量清单**（[deploy_check.py:140-154](../server/scripts/deploy_check.py#L140-L154)）：汇总代码中所有 `os.environ` / `os.getenv` 读取的变量，标出必需/可选。

- **这是什么**：每月跑一次的依赖安全扫描脚本。用 PyPA 官方的 `pip-audit` 工具（数据源：OSV 开源漏洞数据库）检查 `requirements.txt` 里的包是否有已知漏洞。
- **为什么选它**：最低成本的持续安全——pip-audit 是 Python 打包官方（PyPA）维护的，漏洞数据库来自 Google 的 OSV 项目，覆盖全。月扫频率够用（南塘云村的依赖变更很慢），脚本纯 stdlib 不怕依赖漂移。

  - [server/scripts/security_scan.py](../server/scripts/security_scan.py) —— 全文件 101 行

### 4.4 arch_check.py — 架构一致性机检

- **这是什么**：检查"设计图纸"（架构现状图）和"实际工地"（代码）是否一致的脚本。架构图说这个模块有 200 行——代码真有 200 行吗？架构图引用了那个 JS——index.html 真引了吗？
- **为什么选它**：防设计漂移——写过文档的人都知道，Diagram as Code 最大的敌人是"图是上周画的，代码是今天改的"。arch_check.py 作为 CI 门禁，架构图更新不及时就亮黄灯/红灯。
- **五项检查**：
  1. **模块存在性**（[arch_check.py:72-78](../nantang-mobile/scripts/arch_check.py#L72-L78)）：基线所列 18 个 JS 文件是否全在磁盘上
  2. **行数漂移**（[arch_check.py:81-94](../nantang-mobile/scripts/arch_check.py#L81-L94)）：任一模块行数变化超 ±30% 亮黄灯
  3. **引用对账**（[arch_check.py:97-118](../nantang-mobile/scripts/arch_check.py#L97-L118)）：index.html `<script>` 标签 vs 磁盘实有文件，双向交叉对比
  4. **锚点新鲜度**（[arch_check.py:121-141](../nantang-mobile/scripts/arch_check.py#L121-L141)）：架构图文档的 commit 锚点落后 HEAD ≥10 个提交亮黄灯
  5. **旧文件存废**（[arch_check.py:144-148](../nantang-mobile/scripts/arch_check.py#L144-L148)）：`nantang-mobile.html`（旧单体文件）是否已删除
- **用在哪**：
  - [nantang-mobile/scripts/arch_check.py](../nantang-mobile/scripts/arch_check.py) —— 全文件 164 行，纯 stdlib
  - vault_gate 每日自跑会调用（闸第 0 项快照先行后触发）
- **怎么算好**：`exit 0`（全绿）。exit 1 = 黄灯警告（可交付但有漂移），exit 2 = 红灯阻断（有缺失模块或引用不一致）。不这样会怎样：没有架构机检 → 改了 3 个文件忘记更新架构图 → 三个月后架构图变成"fiction"（科幻小说）→ 新人看图以为 A 模块只有 100 行，实际已经 500 行了 → 设计决策基于过期信息。

### 4.5 cron — 每日定时任务

- **这是什么**：一个在服务端后台运行的循环，每天 00:05（UTC）自动生成周期任务 + 执行住宿费日扣。不依赖外部调度器（如 APScheduler/Linux cron），纯 asyncio sleep loop。
- **为什么这样设计**：ponytail 决策——不用 APScheduler 少一个依赖；不用 Linux cron 是因为 Render 容器里没 cron daemon。`asyncio.sleep` 算到下一个 00:05 的秒数，到期执行。单进程跑在 FastAPI lifespan 里（[main.py:32-37](../server/main.py#L32-L37)），跟 API 服务共享一个进程。
- **做什么（两大职责）**：
  1. **生成周期任务**（[cron.py:55-119](../server/cron.py#L55-L119)）：读 `config/periodic_tasks.json` 模板 → 按周期匹配（每天/每周几）→ 幂等检查（同一任务+日期不重复生成）→ 池余额够 → 扣池 + 创建任务
  2. **住宿费日结**（[cron.py:121-128](../server/cron.py#L121-L128)）：直接调用内部函数 `_run_daily_settlement()`，**独立 session** 隔离事务，不走 HTTP。
- **配置**：
  - 周期任务模板：[server/config/periodic_tasks.json](../server/config/periodic_tasks.json) —— 日常清扫（3 NT·1 人）、周末大扫除（12 NT·3 人）、库存盘点（8 NT·1 人）、翻堆肥（5 NT·1 人）
  - 激活变量 `CRON_ACTIVE`：[server/CRON_ACTIVATE.md:9](../server/CRON_ACTIVATE.md#L9) —— 设 `CRON_ACTIVE=1` 才生效
  - 幂等键格式：`{模板ID}:{日期}`，一天一条（[cron.py:78](../server/cron.py#L78)）
- **怎么算好**：① 次日 00:05 后任务大厅出现新的"日常清扫"系统任务；② `journalctl -u nantang -f | grep cron` 看到 `tick complete`。不这样会怎样：没有 cron → 社区池的钱永远花不出去（任务不自动生成）→ 营地住宿费永远不扣（经济系统空转）。

## 伍、链上

### 5.1 OP 链 NT 代币

- **这是什么**：南塘云村的 NT 代币部署在 OP 链（Optimism，以太坊的 L2 扩容方案）上。OP 链比以太坊主网便宜（Gas 费低 10-100 倍）、速度快（2 秒出块），适合小额高频的社区代币场景。
- **为什么选它**：① 以太坊生态兼容——OP 链是 EVM 兼容链，所有以太坊工具（web3.py/MetaMask/ERC-20 标准）直接用；② Gas 费低——主网一笔转账可能 $1-5，OP 链只要 $0.01-0.05，NT 的小额高频交易才跑得动；③ 现阶段链上只是"充提通道"——用户充 NT 上链 → chain_scanner 监听到账 → 自动录入系统，链上不跑业务逻辑（业务逻辑在服务端，快+便宜）。
- **用在哪**：
  - 链扫描器配置（全可选——未配则跳过）：[server/chain_scanner.py:13-17](../server/chain_scanner.py#L13-L17)
    - `OP_RPC_URL`：OP 链 RPC 节点地址
    - `NT_TOKEN_CONTRACT`：NT 代币合约地址
    - `PLATFORM_WALLET_ADDRESS`：平台冷钱包地址
  - ERC-20 Transfer 事件监听：[server/chain_scanner.py:20](../server/chain_scanner.py#L20) —— 标准 Transfer(address indexed from, address indexed to, uint256 value)
- **怎么算好**：① 配了 RPC URL → 链扫描器后台运行（[main.py:23-31](../server/main.py#L23-L31)），监听到转账 → 自动更新用户余额；② 没配 → 静默跳过，系统其他功能正常。不这样会怎样：没选好链 → 用主网 Gas 太高每笔 $1+ → 攒 5 个 NT 花 $1 Gas → 用户发现充值的钱还不够付 Gas → NT 经济没人用。

### 5.2 chain_scanner — 链上充值监听

- **这是什么**：一个后台 Python 协程，定时轮询 OP 链的新区块，找到发往平台钱包的 NT 代币转账 → 匹配用户的充值意图（DepositIntent）→ 自动记账到系统内。
- **为什么选它**：ponytail 单文件方案——不用 The Graph 索引（多一个外部服务依赖），不用 Webhook（OP 链不原生支持）。直接 RPC 轮询——虽然理论上有 30 秒延迟，但充值场景不要求秒到，30 秒够用。
- **用在哪**：
  - [server/chain_scanner.py](../server/chain_scanner.py) —— 全文件
  - 环境变量 `SCAN_INTERVAL`：[chain_scanner.py:16](../server/chain_scanner.py#L16) —— 轮询间隔（默认 30 秒）
  - 环境变量 `SCAN_START_BLOCKS_BACK`：[chain_scanner.py:17](../server/chain_scanner.py#L17) —— 启动时回补多少块（默认 500 块）
  - 断点续扫：[chain_scanner.py:33-46](../server/chain_scanner.py#L33-L46) —— `last_scanned_block.txt` 记录上次扫到哪
- **怎么算好**：① 用户向平台钱包转 NT → 30 秒内系统余额更新；② 重复转账不会重复记账（DepositIntent 匹配逻辑防重）。不这样会怎样：不用这个 → 人工查区块浏览器 → 手动给用户加余额 → 砚仁多一份"财务对账"的兼职。

### 5.3 多签钱包 — 规划中

- **这是什么**：多人签名才能动用的链上钱包。比如社区池的 NT 要转账 → 需要 3 个人里至少 2 个人签名 → 防止一个人卷款跑路。
- **为什么在规划中**：功能清单 F3（[功能清单.md](../方案/功能清单.md)）口径：「设计有/概念引用/未接入代码」。现阶段社区池资金量小（初始 500 NT），单签风险可控。资金池体量上来后（如接入 RMB 充值/外部资助）→ 多签就是安全必修课。
- **用在哪**：
